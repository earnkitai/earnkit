# v6.1.20: install attribution (people)

## Problem

`/api/stats` `installs` is `count(*) FROM installations`. The owner's people tracker reads the Postgres view
`owner_people` (role `earnkit_ro`), which v3.1/v4 defined over `builder_profiles`, written by v4's `ensureProfile` at X
sign-in. The v5 cut deleted that code and the view's definition, but left the legacy tables and the view in the
database, so nothing writes `builder_profiles` any more and the tracker stopped at 26 people (none after Oct 24). In v6
authorize is anonymous; a person (`builders`) exists only if the builder opens a link code and signs in with GitHub.
There is also no flag for the owner's, the CTO bot's and the journey campaign's installs.

## Design

- `people` (one row per person) and `installations.person_id`. Every install makes a person in the same transaction
  (`saveInstallation` -> `ensurePerson`). Linking (`linkInstallation` -> `linkPerson`) joins the installation to the
  builder's person (carrying a test reason), or makes the installation's person the builder's. Unlink leaves
  `person_id`; `deleteBuilder` sets `people.builder_id` NULL. People rows are never deleted.
- `testReasonFor` (`lib/v6/people.ts`, pure): `test_reason` NULL is real; else owner, dogfood, persona, repro or test.
  Sources: `EARNKIT_TEST_INSTALLATIONS`, `EARNKIT_OWNER_LOGINS`, `EARNKIT_DOGFOOD_LOGINS` (all optional), the repro
  client-name tag `l<lane>...-`, and the words dogfood, persona, journey in a client name. Applied at install (name) and
  at link (GitHub login); a reason is never cleared.
- Proven identity at install, `EARNKIT_INSTALL_SIGNIN` = `off` (default, anonymous) or `github` (and the OAuth app
  set up). Authorize validates as before, sets a `__Host-ek_install` nonce cookie and goes to GitHub with a signed
  state of kind `install` (own MAC label, `k: 'install'`, the pending request, 15 minutes). The callback dispatches on
  the state kind; for install it checks the nonce, exchanges the GitHub code, `upsertBuilder`, and `issueCode` with the
  builder in the signed code (`b`). `tokenPost` links the new installation after `installOnce`. Any GitHub failure is
  the plain sign-in-failed page; no code is issued. A link state never verifies as an install state or the reverse.
- `owner_people` is recreated over `people`, keeping the tracker's column names; see the architecture guide.
- `/api/stats` appends `installs_real`, `people`, `people_real`.
- `scripts/people-backfill.mts` (`lib/v6/people-backfill.ts`): dry run (READ ONLY transaction, rolled back) or
  `--apply` (one transaction, idempotent) gives each installation without a person one, from its builder, the legacy
  `builder_profiles` row keyed by the installation id (when the table exists; only existing columns), the owner of its
  last GitHub repo (claimed, unproven) or nothing (with the reason).

## Limits

- The legacy group root `COALESCE(old builder_id, id)`: `installations.builder_id` now holds the v6 builder, so the old
  v4 root id of a non-root installation is not recoverable; the backfill matches a profile by the installation's own id.
- `programs_accepted` is the won count (EarnKit has no accepted status).
- Installations created by raw SQL (no `saveInstallation`) have no person until the backfill runs.
