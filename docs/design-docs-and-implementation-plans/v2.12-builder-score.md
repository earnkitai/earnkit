# v2.12: The verified builder score

Status: built on branch v2.12 (2026-10-13); final review and owner go-live steps next.
Builds on v2.11 (main 2fc80b7, live). Paths are relative to `apps/frontend/lib/earnkit/`, except
`app/` (under `apps/frontend/`), `db/` (under `apps/frontend/`), `archive/`, `programs/` and `docs/`
(repo root).

**Goal.** Every person who installs EarnKit gets a filled, public, shareable profile on day one: a
0 to 100 score and a percentile computed only from verified outcomes of things they shipped, shown
on a premium page they want to post on X. Future work builds on that record.

**Why.** The share loop is the distribution engine, beyond crypto: the audience is anyone who ships
with AI, technical or not. The long-term asset is the verified, consented record of who shipped
what and who used it. Grant-finding stays, demoted to the money hook inside `score` and `find`.

## Owner rules (binding)

- Only verified outcomes score. Commits, deploys and token spend score 0 on their own. Nothing
  self-reported is ever scored or shown: the agent may propose sources, only the server verifies.
- Crypto-neutral. Onchain is one source among several. The profile and card never lead with chains.
- X is the visible identity. Other identities (GitHub, wallets, sites) are data sources only.
  Identity stays just-in-time: wallet at deploy, X at share. No onboarding form.
- Everyone who installed is listed. No opt-in. Hide only on request. Hidden people still count in
  percentiles. People who never installed are never listed.
- Empty profiles are EarnKit's failure, measured and driven down (section 3).
- Every new step writes a builder event to the existing v2.11 log (`events.ts`).
- Archive, don't delete (section 9). No table is dropped.
- Tools: keep `find`, `prepare`, `confirm`, `tell`; add exactly one, `score`.
- Cost stays flat: free APIs only, no new service, no new cron schedule. All work runs inside the
  existing hourly `/api/cron` budget.
- Copy: short, money first, no emojis, no em dashes, no tool names in builder text.
- Targets cover effort only. The empty-profile rate is a measured metric, not a target others decide.

## 1. People and identity

- **Person** = the existing `builder_id` group of installations (`identity.ts linkInstallations`).
  No new identity system. A person with one installation has `builder_id` set to that installation.
- New table **`builder_profiles`** (one row per person):
  `builder_id` PK, `x_handle` (nullable, validated `^[A-Za-z0-9_]{1,15}$`), `fallback_handle`
  (GitHub login, else short wallet `0xabcd…1234`), `slug` (unique, lowercased: x_handle else
  fallback), `hidden` boolean default false, `held` boolean (review hold, section 5),
  `card_offered_at`, `x_asked_at`, `created_at`, `updated_at`.
- **Public URL** `earnkit.com/b/<slug>`. When an X handle is added, the slug changes and the old
  slug 301s to the new one (table `profile_slug_history`: old_slug PK, builder_id).
- The page shows X as the name. Before X is given it shows the fallback handle.

## 2. Sources and readings

New table **`builder_sources`**: `id`, `builder_id`, `kind`
(`repo | site | package_npm | package_pypi | contract | merged_pr`), `ref` (canonical: `owner/repo`,
origin URL, package name, `chain:address`, PR URL), `project_key` (groups a repo, its site, package
and contract into one project card), `proof`
(`github_signin | proof_line | repo_owner | deployer | deploy_wallet | earnkit_txt | dns_txt | repo_link`),
`state` (`proposed | verified | rejected`), `reject_reason`, `proposed_by` (`agent | server`),
`created_at`, `verified_at`. Unique (`builder_id`, `kind`, `ref`).

New append-only table **`source_readings`**: `id`, `source_id`, `day` (date), `signals` jsonb,
`ok` boolean, `error` text. Unique (`source_id`, `day`). Same append-only trigger pattern as
`builder_events`.

| Kind | Ownership proof | Signals read | Read from |
|---|---|---|---|
| repo | own repo (not fork, not template, `repoEverDerived` false) or org repo where the person is top contributor | outside stargazers, forkers, issue authors, contributors (account ids + created_at), shipping weeks (commit weeks, last 52) | GitHub REST (`match-projects.ts gh()`), free |
| site | linked from a verified repo (homepage, `CNAME`, `vercel.json`, `wrangler.toml`, Pages), or `earnkit.txt` / DNS TXT naming the person | resolves (2xx), first seen, up today | plain fetch, HEAD then GET |
| package_npm / package_pypi | package metadata repo URL matches a verified repo | weekly downloads | npm downloads API, pypistats, free |
| contract | deployed by EarnKit's deployer for the person, or deployer address is a person's wallet, or address appears in a verified repo's `broadcast/` / deployments files | distinct callers (from, per day), calls, fees or volume in USD | existing RPC and getLogs (`verify.ts rpcFor`), Base and Arc |
| merged_pr | PR author is the person's verified GitHub login, merged, target repo not theirs | target repo outside stargazers (adoption weight), merged_at | GitHub search API |

- Each source is read at most once a day. The cron works a queue (oldest `last_read` first) within a
  per-run slice of the budget (section 6).
- X `twitter_username` from the person's GitHub profile is stored only to prefill the X question at
  share. It is never shown before the person confirms it and never scored.
- No Stripe in v2.12. `kind` is an open enum so Stripe (read-only OAuth, revenue) lands in v2.13 as
  one more kind without schema change beyond the enum.

## 3. Finding past work (cold start)

**When.** On the first `find` for a person, and again when a new clue arrives (wallet at deploy,
GitHub sign-in, a new local repo). Discovery never blocks a reply: `find` enqueues and answers.

**Clues, in order.**
1. GitHub login: sign-in or proof line if present; else the agent reports local `git config
   user.email` / remotes in `find` input (new optional field `local_git`), and the server resolves
   the login from remotes it can confirm (own repos with a matching push, as v2.11's proof rule).
2. All own public repos and org repos where the person is top contributor.
3. From those repos: homepage, `CNAME`, `vercel.json`, `wrangler.toml`, Pages URL (sites);
   `package.json` / `pyproject.toml` names (packages); `broadcast/**/run-latest.json`,
   `deployments/**`, hardhat-deploy files (contracts and deployer wallets).
4. Merged PRs by the login to repos they don't own (GitHub search, top 30 by target adoption).
5. Wallet given at deploy (existing `installation_wallets`): contracts it deployed on Base and Arc.
6. Local projects the agent can see with no GitHub (Lovable, Replit, v0, Bolt): the agent proposes
   the live URL; the server verifies via an `earnkit.txt` line the agent adds (same format family as
   v2.11's proof line).

**Empty-profile metric.** A person whose profile has no verified outcome 10 minutes after first
`find` (checked by the next cron run) gets one `profile_empty` event with `detail.missing`
(`no_github | nothing_live | ownership_unproven | read_failed`). `scripts/v212-metric.mts` prints
the empty rate for new installs per day. Expected under 10%.

**Filling an empty profile.** When empty, `find` and `score` lead with the single step that would
fill it, e.g. "Your site isn't linked yet. Add earnkit.txt so it counts?" One yes, the agent does it.

## 4. The score

Formula version `v1` and calibration version, both stored with every score. Absolute 0 to 100 within a
calibration (does not move when others join). Bars `Ubar`, `Mbar`, `Wbar`, `Dbar` come from the calibration.

| Part | Max | Input (after anti-farming) | Scale |
|---|---|---|---|
| Users | 45 | U = outside callers + outside stargazers + forkers + issue authors + contributors + merged-PR adoption credit + downloads/50 (weekly, 4-week mean) | 45 × min(1, log10(1+U) / log10(1+Ubar)) |
| Money | 20 | M = verified fees + 0.01 × volume, USD, last 365 days | 20 × min(1, log10(1+M) / log10(1+Mbar)) |
| Staying power | 15 | share of projects with an outcome still live or used Dbar+ days after first outcome | 15 × share, best project counts double |
| Recency | 10 | outcome weight with 90-day half-life | 10 × min(1, recent / max(1, all-time)) |
| Shipping consistency | 10 | commit weeks in last 52 on own non-fork, non-template repos that have at least one outside user | 10 × min(1, weeks / Wbar); 0 if no outcome anywhere |

- Score = round(sum). Commits, deploys, token spend alone produce 0.
- **Generous early, harsher later (owner ruling 2026-10-12).** The bars for full points are a
  versioned calibration (`score-calibration.ts`), not constants in the formula. Launch calibration
  `v1-launch` is generous so new people feel encouraged:

  | Bar | `v1-launch` | Later target (example) |
  |---|---|---|
  | Users for full 45 | 500 | 5,000 |
  | Money for full 20 | $5,000 | $50,000 |
  | Consistency weeks for full 10 | 13 | 26 |
  | Staying power threshold | 60 days | 90 days |

  Only the bars loosen. Verification and every anti-farming rule (section 5) stay strict from day
  one: generous never means gameable. Raw inputs are stored unscaled in `parts`, so any score can be
  recomputed under any calibration. Tightening is an owner decision (a new calibration version, never
  automatic). On a change, the profile shows the percentile as the headline, which keeps its meaning,
  and a one-line note ("Scoring got stricter on <date>; your rank is unchanged") when the person's
  percentile did not fall.
- **Percentile** = share of all scored people (hidden included) with a lower score, recomputed once
  per cron run after scores. Shown as "Top N%" where N = max(1, ceil(100 − percentile)).
- **Stored** in **`builder_scores`** (append-only, one row per person per day): `builder_id`, `day`,
  `score`, `percentile`, `parts` jsonb (each part's points and raw inputs), `top_outcome` jsonb,
  `formula` text, `calibration` text, `computed_at`. Latest row is the live score. History feeds the sparkline and
  "what moved it".

## 5. Anti-farming

Applied before the formula, unit-tested one rule per test.

- **Self-exclusion.** The person's own wallets, GitHub account, and members of their own orgs never
  count as users or fees.
- **One per account.** Each wallet or GitHub account counts once per project. Fees from any one
  wallet count at most 10% of a project's fees.
- **Spread.** Onchain users must appear across at least 3 distinct days per project. Users from a
  single day (when that day holds over 50% of all users) count at 25%.
- **Fresh accounts.** GitHub accounts under 30 days old and wallets whose first tx is in the same
  7-day window as their call count at 50%.
- **Rings.** If two people each count the other (mutual stars or calls), each counts the other once
  at 50%. A cluster of 5+ people mutually counting each other caps their in-cluster credit at 5.
- **Review hold.** A score that rises 30+ points in a day, or where one source is over 80% of the
  score and the score is 60+, sets `builder_profiles.held`. The public page and board show the last
  unheld score. The owner clears holds on `app/admin/scores` (`?key=` pattern, as `admin/veto`).
  Event `score_held`.

## 6. Cron

New steps in `cron.ts runCron`, after the existing steps, each with its own `CronDeps` field and the
usual `if (!opts.only || deps.X) try {...}` shape:
1. `discover` (drain discovery queue, max 20 people a run),
2. `readSources` (max 200 sources a run, oldest first, at most 1 read per source per day),
3. `scoreBuilders` (people with a new reading since their last score, plus everyone once a day),
4. `percentiles` (one SQL pass), then `profileEmpty` checks.
Budget: the four steps share at most 40% of what remains. No new schedule.

## 7. Surfaces

**Design.** EarnKit's own design system (deep navy `ek` tokens, Panel) plus two new accent tokens,
orange and purple, chosen to complement the navy; the score ring is an orange-to-purple gradient.
WHOOP principles, not WHOOP's look: one dominant number, few stats each with a one-line meaning,
trend over time, dark quiet premium surfaces, outcomes in plain words. The page gets a design review
pass and owner sign-off before shipping.

**Profile `app/b/[slug]/page.tsx`** (ISR 600 s; pure `ProfileView.tsx`, markup-tested):
- Hero: score ring, "Top N% of builders", 7-day change.
- Stat strip: the person's three strongest parts in words ("1,240 users", "$3.1k fees",
  "14 months live").
- Project cards: one per `project_key` with its verified numbers, sources, program entries and
  outcomes (won, submitted).
- Verified sources row (GitHub, site, onchain, packages), 90-day score sparkline.
- Never shows self-reported text, private repo names, or a wallet as the name.
- Held profile: last unheld score. Hidden profile: 404. No profile: 404.

**Share card `app/b/[slug]/card.png/route.ts`** (next/og, 1200×630, cached, same pattern as
`api/projects/[id]/mark`): ring, "Top N% of builders", the top outcome in words, the handle.

**The offer.** Right after the first verified outcome or the first backfilled profile with one, the
agent offers the card once ("You're top 12%. Want your card to post on X?"). Skip is one word.
Only here is X asked; the GitHub `twitter_username` prefills it ("Use @name?"). The share is an X
intent link; EarnKit never posts. Events `card_offered`, `x_added`, `card_shared` (on intent click
via a redirect route).

**Leaderboard `app/leaderboard/page.tsx`** (ISR 600 s; pure `LeaderboardView.tsx`): rank, name
(X else fallback), score, "Top N%", top outcome; each row links to the profile. Filters as query
params: `chain` (base, arc), `program` (any program id), `window` (`week` ranks by 7-day score
change, `all` by score). Hidden people are not listed. Held people show their last unheld score.
Paginated 50 per page.

**`score` tool** (5th tool, `mcp.ts` + `tools.ts`): returns score, percentile, change since the
previous call, what moved it (part deltas from stored `parts`), and one next action, the step with
the most expected points (fill an empty source, link a site, add a package, ship to users). When a
program fits with good odds, one line names it with its prize. Event `score_viewed`.

**"What can I earn?"** (`find` reply): two lines max.
```
Base Builder Grants: $5k, closes Oct 30, good odds.
You: score 41, top 22%. earnkit.com/b/jenilt
```

**Token pitch at confirm**: only when the person's live, unheld score is at least 20
(`TOKEN_PITCH_MIN_SCORE`, 20 under `v1-launch`, owner ruling 2026-10-12). Below that, never shown, never mentioned.

**Odds** (`match.ts traction`): use the person's verified users and money for the project instead
of commit counts and raw tx counts.

## 8. Consent and terms

- One line in the first `find` reply only: "Your public work gets a public score at
  earnkit.com/b/<slug>. Say hide anytime."
- "hide" via `tell` sets `hidden`; "show" clears it. Events `profile_hidden`, `profile_shown`.
- `app/terms` gets `#builder-profiles`: what is read (public sources only, plus what the person
  links), that profiles and the leaderboard are public, how to hide, that hidden people still count
  in percentiles, and that this data may transfer to a successor in a merger or acquisition.
  **Owner action: lawyer review of this section before go-live.**

## 9. Archive and simplify

Each archived feature moves to `archive/<feature>/` (code, tests, a notes file on its tables) with a
README: what it did, the flag, the steps to restore. Flag `EARNKIT_<NAME>=on`, default OFF. Its
tables stay, get `COMMENT ON TABLE ... IS 'archived v2.12'`, and receive no writes.

| Feature | Folder | Flag | Notes |
|---|---|---|---|
| Sponsor campaigns + `sponsor_campaign` tool, fund/award pages, check route | `archive/sponsor-campaigns/` | `EARNKIT_SPONSOR_CAMPAIGNS` | `contracts/` untouched |
| Starter registry beyond `arc-tipjar` | `archive/starters/` | `EARNKIT_STARTER_REGISTRY` | `arc-tipjar` stays the one starter |
| v2.9 tool aliases | `archive/tool-aliases/` | `EARNKIT_TOOL_ALIASES` | move lands with the 2026-11-09 expiry; until then they keep working |
| Per-program bonus boards, campaign board, bonus-round traction scorer | `archive/program-leaderboards/` | `EARNKIT_PROGRAM_LEADERBOARDS` | `/bonus/<round>` and `/campaigns/<slug>` 301 to `/leaderboard?program=<id>` |

- **Programs an agent can't complete** are filtered out of `find`: only those needing a
  go-to-market plan or a full-time team (owner ruling 2026-10-12: a team line and a demo video are
  agent-completable) (new program field `agent_completable: false`, set by `programs:sync` from those
  rules and overridable in the program file).
- **Security rounds frozen.** No new review rounds in v2.12 unless a test fails. The plan's reviews
  are code review only.

`source_proposed`, `source_verified`, `source_rejected`, `reading_taken` (one per source per day),
`score_computed`, `score_held`, `profile_empty`, `profile_hidden`, `profile_shown`, `card_offered`,
`x_added`, `card_shared`, `score_viewed`. All go through `noteEvent` with dedupe keys.

## 11. Testing

- Unit: each score part, each anti-farming rule, percentile and "Top N%" rounding, slug and
  redirect rules, program `agent_completable` derivation, discovery clue parsing (CNAME, vercel.json,
  wrangler.toml, broadcast files, package files) on fixtures.
- Golden: a farmed fixture (self-calls, one-day burst, fresh wallets, star ring) scores at or below
  its honest twin.
- Markup: `ProfileView`, `LeaderboardView`, card props (as `BoardView` tests).
- End to end (fixtures, no network): fresh install, `find` with `local_git`, cron discover, read,
  score, profile renders filled, `score` returns a next action.
- Archive: with each flag OFF the feature is absent; with it ON the existing tests for it pass.

## Out of scope

Stripe and other OAuth sources (v2.13), ERC-8021 builder codes (Base issues them only per wallet
via its API, no registry on Arc, and they would tag only our own tip page; contract indexing already
counts those users), posting to X, opt-in listing, listing people who never installed.
