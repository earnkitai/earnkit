# v3.8 E17: backtest storage, method version, `until` reads

Plan: v3.8 item 12 and section 18 ("The backtest"), section 9 (benchmark dataset). Approval: earnkitai/earnkit#159.
No flag: an admin script, dry run unless `--apply`. Nothing the app serves reads the new tables or the new option.

## What it does

`pnpm backtest --file <round.json> [--apply]` scores a past round from public data (a winner list or gallery) with the
screen's method as frozen in `METHOD_VERSION`, and asks: would the method have picked the actual winners?

- Round file: `program_id`, `round`, `until` (the submission deadline, an ISO instant with a zone), optional
  `source_url`, and entries (`ref`, `name`, `repo_url`, `live_url`, `contracts`, `won`, optional `builder_id` for an
  EarnKit user, optional `source_url`). Parsed with zod; repeated refs and a zoneless cutoff are refused.
- Each entry is read with `readEvidence({ now: until, until, cache: false })` and placed with `place(..., until)` and
  the shared-contributor count across the round (galleries carry no pitch). Picked = used, live or building.
  Hit = the pick agrees with the outcome; misses are printed with hits.

## The cutoff (`until`)

- `code.ts`: `GhRead.until`. The commit window asks GitHub with `&until=` and also drops any commit dated after the
  cutoff (or undated), so an answer that ignores the parameter cannot leak. The window memo key includes the cutoff.
  `last_push_at` is the repo's push date when not after the cutoff, else the newest commit read before it, else null.
- `team.ts`: shares the window, so contributors in the window are cut too.
- `onchain.ts`: `readContract({ until })` drops transactions after the cutoff before counting, so no later sender is
  sampled. When the explorer's newest 1000 hit the cap, the note says fewer before the cutoff may be counted.
- `evidence.ts`: `EvidenceDeps.until`; the cache is neither read nor written (its rows are as of their read). What has
  no history is read as it is today and named in `Evidence.leaked` (`leakedBlocks`): site, repo tree, releases,
  issues, fork share, contributors, contract source. These are "possibly leaked" in the report and stored per score.

## Public-safe output

The printed report is the form that may be shown: totals (winners picked, picks that won, hits, misses, entries with
possibly leaked blocks), then one line per entry. A non-user's line is name, `hit`/`miss`, and `won` when it won: never
a tier, flag or reason (section 18: no negative tier or flag next to a named non-user). Only an entry with a
`builder_id` shows its tier. No order of merit for anyone.

## Storage (private dataset)

Three additive tables in `db/schema.sql`: `backtest_rounds` (unique program and round, the cutoff), `backtest_entries`
(unique per round and ref; `builder_id` references builders ON DELETE CASCADE so a delete removes the rows),
`backtest_scores` (unique per entry and `method_version`: tier, flags, because, verdict, leaked, evidence rows and notes).
A score is never rewritten under the same method version (ON CONFLICT DO NOTHING); a round already stored with another
cutoff is refused and nothing is written. Bump `METHOD_VERSION` whenever placement, thresholds or readers change.

## Tests

`backtest.test.ts`: cutoff on code rows, on onchain rows and through a scored round (cache untouched, leaked named);
verdicts; the no-negative-label test (non-user lines carry no tier name, flag or reason; a user's carries the tier; no
rank wording); dry run writes nothing, `--apply` stores under `METHOD_VERSION`, a rerun keeps every score, another cutoff
is refused; round file validation.
