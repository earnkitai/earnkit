# v3.8 E18: screen order inside a tier, package readers, one review order (flag `screen_v2`)

Plan: v3.8 item 13 ("Quality filter") and section 9 ("Where you stand", k>=10). Approval: earnkitai/earnkit#159.
Stacked on E17 (`v38/e17-backtest`): it builds on E17's `evidence.ts` changes and the backtest reads `place` unchanged.

## What changes with `screen_v2` on

- **Order inside a tier** (`lib/v6/ordinal.ts`). `standing(rows)` gives points from verified evidence rows only. Those
  are the best counted mainnet contract's outside senders and transactions, npm and PyPI downloads, active weeks,
  commits in 60 days, contributors, releases, answered issues, tests and CI. Counts are log-scaled, so one huge number
  never decides. It returns the three reasons that carried the most points, in reviewer words. `ordinals(items)` sorts
  each tier by points (then ref) and gives `{ ordinal, of, reasons }`. The tier still decides; the order only sorts
  inside it.
- **The floor.** Below `ORDINAL_FLOOR` (10) applicants placed on read evidence (used, live, building), `ordinals`
  returns nothing. No applicant then carries `ordinal`, `ordinal_of` or `ordinal_reasons`, and the report prints no
  order. This is the "rank stays hidden until 10 verified builders" rule applied to a screen's reference class (the
  job). The screen's applicants are not EarnKit users, so the E3 count of verified people is not the class here.
- **Where it shows.** `jobResults` (the screen tool's results, reviewer-only) computes ordinals across the whole job and
  sorts each page by tier, then ordinal. The pilot CLI's markdown report sorts each tier by it and adds
  `order in <tier>: N of M, reasons`. A builder's reply never carries it, and `builderRules` keeps banning
  score and rank words.
- **Package readers** (`lib/v6/packages.ts`). The npm name comes from the root package.json (already read; not
  private). The PyPI name comes from the root pyproject.toml `[project]` name (one raw read). A package counts only
  when its registry entry links back to this repo (repository, homepage, bugs, project URLs). Downloads come from
  npm's last month and pypistats' last month. `readEvidence({ packages: true })` reads them uncached and never with a
  cutoff. The worker and the CLI pass `packages: flagOn('screen_v2')`. Rows use basis `registry`, which is public.
- **One review order.** `tiers.ts` `REVIEW_ORDER` is used, flagged, unverified (the CLI report's order, now shared). With
  the flag on, the tool's results use it too. Off, they keep main's order (unverified before flagged).

## Flag off

Identical to main. There are no package reads, no ordinals, and main's order. The one difference not visible to
users: a repo block cached from now on carries `package_names` (names only, never shown), so packages can be read
from a cached block once the flag is on.

## Migration

None. Ordinals are computed when results are read, from the stored evidence rows.

## Tests

`screen-v2.test.ts`: standing (verified rows only, log scale, reasons); no ordinal below 10 verified however many are
placed, every placed applicant at 10; the report renders no order below the floor (byte-identical to no ordinals) and
`order in live: 1 of 10` at it; `jobResults` with the flag on and 9 verified returns no ordinal key or rank word, with
10 returns ordinals across pages, sorted and flagged before unverified; flag off is main's order with no ordinal;
builderRules still bans rank; package names, pyproject parsing, repo links, and downloads only for a package that
links this repo.
