# v2.3: Token launch at submission

Status: implemented on branch v2.3-token-at-submission (not merged), 2026-10-04. Builds on v2.2 (`main` at 5c228f8). See "Rulings during implementation" at the end: they override the text above where they differ.

## Goal

Every builder who submits through EarnKit gets a token for their project by default. EarnKit proposes the name, ticker and logo. The builder sees what they'd earn and can change the token or skip it in one reply. A token launches only for a real project.

## Decisions (from the owner)

- **Default:** a token launches with the submission. One reply opts out ("no token"). The builder can change the name, ticker or logo.
- **Earnings preview:** shown before the builder confirms: "you keep 40% of trading fees, paid in WETH".
- **Funder policy:** `encouraged | allowed | off`. Encouraged and allowed **both** launch by default. Encouraged also shows "Entries get a token" on the campaign. Off means no token for entries.
- **Validity gate:** public repo (exists, not a fork, has commits) **and** a live link that loads. If the gate fails, the submission is still recorded; only the token is skipped, with the reason.
- **Logo:** the agent's generated image if it can make one, otherwise an EarnKit monogram.
- **Pairing and fees:** unchanged. tokens.fun already pairs every token with WETH and collects every reward share in WETH, the quote side (`clankerRewards.ts` `token: "Paired"`). The split stays as it is:
  - Clanker 20% protocol cut first;
  - then platform 50%, creator 40%, MINI buyback 10%.

  tokens.fun is part of EarnKit, and its platform share is tokens.fun revenue. EarnKit adds no fee share to tokens.
- **EarnKit's own revenue** is the 10% sponsor-campaign fee. It is paid to the company treasury `0xc8A889577446153e28D42254B75238Ae31EC7D57`, and the mainnet deploy is locked to that address (§7).

## State before v2.3 (verified 2026-10-03)

- **There is no default launch today.** `record_submission` returns a `next` text asking the agent to offer a token. `launch_token` is a separate call that needs the name, ticker, wallet, image and X handle.
- **Launches from EarnKit work as they are.** tokens.fun's `origin/main` deploy route accepts an `https://` `tokenURI` (`app/api/v1/deploy/route.ts:282`). An outdated local checkout required `ipfs://`; that is not what production runs. EarnKit keeps passing its hosted image URL.
- **tokens.fun limits launches:**
  - 5 an hour and 20 a day per client IP (in memory). Every EarnKit launch comes from one server IP.
  - 2 a day per creator wallet (`MAX_TOKENS_PER_USER_PER_DAY`, in the DB).
- **tokens.fun has no name or ticker blocklist.** `/api/check-ticker?symbol=` reports whether a ticker is already used on tokens.fun.

## 1. Builder flow

1. **`prepare_submission`.** Unless the policy is `off`, the response includes:

   ```
   token: {
     proposed: { name, symbol, image: "agent" | "monogram", image_url? },
     chain: "base", paired_with: "WETH",
     creator_wallet,            // payout wallet (campaign) or remembered wallet; null → ask once
     earnings: "You keep 40% of trading fees (after Clanker's 20% protocol cut), paid in WETH to <wallet>. tokens.fun pays the gas.",
     terms: { agreement, risks },
     policy: "encouraged" | "allowed",
     say_to_builder: "Submitting <project> to <program>, and launching $<SYMBOL> (<name>) with your entry on tokens.fun. "
                   + "<the earnings line> Terms: <agreement> · Risks: <risks>. Your repo needs earnkit.txt at its root with \"payout_wallet: <wallet>\" and \"token: <SYMBOL> <code>\" (this agent's line, when the repo is known). "
                   + "Change the name, ticker or logo, or say \"no token\".",
     note: "… The project's public GitHub repo needs a file named earnkit.txt at its root with the line \"payout_wallet: <creator wallet>\" (or \"creator_wallet: …\") and, for each launch, \"token: <SYMBOL> <code>\" (the exact line, when the repo is known) …"
   }
   ```

   (Ruling 12/Important 3: `say_to_builder` alone is the complete consent text — earnings line and both terms links included. There is no token block when launches aren't configured, i.e. `TOKENSFUN_DEPLOY_API_KEY` is unset.)

   The agent puts `say_to_builder` in the submission summary the builder confirms. The tool text says to generate a square logo if the agent can, and to pass it as `image_data`; otherwise EarnKit uses the monogram.
2. **`record_submission`** accepts `token`:
   - omitted: ~~use the proposal as is~~ — superseded by ruling 10: nothing launches; the reply is `skipped` with a note to pass `token: { name, symbol }`, and the proposal is stored for `launch_token`;
   - an object with any of `name`, `symbol`, `image_url`, `image_data`, `creator_wallet`, `builder_x`;
   - `"skip"`: no token.
   - (Ruling 13) the object is accepted loosely: echoing `token.proposed` verbatim (with `image`) never fails the call, `image` is ignored, and any other unknown key or a bad field gives `skipped` with a note naming it. `token: null` is the same as omitted. `builder_confirmed` accepts any value; only `true` counts.

   It records the entry first (unchanged behavior), then runs §3, then launches. The reply always includes `token: { status, … }`, with one of these statuses:
   - `launched` (address, tokens.fun link);
   - `skipped` (the builder said no, the policy is off, launches aren't configured, not confirmed, no explicit symbol, a bad token field, a refused edit, or the project or its repo already has a token);
   - `gate_failed` (the reason, plus what to fix);
   - `pending` (the outcome is unknown; check tokens.fun);
   - `failed` (tokens.fun's reason, or the daily launch limit; on the `launch_token` path also a refused edit, or an existing or pending token on the project or its repo).
3. **Consent.** The builder's single confirmation of the summary, which contains the token line, earnings and terms links, is their acceptance of the creator terms. `builder_confirmed: true` remains required on `record_submission` whenever a token is not `"skip"`.
4. **Later launch or retry.** `launch_token { project_id }` with optional overrides reuses the stored proposal and runs the same gate. "Launch the token" works after the builder fixes their live link or after the per-wallet daily cap resets. (Ruling 14) `launch_token` also takes `live_url` (any entry) and `repo_url` (not campaign entries: their repo was proven at entry); each passes `canonicalBuilderUrl` and is saved on the project (this installation's, no token yet; a campaign entry's `live_key` follows) before the gate. A refused edit on `launch_token` is `failed`.
6. **(Ruling 12) Limits on launches.** One launched or pending token per normalized repo across EarnKit (another entry of the same repo, e.g. a `record_submission` retried after a timeout, gets `skipped` at submission, `failed` on `launch_token`); at most 3 launches sent to tokens.fun per installation per day (`LIMITS.tokenLaunch`; over it is `failed`).
5. **`builder_x` becomes optional** everywhere.

## 2. Proposal rules (`token-proposal.ts`, pure apart from the ticker lookup)

- **Name:** the project name after the single-line untrusted-text rules, trimmed to 50 characters.
- **Ticker candidates, in order:**
  1. the initials of the name's words, if there are 3 or more;
  2. the first word's letters, cut to 6;
  3. the first word plus a digit, 2–9.

  Each candidate is uppercase A–Z0–9, 3–6 characters long. The first one that passes the brand check and is unused (`check-ticker`) wins. If `check-ticker` is unreachable, use the first brand-clean candidate and note "ticker not checked for duplicates".
- **Brand check:**
  - Names and tickers go through the reserved-brand check sponsor names use (`sponsor-identity.ts` `RESERVED_BRANDS`, the confusable skeleton, and the brand+suffix rule). Tickers additionally refuse an exact brand or brand symbol, e.g. BASE, CBBTC, USDC, ETH, WETH, MINI, EARN.
  - A name that fails is replaced by the project name plus " Token" if that passes. Otherwise there is no proposal: `token.proposed = null`, and the reason says to pick a name.
- **Builder edits** go through the same rules. A refusal names the rule; it never silently rewrites.
- **Monogram:** `GET /api/projects/:id/token-image`, a 512×512 PNG rendered with `next/og` `ImageResponse` (built in; no new dependency).
  - It shows 1–3 letters of the ticker on a background colour taken from a hash of the project id. The colour comes from a fixed palette of 12 colours chosen to give the letters enough contrast.
  - It is deterministic and cacheable.
  - The proposal stores which image source was used.

## 3. Validity gate (`token-gate.ts`)

All five checks must pass, in this order, stopping at the first failure:

1. **Policy:** the program's `token_policy` is not `off`.
2. **Repo:** the public GitHub repo exists, isn't a fork, and has at least one commit. This reuses the repo cache and GitHub lookup that ownership uses.
3. **Ownership (Ruling 12 and the owner-approved fix round):** the repo's `earnkit.txt` (the same file and fetch campaign entries use, `ownership.ts`) is read for every launch, campaign entries included, and must:
   - name the creator wallet: its `payout_wallet:` line, or a `creator_wallet:` line when `payout_wallet:` names another wallet (a campaign entry's proven payout wallet also counts);
   - carry `token: <SYMBOL> <code>` for the exact ticker being launched (symbol case-insensitive, code exact, extra whitespace tolerated; several `token:` lines allowed). **Ruling 17:** `code` is the first 10 hex characters of `HMAC-SHA256(EARNKIT_AUTH_SECRET, "token-line:" + installationId + ":" + normalizedRepo + ":" + SYMBOL)` (`tokenLineFor` in `token-gate.ts`, compared timing-safely). It is shown only to the launching agent (prepare_submission's token note and `say_to_builder` when the repo and ticker are known, and the gate_failed reason), never on public pages or to sponsors. Only someone who can push to the repo can add the line, and a line copied from the public file is refused for any other agent. Without `EARNKIT_AUTH_SECRET` the gate fails closed ("Token launches aren't configured right now.").

   Malformed `creator_wallet:` and `token:` lines are ignored and never affect campaign ownership checks. A missing file, another wallet, a missing token line, or a read error gives the exact lines to add (e.g. `Add the line "token: <SYMBOL> <code>" to earnkit.txt at the repo root (default branch), then call launch_token.`).
   The claim is bound to the links this gate checked (§6): if `repo_url` or `live_url` changed before the claim, nothing is claimed and the result is `failed` ("The project's links changed during the launch; call launch_token again.").
4. **Live link:** a `live_url` is present and fetches 2xx via `safeProbe` (5 s, no redirects to private addresses; one same-site redirect followed; User-Agent `EarnKit-linkcheck/1`). No live link, or one that doesn't load, says to "call launch_token with live_url".
5. **Creator wallet:** it passes the sanctions screen (`sanctions.ts`, fail-closed in production).

Each failure becomes `token.status = "gate_failed"` with a human reason and a fix. Results are not cached: each attempt re-checks.

## 4. Policy

- **Sponsor campaigns:** `sponsor_campaign create` takes `token_policy` (default `encouraged`). It is stored in `CampaignConfig` and shown in the create summary.
  - It's listed under "Defaults used" when it wasn't given.
  - It can be changed with `replaces` before funding. After funding it is fixed, because builders may have entered under it.
- **Program files and EarnKit campaigns:** an optional `token_policy` field, default `encouraged`. `ProgramFile` validates it.
- **Display:** encouraged shows "Entries get a token" on the campaign page and in `get_program` (not in `list_programs` rows: ruling 3). Allowed shows nothing extra. Off shows "No tokens for entries" on the campaign page.

## 5. Data

```sql
ALTER TABLE projects ADD COLUMN IF NOT EXISTS token_name   text;
ALTER TABLE projects ADD COLUMN IF NOT EXISTS token_symbol text;
ALTER TABLE projects ADD COLUMN IF NOT EXISTS token_status text;  -- skipped|gate_failed|pending|launched|failed
ALTER TABLE projects ADD COLUMN IF NOT EXISTS token_note   text;  -- reason / fix shown to the builder
```

- Existing columns keep their meaning: `token_url` is the claim plus the page link, and `token_image`/`token_image_type` hold an uploaded image.
- The atomic claim (`token_url = 'pending'` only if NULL, for this installation's project) is unchanged, so a lost response can never produce a second token.
- The migration is additive and idempotent, and runs through `predeploy`.

## 6. Launch call (`tokens.ts`)

1. **Claim** the project (existing).
2. **Deploy:** `POST {TOKENSFUN}/api/v1/deploy` as today. `tokenURI` and `imageUrl` are EarnKit's hosted image (the upload, or the monogram). `twitter` is included only if given.
3. **Outcomes:**
   - Success: `token_status = launched` and `token_url` is set.
   - A 4xx with a JSON body (a refusal before minting: validation, auth, the 429 daily cap): the claim is released, `token_status = failed`, and the note is tokens.fun's message. A 429 gives "try again tomorrow".
   - No response, a timeout (`EARNKIT_TOKENSFUN_TIMEOUT_MS`, default 120 s), any 5xx (e.g. tokens.fun's 502 "Deployment status unknown"), or a body that isn't JSON: the claim is kept, `token_status = pending`, and the note is "check tokens.fun before retrying". tokens.fun may have minted, so releasing could let a second token through.

   The submission is never rolled back.

## 7. Outside the EarnKit app

- **tokens.fun (separate PR in the tokens.fun repo, from `origin/main`):** a second key, `EARNKIT_DEPLOY_API_KEY`, is accepted by `/api/v1/deploy` and `/api/check-ticker`. Requests with it skip the per-IP limits, since every EarnKit launch comes from one server IP. The per-creator-wallet daily cap stays. Other callers keep `DEPLOY_API_KEY` and its IP limits. The owner sets the new key on both Railway services. EarnKit relies on this; until it ships, launches past 5 an hour fail with the 429 reason.
- **Contracts (`contracts/script/Deploy.s.sol`):** on chain 8453, `TREASURY` must equal `0xc8A889577446153e28D42254B75238Ae31EC7D57`, or the script reverts. Testnets and anvil are unchanged. Add a test.

## 8. Abuse and safety

- A token only launches for a recorded entry that passes the gate.
- Existing caps still bound volume:
  - 20 `record_submission` a day per installation;
  - 3 entries per campaign;
  - OAuth install limits per IP;
  - tokens.fun's 2 launches a day per wallet.
- Names and tickers are public and permanent, so they get the single-line text rules and the brand checks.
- The monogram endpoint renders only the stored ticker (validated A–Z0–9), never free text.
- Only a builder's own installation can launch for its project (existing claim condition).

## Known limitations

- **Ruling 15: brand logos aren't checked.** A logo passed as `image_url` or `image_data` is checked for type and size only; EarnKit doesn't detect a brand's logo in it. The name and ticker rules (§2) are the impersonation guard.
- **Ruling 16: a copied project passes.** A non-fork copy of someone's repo, entered with that project's live link, passes the gate: its `earnkit.txt` is the copier's own. The token's repo and fee wallet are then the copier's. Requiring a file on the live site as well was declined because it adds friction for every builder.
- Only EarnKit's own launch claims (`token_repo_key`) count for "one token per repo"; a `token_url` typed into `record_submission` is unproven and doesn't block a repo. Tokens launched before v2.3 have no `token_repo_key`.

## Out of scope

Dev-buy, vesting vaults, chains other than Base, any change to the fee split, AI image generation by EarnKit, and EarnKit-side fee tracking for tokens (tokens.fun's `fee_events` indexer already covers it).

## Rulings during implementation

- **Ruling 3: `list_programs` rows don't show the policy.** The "Entries get a token" line is on `get_program` and the campaign page only, to keep the list compact.
- **Ruling 10: an explicit, confirmed symbol is required.** `record_submission` launches only when `builder_confirmed: true` and `token` carries a `symbol`: the ticker the builder confirmed, echoed from `prepare_submission`'s `token.proposed` (or their change). An omitted token, or one without a symbol, gives `skipped` with a note saying to pass it; the proposal is stored so `launch_token` can launch it later. This supersedes §1.2's "omitted: use the proposal as is".
- **Statuses for an existing token:** at submission, a project that already has a token (or a launch in progress) gives `skipped` ("already has a token: <url>"); on the `launch_token` path it gives `failed`.
- **Claim release:** only a 4xx with a JSON body releases the claim; any 5xx keeps it `pending` (§6 above is updated to match).
- **The token never fails the submission:** `submissionToken` catches any error in the token part and returns `failed` with "say 'launch the token' to retry".
- **Ruling 12: tokens are tied to repo owners.** Every launch needs the repo's `earnkit.txt` to name the creator wallet (§3 step 3); one launched or pending token per normalized repo across EarnKit (`token_repo_key` + a unique partial index); at most 3 launches per installation per day. Launches aren't offered at all when the deploy key is unset.
- **Ruling 13: the token echo is loose.** See §1.2; `launch_token` stays strict.
- **Ruling 14: `launch_token` link overrides.** See §1.4.
- **Fix round (owner-approved): the claim is bound to the checked links, and every launch needs a `token: <SYMBOL>` line.** `deployToken` gets the repo and live links the gate checked and claims only while the row still holds them (§3, step 3). `earnkit.txt` must carry `token: <SYMBOL>` for each launch, campaign entries included. A `token` value that is neither `"skip"` nor an object gives `skipped` with a note.
- **Ruling 17: the token line is bound to the launching agent.** `token: <SYMBOL> <code>`, with `code` an HMAC of the installation, the normalized repo and the ticker (§3, step 3). A bare `token: <SYMBOL>` line, or one copied from someone else's file, no longer proves anything.
