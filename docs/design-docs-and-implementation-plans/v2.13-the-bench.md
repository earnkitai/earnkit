# v2.13 The Bench: one project, a weekly ship log, a way to get funded

Status: draft for owner review (2026-10-15). Branch `v2.13`, worktree `~/earnkit-v213`.
Flag: `EARNKIT_BENCH` (off = production as it is today, v2.12.2 with `EARNKIT_BUILDER_SCORE=on`).

## Why

The owner's thesis, in their words:

> "The high level thesis is connecting builders to capital via EarnKit."

> "Every serious ecosystem has converged on the same selection mechanism, public evidence of
> continuous shipping, and every one of them collects it in the most broken way possible: Google
> forms, Notion pages, X threads, Discord updates, read by three humans who then pick ten out of 750."

> "The solution is we evaluate builders and connect them to capital by deeply measuring them and
> scaling judgement: the portable, agent-verified ship log of a builder's work, written by their own
> agent from the repo and the deploys rather than self-reported."

> "The moat is proprietary data (the corpus of verified ship logs) with two-sided network effects
> (builders bring programmes, programmes bring builders)."

> "I as a founder want to help builders find capital whether it comes through a grant, a raise."

Reference product: DeltaV (deltav.monad.xyz). DeltaV lists startups, founders type weekly updates by
hand, the updates sit behind sign-in, and it ranks by "update weeks". EarnKit's edge is that the
update is written by the builder's own agent, the facts on it are checked by EarnKit, it is public,
and it is not tied to one chain.

## Who this is for

1. **The builder** (unchanged from v2.12.1): uses AI to build now and then, lazy, not technical, one
   project, little traction, wants money. They should never feel they are filling in a form. Every
   step must read as help: a page that grows, a streak, a rank, money they can go after.
2. **The ecosystem** (programs, grant teams, investors): wants to find builders who ship every week,
   on their chain, and see the proof in one place. In v2.13 they get public links only; no accounts.

## The flow

### 1. Install and connect X (unchanged)

The first reply carries the one claim link (Sign in with X). X is the builder's name everywhere: the
photo, earnkit.com/<x-handle>, the Bench.

### 2a. They have a project

The agent is in the project's folder. `find` gets one project:

```
identity.project = { name, what, repo (remote URL), live_url?, chain? }
```

- `name` and `what` come from the README and package files; `repo` from `git remote`; `live_url` from
  the README, package `homepage` or the deploy config. The tool description tells the agent exactly
  this, and to send the project it is in, not a list.
- An older agent that sends `identity.projects[]` (v2.12.x): the first entry is the project; the rest
  are ignored.
- **Proof that it is theirs:** the agent commits the existing proof line (the earnkit.txt line, v2.9
  `proof_line`) to the repo's default branch and pushes, in the same turn. The cron checks it. No
  sign-in, no question. GitHub sign-in stays as the fallback when the agent cannot push.
- **The project goes on the Bench as soon as the proof line is read.** Until then the page shows the
  project as "Confirming" and it is not ranked. The reply asks for nothing extra: the agent already
  did the proof.
- First ship log entry, written by the server at entry: "Started tracking <name>." with the facts
  EarnKit can already see (live, weeks shipping from the repo's commit weeks, people using it).
- **Reads:** one by-name GitHub read of the one repo per day (`readGithubRepos`, batched 25 projects a
  call across builders), plus the site, package, contract and coin reads that already exist. The
  person query (`readPersonGithub`) is no longer called on the reply path or the daily read under
  the flag.

Reply (the agent shows it as written):

```
Where you stand
Recipe planner is on the Bench: top 18% of builders, 6 weeks shipping.

Ways to get funded
Avalanche Team1 Mini Grants pays up to $10K and fits Recipe planner; it's open all year.

How to move up
Want me to post what you ship here every week? It keeps your streak going on the Bench.
```

While confirming: "Recipe planner joins the Bench as soon as I've confirmed it's yours (a minute or
two)."

### 2b. They have no project

The reply leads with money they can go after, phrased as ideas, and the one yes builds it (v2.11
starter flow: built, online, entered). That project is their project.

```
Where you stand
You're not on the Bench yet. Pick something to build and you're on it today.

Ways to get funded
Arc pays up to $10K for payment apps. Base pays up to $5K for a live app.

How to move up
Want me to build a tip jar on Arc and put it online? It takes a few minutes and you won't have to do anything.
```

### 3. Every week: the ship log

- **The yes, once.** Asked at the first reply after the project is confirmed: "Want me to post what
  you ship here every week? It keeps your streak going on the Bench." Stored as
  `builder_profiles.updates_on_at`. The builder can turn it off ("stop posting updates").
- **Who writes.** The agent schedules a weekly task (`schedule_weekly_update` in the reply, replacing
  `schedule_daily_check` under the flag). The task reads `git log` for the week and what it deployed,
  writes the update, and calls `tell update { text }`. Agents that cannot schedule get the ask in
  the reply's last line when the week has no update yet: "Want me to post this week's update?"
- **The text.** One paragraph, at most 280 characters, plain words. Links are allowed only to the
  project's own live URL or repo. The same banned-word and secret checks as other agent text. One
  update per project per ISO week: a second `tell update` in the same week replaces the text.
- **The facts.** EarnKit attaches the week's facts it checked itself, as chips on the card. The text
  never sets them.

| Fact | Source | Chip |
|---|---|---|
| `shipped_code` | Commits to the repo's default branch dated in the week (by-name read; count kept per week) | "12 commits" |
| `went_live` | First week the site answered, an EarnKit hosting, or a deploy | "Went live" |
| `users_up` | `people_week` grew | "+31 people" |
| `earned` | Coin creator fees or a prize booked in the week | "$120 earned" |
| `won` | An announced program win in the week | "Won Base Builder Grants" |
| `streak` | Consecutive ISO weeks with `shipped_code`, `went_live` or an EarnKit deploy | "6 weeks in a row" |
| `raising` | The project is raising (R8) | "Raising $RECIPE" |

- **New dated events** (in `builder_events`): `shipped_code`, `went_live`, `users_up`, `update_posted`,
  `update_hidden`. Each has a dedupe key per project and week.
- **Edit and hide.** `tell update { text }` in the same week edits it; `tell update { hide: "<week>" }`
  hides one. Hidden updates leave the profile and the feed; the facts still count toward the score.
- **No label** saying an agent wrote it (R6).

### 4. Optional: raise

- **When it is offered.** At the existing coin moments (v2.12.1 `coin_moments`: went live, countable,
  first five people, has people) and once at the fifth week in a row of shipping. One line, last in
  the reply: "Want to raise for Recipe planner? I'll launch $RECIPE on tokens.fun and you get 40% of
  its trading fees." The ticker is named before the yes, as today.
- **On the yes.** The existing launch path (`token-launch.ts`, `tokens.ts deployToken`) runs. The
  project gets `raising_at`. The pill shows while the coin is launched and `raising_at` is set.
- **Stopping.** "Stop raising" (`tell coin { raising: false }`) clears `raising_at`; the coin stays.
- **A coin launched before v2.13** does not turn the pill on by itself (R8). Its builder gets the
  same one line, worded "Want to show you're raising with $X?".
- **Stored at launch** (new): `coin_tx` (tokens.fun `txHash`) and `coin_chain_id` (`chainId`).
  tokens.fun does not return the pair; it is not stored.
- **The pill:** "Raising $RECIPE" linking to the tokens.fun page. Factual: it names the coin, nothing
  about returns. Go-live step: the owner's lawyer approves the word "Raising" and the one line.

### The last line: one question, in this order

The reply's last line asks one thing, the first that applies:
1. No project: the build offer (2b).
2. Not live: put it online (v2.12.2 `go_live`).
3. Weekly updates not on: the updates yes.
4. Updates on but none this week, and the agent cannot schedule: post this week's update.
5. A coin moment: the raise line.
6. Otherwise: the best-fitting program.

### 5. Ways to get funded

The reply heading "Ways to earn right now" becomes "Ways to get funded". It lists the programs that
fit the one project (grants, prizes) and, when raising, nothing more about the coin. Program matching
uses the one project only.

## The Bench

### Population

Ranked: the project is confirmed, the builder claimed X, not hidden, not held (the v2.12.1 rules,
now per project). One builder, one row.

### Order

Score v2 on the one project, as computed today, with Consistency drawn from the new weekly facts as
well as commit weeks.

### Percentile (R13)

- `P = 100 * rank / total`.
- Shown as "Top P%" only when `total >= 20` and `P <= 50`.
  - P of 1 or more: rounded up to a whole number ("Top 4%").
  - P under 1: rounded up to one decimal ("Top 0.3%"), never below 0.1 ("Top 0.1%").
- Under 20 ranked in the pool: "#N of M", only in the top half.
- Outside the top half: no rank line, only the streak and facts.
- The word "percentile" never appears.

### Chains (R14)

- A project is on a chain when it has, on that chain:
  - a confirmed contract;
  - an EarnKit deploy;
  - a launched coin;
  - an entry in a program whose `chains` names that chain.
- Shown chains: Base, Robinhood Chain and Arc only, each as its logo with the name as alt text and a
  tooltip.
- A chain chip appears on the Bench only when 10 or more ranked projects are on it.
- Per-chain rank uses the same percentile rule inside that chain's pool ("Top 1% on Base"). A
  profile shows a chain's rank line only when that chain's chip would show (10 or more ranked).

### Filters (R9)

- Chain (the logo chips), Raising, Shipping every week (a streak of 4 or more).
- Each filter is a URL parameter (`/bench?chain=base&raising=1&weekly=1`), so an ecosystem lead can
  bookmark "top builders on Base who are raising".
- This reverses the v2.12.1 ruling that the leaderboard ignores parameters. The set of variants is
  small (4 chains × 2 × 2), each cached with `s-maxage 60`.
- `/leaderboard` redirects to `/bench`.

### Row

- X photo, name, @handle, Raising pill when raising, chain logos.
- The project name and its best fact ("31 people this week", "6 weeks in a row").
- "Top N%" on the right.

## The feed (R7)

- Every week's visible updates with at least one fact are ranked by progress points:

| Fact | Points |
|---|---|
| `went_live` | 40 |
| `won` | 40 |
| `users_up` (n people) | `min(30, 6 * log2(1 + n))` |
| `earned` ($d) | `min(20, 5 * log2(1 + d / 10))` |
| `shipped_code` | 10 |
| `streak` (w weeks) | `min(10, w)` |

- Ties: the higher Bench score first.
- The feed shows the top 20 of the last finished ISO week, then older weeks.
- Updates with no facts never reach the feed. They still show on the profile.
- **Owner control:** `pnpm feed:pin <update-id>` and `pnpm feed:hide <update-id>`. These are owner
  scripts, like `events-redact.mts`. A pinned update leads its week; a hidden one leaves the feed
  and stays on the profile.
- **Where it shows:** `/feed` (long cards) and the landing carousel (square cards, the top 12).

- **Header:**

  - the rank lines (the Bench, then each chain the project is on, with its logo).

  number out of its weight.
- **Shipping grid:** 52 squares, one per ISO week. Filled when the week had `shipped_code`,
  `went_live` or an EarnKit deploy. The streak count sits next to it.
- **Ship log tab (default):**
  - long rectangular soft-edged cards, newest first;
  - each card shows the week, the update text and the fact chips;
  - weeks with facts but no update show the chips alone.
- **Project tab:**
  - the name, what it is, the live link and the repo;
  - its chain logos;
  - people using it, and money (fees, prizes);
  - the coin, with its tokens.fun link;
  - programs entered and won;
  - the programs it fits now ("Ways to get funded").
- **Sources line:** kept and shortened. "Facts come from public data EarnKit checks: GitHub, the
  live site, packages and public transactions."
- **Card (OG image):** photo, name, "Top 4% on the Bench", project name, the streak.
- **Design:** the existing design system (dark navy, the orange and purple accents, the WHOOP
  lessons from v2.12):
  - no all-caps labels;
  - no jargon ("outcome", "percentile", "signal");
  - every surface works at phone width.

## Tools

- `find`:
  - takes `identity.project` (one);
  - the reply carries the three sections above;
  - `schedule_weekly_update` replaces `schedule_daily_check` under the flag.
- `tell`:
  - `update { text }` posts or edits this week's update;
  - `update { hide: "<YYYY-MM-DD>" }` hides one;
  - `updates { on: boolean }` turns weekly posting on or off;
  - `coin { raising: boolean }` starts or stops raising.
- `score`: unchanged in shape; it returns the percentile lines and the streak.

## Cost

- **GitHub:** reads fall, from one person query per builder (100 repos, heavy) to one share of a
  25-repo by-name call per builder per day.
- **Storage:** one update row per project per week.
- **New services:** none. No paid X API: the photo refreshes at sign-in only.
- **Cron:** the hourly cron gains the weekly facts step (Mondays, after the digest) and the feed rank
  step (once a day).

## Acceptance test (the owner, on production, before "done")

1. **With a project.** In a project folder with a GitHub remote, install EarnKit fresh and connect X
   from the first reply's link.
   - The first reply names the project.
   - Within one more reply (after the proof line is read), the project is on the Bench.
   - earnkit.com/<x-handle> shows:
     - the X photo;
     - the Started-tracking card with its facts;
     - the Project tab.
2. **Without a project.** In an empty folder:
   - the first reply leads with ways to get funded and one build offer;
   - one yes leads to a live starter, and to the Bench.
3. **Weekly update.** Say yes to weekly updates, then ask the agent to post this week's update now.
   - A long card shows on the profile with its chips.
   - If it has a fact, it is in `/feed`.
4. **Bench filters.** `/bench?chain=base` lists only Base projects, with the Base logo.
   - A Base builder's profile shows "Top N% on Base" (or "#N of M" under 20).
5. **Raise.** Say yes to raising.
   - The coin launches.
   - The pill shows on the profile, the Bench row and the card.
   - "Stop raising" removes it.
6. **Landing page:** shows the Bench top 10 and the carousel of square cards.
7. **Builder bonus:** no builder bonus text anywhere a builder can see (replies, landing, program
   pages, terms).

## Not in v2.13

- program or investor accounts;
- likes or follows;
- the monthly top-builders email;
- a second project per builder;
- reading commit messages on the server;
- chains other than Base, Robinhood Chain and Arc on chips;
- Robinhood Chain contract reads (its chip comes from coins and program entries until then).

## Risks

- **Raising language.** A coin framed as a raise is closer to an offering than a coin framed as
  fees. The pill is factual and the owner's lawyer approves it before the flag goes on.
- **Agent-written text.** It can overstate. The facts on each card are EarnKit's own, and only
  updates with facts reach the feed. The text is capped, checked and hideable by the owner.
- **Small pools.** Per-chain pools will be small at first. The "#N of M" fallback under 20 and the
  10-project chip threshold keep numbers honest.
- **Losing the multi-project view.** Builders with several projects show only the one their agent
  entered. That is R1; the data stays for later.
