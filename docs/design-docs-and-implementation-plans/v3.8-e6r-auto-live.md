Plan: `/workspace/cto/earnkit-power-user-plan-v3.8.md` item 5, decisions 21 and 25, cutover A1. Build-plan row E6.
Approval: earnkitai/earnkit#159. Supersedes #164 (built on an older main, and it deleted the approval path while

## The rule

`POST /api/programs/write` upserts take one of two lanes (`automatedLane` in `programs-api.ts`):

- **Automated lane** (E6's official-page check: quotes on the page and tied to the record, organizer status,
  information only; `official-page.ts`). Taken when any of these holds:
  1. `auto_live` is on (`EARNKIT_FLAGS`): every write.
  2. The writer asks for it by sending any of the check's fields (`amount_quote`, `deadline_quote`, `found_by_query`,
     `found_by_source`, `handle`, `evidence_url`). This is how Growth's writer (the `EARNKIT_PROGRAMS_TOKEN` bearer)
     uses it. Main's envelope is strict, so main refused every such body with a 400. No existing caller sends them,
     and nothing that worked on main changes.
  3. The caller is the owner or a test account. This is case 1 for them: `/api/programs/write` runs in the /me
     session's flag context (`withSessionFlags`, main's owner/test flag preview, #187), and `auto_live` is in
     `PREVIEW_FLAGS`. The callers are main's: a person flagged owner, test, persona or dogfood, or an env-list login or
     installation (built-in owner logins, `EARNKIT_OWNER_LOGINS`, `EARNKIT_DOGFOOD_LOGINS`,
     `EARNKIT_TEST_INSTALLATIONS`); not `repro`. No session, a normal builder, or a failed lookup follows
     `EARNKIT_FLAGS`, so they keep main's lane. (The first E6r draft had its own `lib/v6/preview-caller.ts`; it was
     replaced by the shared preview on rebase.)

  A passing write goes live at once, labelled as the check found. A failing one is a 400, audited with its found-by
  fields. It is never held, never mailed and never given an approve link (`no-approval.test.ts`, H5).
- **Main's lane** (everything else): the code is unchanged. A create, or a link, chains, form or gate change whose
  links don't check out, is held; the owner is emailed the signed approve link; the confirm page and
  `POST /api/programs/approve` apply it (`approval-while-off.test.ts`, plus the untouched `programs-api.test.ts`).

## Why the bearer alone does not pick the lane

There is one programs token. Today Jenil AI holds it; the plan moves it to Growth at cutover (item 16). If the token
alone chose the automated lane, Jenil AI's current writes (no quotes) would start failing with 400 "amount_quote:
required". Main's behaviour would break and adds would stop. Opting in per request keeps main's behaviour for those
writes and gives Growth the new lane now.

## Kept until auto_live is on for everyone

The approval email (`mailPending`, `pendingMailText`, `PENDING_SUBJECT`, `owner_emailed`, `MAIL_FAILED`), the signed
approve link, the confirm page and `app/api/programs/approve`. `no-approval.test.ts` allows them only in three legacy
files (`LEGACY`). The draft follow-up PR "delete old program approval path (land when auto_live is on for everyone)"
deletes them, empties `LEGACY` and restores the route-gone check.

## Flag-off identity with main

- Main's lane is byte-identical: no field is added to its responses, and its audit rows store null found-by fields.
- `GET /api/programs/writes` shows `found_by_query`/`found_by_source` only on rows that have them. Rows written by
  main's lane read exactly as before.
- `find` and `track` change only for a program carrying `new_organizer`/`info_only`. Only the automated lane sets
  those fields.
- New requests that main refused now work: the `handle` action, and an upsert with check fields.
- A writer who sends `new_organizer`/`info_only` inside `program` is still refused with a 400. Only the problem text
  differs ("set by EarnKit's official-page check" instead of "not a program field").

## Schema (additive, idempotent)

`program_writes.found_by_query text`, `program_writes.found_by_source text` (`ADD COLUMN IF NOT EXISTS`), and
`CREATE TABLE IF NOT EXISTS tracked_handles (handle text PRIMARY KEY, profile_domain text NOT NULL, at timestamptz)`.
No foreign keys, no ON DELETE.
