# v3.8 E3: verified columns and the stats ladder

**Approval:** Jenil, "Yes, build v3.8" (Nov 24 2026), logged in earnkitai/earnkit#159. Plan: power-user plan v3.8
BUILD item 3, section 19, decision 15; build plan row E3 and finding 11. Definitions: `docs/stats-definitions.md`.

**What was true before:** `/api/stats` counted every installation in `installs_active_7d`, `finds_7d`, and every
application and win, with no filter for test or owner rows. Nothing recorded a verified sign-in. `identity_proven` on
`owner_people` was true for a linked builder or a legacy X backfill row, so it cannot be "verified".

**Contract**

- Schema (additive, idempotent): `people.verified_by`, `verified_at`, `account_created_at`, `review_mark`; six columns
  appended to `owner_people` after `test_reason` (the tracker reads `SELECT *`; existing columns keep their order).
- `markVerified` (`lib/v6/people.ts`) runs only on a successful GitHub OAuth callback (the /link sign-in and the
  install sign-in, which is still off). It locks the builder row (as `linkPerson` does) and upserts the builder's
  person with `verified_by = 'github'`, `verified_at`, and GitHub's account `created_at` (now read by `exchangeCode`).
  A new person gets its env-list flag by login. No backfill: legacy X rows and builders who signed in before this ship
  are verified at their next sign-in.
- The owner: `OWNER_LOGINS = ['jenil04', 'jenilt']` are always `owner` (source `OWNER_LOGINS`, one of `ENV_SOURCES`,
  so it carries at link like the env lists), whether or not `EARNKIT_OWNER_LOGINS` is set in Railway.
- `deleteBuilder` clears the person's verification with the builder.
- Stats: seven keys appended (`installs_verified`, `people_verified`, `people_verified_active_7d`,
  `people_verified_applied`, `people_verified_won`, `applications_owner`, `won_owner`). Active, finds, application and
  win counts take real owners only; the owner's are `*_owner`. Win dedupe partitions by class as well.

**Trade-offs**

- Making the person at sign-in (not only at link) means a builder's first link moves the installation onto that person
  instead of adopting the installation's person. The old person row is left empty, which `owner_people` already hides
  (no installation, no builder). `people.created_at` of such a person is the sign-in time; `joined_at` still reads
  the first installation.
- "With proof" in the plan's applied and won rungs cannot be checked: no proof is stored until E9. The rungs count
  recorded sends and wins until then, and the definitions note says so.
- Activity is an installation seen this week, not a /me visit, so signing in alone does not make someone active.

**Production effect of applying:** four nullable columns on `people` (no rewrite, no default), and the
`owner_people` view dropped and re-created with six more columns at the end; the `earnkit_ro` grant re-runs. No
existing row changes. `/api/stats` gains seven keys. `installs_active_7d`, `finds_7d` and the application and win
counts drop by the flagged rows' share (live on Nov 24: 3 active, 0 applications, 0 wins). `people_verified` starts
at 0 and grows as people sign in. After deploy, run `people-backfill --reflag` (a dry run first) so the owner's
existing people pick up `OWNER_LOGINS`.
