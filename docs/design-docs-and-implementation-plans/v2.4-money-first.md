# v2.4: Money first, nothing manual

Status: draft for review (2026-10-04). Builds on v2.3 (`main` at d924e4a).

## Goal

A builder installs EarnKit, asks one question, and the first answer shows real money they can win or already qualify for. EarnKit's own campaigns lead the answer. Entering takes one confirmation. Scoring, picking winners and paying them run on their own, at about zero cost. Builders hear about wins, new campaigns and token fees without asking.

## Decisions (from the owner)

- **First message leads with money.** EarnKit campaigns come first, then programs the builder's existing repos qualify for, then the rest. It must be useful on its own and feel like a win.
- **Builder-facing text is short, money first, uses tables, and has no emojis.** Builders only care about the payout.
- **Campaign #1:** $500 of MINI, $100 each to the top 5. It runs 14 days from go-live. The MINI amount is fixed at go-live from the DefiLlama price (≈ 85M MINI each at $0.00000118).
- **Nothing manual.** Scoring, freezing, review and payout are automatic.
- **Payout custody:** a capped hot wallet on Railway holds only this campaign's prize plus gas. A 48h public review window comes before the automatic payout, and the owner can veto with a secret link.
- **Alerts:** through agent check-ins (free). Every reply leads with what changed, and the agent schedules a daily check once.
- **Cost:** no new paid services. The scheduler is a GitHub Actions cron (free tier) calling a secret-protected endpoint once a day.
- **Tokens are not the product.** A token is a default at the submission step only: one row the builder can turn off. It is never sold or announced anywhere else: not in listings, `get_program`, campaign pages or tool descriptions beyond what an agent needs to pass it.
- **Payout wallet:** the owner's existing dedicated hot wallet (already funded with ETH for gas) becomes the campaign payout wallet. The owner tops it up with the MINI prize and sets its key on Railway (`railway variable set CAMPAIGN_PAYOUT_PRIVATE_KEY --stdin`); the key never passes through chat.
- **Fee alerts only above $100**, to keep reads and noise down.

## 1. The first message (`list_programs`)

Order, always:
1. Alerts ("Since you last checked").
2. EarnKit campaigns.
3. Programs the builder's repos already qualify for.
4. Other open programs.
5. Sponsor campaigns (never first).

Example, with the exact shape (markdown table, no emojis):

```
Since you last checked: your token $TIP has $38 in fees to claim (tokens.fun/coin/0x…).

| Win | Prize | Ends | You |
|---|---|---|---|
| EarnKit Campaign #1: Base apps with real users | $100 each to top 5 (in MINI) | Oct 18 | 12 entered, #5 has 14 users |

Your repos already qualify for:

| Program | Prize | Ends | Repo |
|---|---|---|---|
| Base Builder Grant | up to $5,000 | rolling | tipjar |
| Arc Microgrants | 500 USDC | Oct 14 | tipjar |

Want me to build your entry for the $100?
```

**Rules:**
- **Repos without asking.** The agent passes `local_repos` read from local git remotes (the tool text tells it to). A GitHub username is optional, never asked first.
- **Every prize shows a USD value** (MINI converted at the fixed go-live amount). Rows sort by prize per winner within each group.
- **Campaign rows show live numbers:** entries, the score at #5, days left. When the builder has an entry, the "You" column shows "#3, in the top 5" or "#7, 4 users behind #5".
- **Other open programs** go in a single compact table after the matches, capped at 5 rows.
- **One closing offer**, never a menu.
- `show_to_builder` stays "show exactly as written".

## 2. Entering (campaigns), one confirmation

1. **`prepare_submission` returns `show_to_builder`, one short block the builder confirms:**
   ```
   | Entry | Tip Jar for EarnKit Campaign #1 |
   | Prize | $100 in MINI if top 5, paid to 0xAbCd…Ef01 on Oct 20 |
   | Token | $TIP on tokens.fun, you keep 40% of fees (say "no token" to skip) |
   ```
   - The prize line is always first. The token line is always one row. Terms links go in a footnote line under the table.
2. **Proof without the builder's keys.** The agent deploys from its own wallet. Proof is either:
   - (a) the contract was deployed by the payout wallet (as today); or
   - (b) the deployer wallet signs `EarnKit entry: <repo key> <payout wallet>` (EIP-191) and the agent passes `deployer_signature`. EarnKit recovers the address and requires it to equal each contract's deployer, per Blockscout `creator_address_hash`.

   Then `earnkit.txt` holds only `payout_wallet: <wallet>`. The agent writes and pushes it in one commit, along with the token line when a token is wanted.
3. **`record_submission` runs every check and returns all problems at once** (a list), not the first one. Attempts that fail validation don't count toward the 20-a-day limit; only recorded entries do.
4. **The reply** confirms the entry, the current rank, the leaderboard link (`/campaigns/<id>`) and the payout date.

## 3. Campaign #1 runs itself

### Program file

- `status: active`.
- `starts_at` = go-live, `ends_at` = go-live + 14 days.
- **Prize:** USD 500 total, 5 winners, `amount_each` in MINI computed at go-live and written to the file. The rules and summary text are generated from these fields, not hard-coded.
- `max_award_usd: 100`.
- No `token_policy` line: the default applies (a token row at submission, on by default, one word to turn off).

### Scoring (daily cron)

- **Users counted:**
  - senders of successful transactions to an entered contract; plus
  - smart accounts and contracts that call it through internal calls (Blockscout `internal-transactions?filter=to`).

  This counts Base App and relayed users.
- **Excluded:** the entry's payout wallet, its deployer wallets, and the EntryPoint/bundler addresses.
- **History:** an EOA counts if its nonce was at least 3 at the start block. A smart account counts if it had code at the start block.
- **Stored:** the counted wallets per entry (new `entry_wallets` table) and the score time.
- **Reuse:** a wallet shared by several entries still counts for each, but the review shows the overlap.

### Winners and payout

- **One prize per payout wallet and per installation.** The next eligible entry takes the slot.
- **Freeze** at `ends_at`: the final score is computed once, and `score_final` is set.
- **Review window:** the top 5 are published on the campaign page with their evidence for 48h. The owner gets a secret veto link (an `ADMIN_VETO_SECRET` URL) to drop an entry. The next eligible entry moves up.
- **Payout:** after 48h, the cron pays from `CAMPAIGN_PAYOUT_PRIVATE_KEY` (a dedicated wallet on Railway holding only this prize plus gas), in rank order, with ties to the earlier entry.
  - Each payout is idempotent (`prize_tx` written before the next one).
  - It stops if the balance is short, and the page says so.
  - Winners are sanctions-screened at payout.
- **Proof of funds:** the campaign page shows the payout wallet and its live MINI balance.

### Scheduler

- `.github/workflows/earnkit-cron.yml` runs daily at 00:15 UTC (and hourly during the last day and the review window, still within the free tier). It sends a POST to `https://earnkit.com/api/cron` with `CRON_SECRET`.
- The endpoint is idempotent: it scores active campaigns, freezes ended ones, and pays after the review window.
- It also refreshes token fee balances (§4).

## 4. Alerts (agent check-ins)

- **Every tool reply** starts with "Since you last checked:" when there's news for this installation:
  - a new campaign (by `opened_at`, not `created_at`);
  - a rank change into or out of the top 5;
  - a prize paid (amount and transaction link);
  - token fees to claim.
- **Token fees:** read `availableFees(creator_wallet, WETH)` on Clanker's Base FeeLocker `0xf3622742b1e446d92e45e22923ef11c2fcd55d68` for this installation's launched tokens.
  - It's a free RPC read, cached for 6h.
  - It's shown when above $100, with a link to the token's tokens.fun page to claim.
  - It counts only fees already in the locker.
- **Daily check:** the first reply asks the agent once to schedule a daily `list_programs` that messages the builder only when "Since you last checked" is non-empty.
- **Fix:** programs get `opened_at`, set when the status becomes `active`, so going live counts as new.

## 5. Identity

- **One installation per OAuth client.** Re-authorizing the same agent (a new code or token) maps to the same installation. The token encodes the client id, and the installation is keyed by client.
- **Wins and fees also show for any wallet this installation has used**, so a builder who reconnects through a new client and names their wallet sees them.

## 7. Base Builder Codes in the Campaign #1 starter

- **The starter:** EarnKit's Base campaign starter appends an ERC-8021 attribution suffix to every transaction it sends (EOA transactions and smart-wallet user operations, e.g. via a viem `dataSuffix`). The codes are:
  - `earnkit`: EarnKit's own code. The owner registers it once at base.dev. Every campaign app is then attributed to EarnKit on Base's leaderboards and analytics.
  - the builder's own Builder Code, when they have one. It's optional; registering one at base.dev makes their app eligible for Base's own rewards and placement. EarnKit mentions it once, as money ("register a Builder Code to also qualify for Base rewards").
- **Per-project codes aren't possible yet.** Minting codes for builders needs `REGISTER_ROLE` (or a signature from an authorized signer) on Base's registry, which EarnKit doesn't have. If Base grants EarnKit a registrar role, each entry could get its own code automatically.
- **Scoring doesn't depend on the suffix.** It keeps counting real callers of the entered contracts (§3), because:
  - apps not built from the starter must still score;
  - for smart-wallet users the suffix sits inside a bundled transaction to the EntryPoint, so it isn't a cheaper signal.

  The suffix is used as supporting evidence in the review window: the share of a top entry's transactions carrying its codes.

## 8. Safety

- **Hot wallet:** only `CAMPAIGN_PAYOUT_PRIVATE_KEY` goes on Railway. It holds this prize plus gas, and the most it can lose is that.
  - Operator, guardian and deployer keys still never go on Railway.
- **Every payout is bounded.** It must be a winner from the frozen list, `amount_each` comes from the program file, it pays a winner's payout wallet only, it's sanctions-screened, and it's idempotent.
- **Endpoint secrets:** the cron endpoint and the veto link are secret-protected, timing-safe and rate-limited.
