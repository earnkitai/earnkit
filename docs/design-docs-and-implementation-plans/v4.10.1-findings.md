## 1. Circle Developer Grants labelled "Ready"

### How readiness works
- `lib/earnkit/bench-find.ts:1075 readyDrafts(id, key, progs, record, extra)` reads each program row and computes
  `only = builderOnly(row, held)` (line 1088-1089). `only` becomes `ReadyProgram.needs` via
  `needsOfDraft` (line 1099) in `readyCommit` (line 1207).
- `lib/earnkit/ready-copy.ts:79 stateOf(p, hosted)`: `p.needs` null, then `'Ready.'` (or the long-shot line
  `longShotLine(p, 'Ready')`, line 83: "Ready, but Circle looks for apps on Arc, so it's a long shot.").
- `lib/earnkit/conversation.ts:684 builderOnly(p, held)` (the only gate):
  `required.filter((r) => r.from === 'builder' && r.kind !== 'contact' && !held[r.key]?.trim()).filter(mustAsk)`.
- `conversation.ts:658 mustAsk(r)`: `ASK_KINDS` (`['team','traction','demo_video']`, line 652), `type === 'url'`,
  `type === 'choice'`, or the label regex `amount|usd|location|wallet|consent|... code`.

### Root cause
Two filters both let Circle through:
1. **`from` gate:** all four Circle fields in `programs/circle-developer-grants.json` say `"from": "project"`
   (business/solution, integrations/how_it_works, roadmap/milestones, milestones/milestones). `builderOnly` only
   looks at `from === 'builder'`, so `only = []`, `needs = null`, and the line says "Ready".
2. **`mustAsk` kinds:** even with `from: 'builder'`, `mustAsk` would not fire. `milestones` and `how_it_works` are
   not in `ASK_KINDS`, and the type is `text`. So `builderOnly` would still return nothing.

The rules in the codebase disagree. `lib/earnkit/coach.ts:313 askableKeys` (the prepare coach) asks a field when
`r.from === 'builder' || !AGENT_DRAFTS.includes(kindOf(r))`, with
`AGENT_DRAFTS = ['name','one_liner','solution','how_it_works','links','demo_video','other']` (coach.ts:125). By that rule
Circle's `roadmap` and `milestones` (kind `milestones`) ARE asked, but the ready set uses `builderOnly` and never asks.
`agent_completable` (`program-file.ts:800 deriveAgentCompletable`, `UNCOMPLETABLE_KINDS = []`) works per program, not
per field, and is only a discovery filter (bench-find.ts:3213). It does not help here.

### What should count as builder-only (proposal)
A required, unheld field is a builder need when ANY of these holds:
- `from === 'builder'` and `mustAsk` (today's rule), or
- its kind is a **plan or claim the record can't show**: `milestones` (roadmap, grant milestones, GTM plan),
  `use_of_funds`, `team`, `traction`, `raised`, `demo_video`, whatever `from` says. This is coach.ts's
  "not in AGENT_DRAFTS" idea, minus `problem`/`why_you`, which the agent can draft honestly from the repo, or
- `type === 'multi_choice'` (today only `'choice'` matches; Base's `primary_challenge` is multi_choice and slips through), or
- the label names revenue or how it makes money (`/revenue|make money|monetiz/i`) and the record has no verified
  revenue line (see item 2).

`how_it_works` from the project (Circle `integrations`, "Your Circle and Arc integrations") is the hard case. The repo
can show it only if the project really uses Circle or Arc. Circle is in the set as a long shot *because* the project
isn't on Arc, so any answer the agent writes is invented. Minimal: fix the data and set `integrations` to
`"from": "builder"`, plus a new `kind`-independent rule: **a `from: 'builder'` field is a need unless its kind is in a
small agent-draftable allowlist** (`one_liner`, `solution`, `problem`, `how_it_works`, `links`, `name`, `why_you`).
For Circle, give `integrations` kind `other` (or add an `ask: true` field to `SubmissionRequirement` in
`program-file.ts:~100`, not API-writable at first). Reuse `MAX_BLANKS` and `READY_NEED_MAX` as they are.

## 4. Score 69 / 6 weeks in find, then 83 / 7 weeks in score, seconds apart

### Where each is computed (the same code path)
- find: `tools.ts:872` `refresh.started = startRefresh(...)`, then `tools.ts:1118 await refresh.started?.within(REPLY_WAIT_MS)`,

- score: `tools.ts:2969` -> `score-tool.ts:29 scoreReply` -> `bench-find.ts:3143 benchScore`: its own
  `startRefresh(...).within(REPLY_WAIT_MS)` (line 3150-3151), then the same `benchRead` and `benchView` (with
  `alwaysStanding: true`, so `standingLed` puts the paragraph first).
- Score: `standing.ts:27 pageScore(lines, {parts})` = `storedShipping(builder_live.parts).points` while listed.
- Weeks: `benchRead` line ~408 `streaksFor([id], now)` (streak.ts:19) -> `site-streak.ts:23 streakWeeks`
  (adds the **current ISO week** when `thisWeekCommits > 0`, read from the repo source's stored
  `signals.commit_counts[<this week>]`) -> `weeks.ts:49 streakOf` (counts back from this week if lit, else from last week).

Same project (`builder_profiles.main_project_key` in both), same functions, same week boundary (ISO week, UTC Monday).

### Root cause: the stored numbers changed between the two calls (a refresh that finished late)
- `REPLY_WAIT_MS = 1_500` (reply-wait.ts:8). The refresh runs up to `REFRESH_BUDGET_MS = 8_000`
  (person-score.ts:36) and goes on in the background (stand-view.ts:34 comment: "this reply uses the last stored numbers").
- find's refresh claimed `builder_live.read_at` (person-score.ts:573-578) but did not finish in 1.5 s. find
  then read the **old** `builder_live.parts` (69) and the old source reading, which had no commits for this week.
- 2026-11-02 is a **Monday**: a new ISO week (2026-W45) had just started. Before the refresh, `thisWeekCommits = 0`,
  so `streakOf` counted from last week: 6. The refresh read today's commits, wrote `commit_counts['2026-W45']`
  and rescored `builder_live.parts`.
- Seconds later, score's own `refreshPerson` was a no-op: the `read_at` claim needs `read_at <= now - REFRESH_MS`
  (10 min, person-score.ts:31), and find had just set it. score read what find's background refresh wrote: 83 and 7
  (this week lit). So there is no different rule or cache key. Same reads, before and after the refresh landed.

### Minimal fix (pick one; A is the smallest)
- **A. Don't state numbers that are being updated.** `stand-view.ts:34 startRefresh(...).within` returns
  `Promise<boolean>` (true = settled). In `tools.ts:1118` (find) and `bench-find.ts:3151` (score), pass
  `fresh: boolean` into `benchView` via `ViewIn`. When `!fresh`, `readStanding` (standing.ts:139) returns
  `score: null`, and `standingFields` leaves out the weeks part (or adds `standing_note: 'updating'`); `readyRecord`
  also leaves out the score and streak lines. The next reply has the new numbers, and the builder never sees two.
- **B. Wait longer on the first find of a new week.** If `builder_live.computed_at < this Monday 00:00 UTC`, wait
  `within(REFRESH_BUDGET_MS)` instead of `REPLY_WAIT_MS`. This costs up to 8 s of latency once a week.
- Also worth doing: in the score reply, if `standing_seen.said` has this session's earlier standing, say the change
  ("Score 83, up from 69 this morning"). That is copy work, so optional.

### What a write carries
Only `API_FIELDS` (api-program-text.ts:20): `source_url`, `submission_url`, `pool_source_url` are the only URLs.
There is **no official-site field**. **`x_handles` and `proof_hosts` are not API-writable** (owner file only). So
today the only notion of "official" is `source_url`'s registrable domain, and the bot picks that freely. A
lookalike domain with source and submission on the same domain passes every check.

### Where hidden or stale filtering happens (a pending state can reuse it)
- `lib/earnkit/api-stale.ts`: `apiStale(p, now)` (pure), `freshSql(db, alias, now)` (the SQL predicate
  `NOT (source='api' AND (verified_at IS NULL OR verified_at < today - 14))`), `connectedSql` (builders who
  entered, applied to or drafted it keep it), `hiddenFor(p, installationId)` (unlisted, or stale and not connected).
- `freshSql` call sites (discovery): `programs.ts:286, 479, 523`, `bench-find.ts:2648`, `alerts.ts:686`,
  `digest.ts:524`, `stats.ts:243, 248`, `site-data.ts:533`, `app/sitemap.ts:22`.
- `hiddenFor` call sites (read by id): `tools.ts:1219, 1248` (get_program and prepare), `draft-application.ts:98`.
- `programs.ts:579`: `status === 'unlisted'` throws NotFound (getProgram).

### Proposed design (minimal)
- **Check:** new pure `linkChecksOut(p, officialSite, known)` in submit-hosts.ts. True when
  `registrableDomain(host(submission_url))` equals `registrableDomain(host(official_site))`, or is in
  `KNOWN_ECOSYSTEM_DOMAINS[chain]` for one of `p.chains` (new map, e.g. `base: ['base.org','coinbase.com','base.dev']`,
  `arc: ['arc.network','circle.com']`; owner-curated in code), AND `source_url`'s registrable domain also matches.
  A submit-platform link (forms.gle, questbook, dorahacks) can't match a domain, so it checks out only when
  `source_url` is on the official or known domain AND the program is not new. For a create, it lands pending (owner
  ruling needed; Base's own form is forms.gle).
- **New writable field:** `official_site` (https URL) in `API_FIELDS` and in `ProgramFile` (optional), stored in
  a new `programs.official_site text` column (or only in the `program_writes` body). Same `apiUrlProblem` hygiene.
- **When it applies:** in `upsertAction`, after group 6 and before the transaction: `isCreate = !existing`,
  `linkChanged = existing && (existing.submission_url !== p.submission_url || existing.source_url !== p.source_url)`.
  If `(isCreate || linkChanged) && !linkChecksOut(...)`, then pending.
- **Pending storage (recommended: no programs row):** insert `program_writes (program_id, action:'upsert',
  result:'pending', reason:'link not on <domain>', body: clean)` and return
  `202 {ok:true, id, result:'pending', live:false}`. For a create nothing reaches `programs`, so no discovery filter
  changes. For a link change the old row stays live with its old link, which is the safe default. Approval runs
  the same transaction with `body`. This avoids touching `freshSql` and `hiddenFor` at all.
  - Alternative (if a pending row must exist): add `programs.pending_at timestamptz`, extend `freshSql` with
    `AND NOT (source='api' AND pending_at IS NOT NULL)`, `apiStale` with `|| p.pending_at != null`, and
    `hiddenFor` the same without the `connectedSql` exemption. The call sites are listed above.
- **Owner email:** `lib/earnkit/owner-mail.ts:17 ownerMail(subject, text, key, mailer?)` sends to
  `CONTACT_EMAIL` (`policy.ts:25`, the owner address only) from `DIGEST_FROM_DEFAULT` through
  `digest.ts resendMailer`. It needs only `RESEND_API_KEY` (`ownerMailEnabled`). Use
  `idempotencyKey = program-pending:<write id>`. Note: `alert-mail.ts` mails **builders** (opted-in
  `digest_subscriptions.email`), not the owner, so don't use it for this.
- **Approve link (HMAC):** follow `digest.ts:215-242 unsubToken/unsubTarget` (HMAC-SHA256 under
  `EARNKIT_AUTH_SECRET`, domain-separated prefix, base64url, `timingSafeEqual`), or `veto.ts:18 vetoKey` (under
  `ADMIN_VETO_SECRET`, 32+ characters, the owner's admin links). Token = `HMAC(EARNKIT_AUTH_SECRET or ADMIN_VETO_SECRET,
  "program-approve:v1:<write id>:<sha256(body json)>:<expires>")`. Link =
  `${siteUrl()}/api/programs/approve?w=<id>&e=<expires>&t=<mac>`. Use a **GET that shows a confirm page with a
  POST button**: email scanners prefetch GET links, so a bare GET would self-approve. The POST re-verifies the token,
  then `UPDATE program_writes SET result='approved' WHERE id=$1 AND result='pending' RETURNING body`
  (single use), then runs the upsert transaction (`upsertProgram(body,'api',tx)`, audit `approved`), then
  `programsChanged(id)`. Re-run `apiRuleProblems` and `checkLink` before applying, since `verified_at` may now be
  older than 7 days. Never print the secret values.
- **Docs:** `docs/programs-api.md` line 3 ("A write that passes every check is live at once") and line 52 (the
  success shape) need the pending result. Line 120 (URL rules) needs `official_site`.
