## 1. The no-repo lead

**What changes.** `find`'s short first reply (v2.10 item 2) gets a third kind of lead. Today a
builder with no fitting row sees "No repo fits yet. $1.1M+ is open; want the 3 easiest?". In v2.11,
when no row leads, nothing waits on submission, and no users question applies, the reply is one
context line plus one lead line ending in a question.

**When it shows.** All of these must hold:
- There are no repos, or no good-odds row (`leadRow` is undefined).
- There is no `submitStep` and no `usersAsk`.
- `freshPick` returns a program.

**`freshPick(cards, now, hidden)`** (new, pure, `fresh-build.ts`). A program qualifies only when
all of these hold:
- It is open and curated: not sponsored, not an EarnKit campaign, not an investment, not tagged
  `long shot` or `needs a live product`, and not hidden or already entered.
- It has a `fresh_build` starter (section 2) whose chain EarnKit can deploy to (Arc or Base).
- It is Easy or Medium.
- `max_award_usd` is $5,000 or less.
- It has an end date at least 24 hours and at most 14 days away. A rolling program qualifies too,
  but only when no dated program does.

Qualifying programs rank:
1. Easy before Medium.
2. More `winners_per_round` (unknown counts as 1).
3. The sooner close.
4. The higher prize.

Never a long shot, so never the $840K hackathon or a16z.

| Line | Text |
|---|---|
| Context (always first) | `$1.1M+ in prizes is open right now across 7 programs.` (`moneyText(openMoneyUsd)`, the count of open curated programs) |
| Lead, dated program | `Arc Microgrants pays 500 USDC and closes in 4 days. A USDC tip page on Arc takes about an hour. Want me to build it?` |

## 3. The personal twist

**What changes.** A yes to the lead reaches `prepare` with `build: { start: true }`. The reply asks
one question before any work starts:

| Case | `show_to_builder` |
|---|---|
| Wallet known (non-shared client, remembered) | `What should it do for you or your users? One line is enough, like "tips for my podcast listeners".` |
| No wallet known | `What should it do for you or your users? One line is enough, like "tips for my podcast listeners". Add the wallet that should own it.` |

- The wallet sentence is declarative, so the reply keeps one question (the v2.10 M5 pattern).
- The agent sends `build: { twist, name, description, feature, wallet? }`. The agent writes the
  name, description and feature from the twist, because EarnKit runs no LLM.
- The server checks every field:
  - `plainProblem` (no addresses or stat dumps);
  - the name is 3 to 40 characters and isn't a starter name (`EARNKIT_STARTER_NAMES`);
  - the feature is one sentence;
  - the wallet is a checksummed address the builder gave, never a remembered one on a shared
    client.
- Each refusal is an `agent_note` only.
- On a pass, the builder sees: `Building PodTips: a USDC tip page on Arc for your podcast listeners. I'll be back with the live link.`
- The agent gets the build kit:
  - the starter's degit command and its twist slots;
  - the `earnkit.txt` proof line;
  - the artifact shape `prepare.deploy` takes;
  - the rule that the repo is public, under the builder's own account, with no secrets and no
    fork link.
- The twist (at most 200 characters, plain text) is stored on the `built` event. The name,
  description and feature go to the draft entry.

## 4. Deploy and host by default

**What changes.** On the build path, the agent's next `prepare` call carries `deploy` and
`host: true` together (`build: { program_id }` marks the call). The server then does three things
with no extra yes:
- It runs the capped v2.10 deploy. The owner is the build wallet. For `arc-tipjar` the owner is a
  constructor argument, so `owner()` reads the builder at once and no transfer is needed.
- It returns the one-use upload URL. The agent bakes the contract address into the site, zips it
  and uploads it.
- It records the events (section 6).

**What the builder sees.** Only the outcome lines that exist today, joined in one reply with the
next step:

```
PodTips is live: podtips-jenil04.earnkit.com
PodTips is deployed on Arc: 0x12ab…9f3e. You're the owner.
```

**Hosting without a click (needs open decision 2).** On a non-shared client, the v2.9 host
sign-in is replaced by the deploy's ownership proof: the `earnkit.txt` proof line in the public
repo (`repoOwnershipPasses`), plus a public `GET /users/<owner>` read for the v2.9 gate (account 30
days or older, at least 1 public repo). Shared clients keep the sign-in. All the upload limits stay.

**When a piece is off or refused.** The reply says it once, in v2.10's words, and the flow
continues where it can:
- **Deploys off:** "Deploys are off right now." The build path is never offered while deploys are
  off: `freshPick` needs `deployEnabled()` for starters with a contract.
- **Hosting off or gate refused:** the agent hosts on GitHub Pages from the builder's public repo
  (agent note, free). The `hosted` event records the github.io URL with `host: 'github_pages'`.

## 6. The builder event log

**What changes.** A new append-only table, plus one writer, `events.ts recordEvent`. Every existing
step that ships something writes one row. Nothing reads it for scoring or leaderboards yet.

```sql
CREATE TABLE IF NOT EXISTS builder_events (
  id              bigserial PRIMARY KEY,
  at              timestamptz NOT NULL DEFAULT now(),
  type            text NOT NULL CHECK (type IN ('built','deployed','hosted','entered','submitted','won','lost','usage_check')),
  github_login    text,                 -- lowercased
  login_basis     text CHECK (login_basis IN ('signin','app','proof_line','repo_owner')),
  installation_id integer,              -- no FK: an installation delete never removes history
  wallet          text,                 -- lowercased 0x address the builder gave
  repo_key        text,                 -- owner/repo, lowercased
  program_id      text,                 -- no FK, same reason
  project_id      integer,
  chain           text,
  proof_tx        text,                 -- tx hash
  proof_url       text,                 -- live link, repo, submission or results URL
  detail          jsonb NOT NULL DEFAULT '{}'::jsonb,  -- small: twist, address, counts, host kind, basis
  dedupe_key      text NOT NULL UNIQUE  -- idempotent writes: retries never double-count
);
CREATE INDEX IF NOT EXISTS builder_events_login ON builder_events (github_login, at);
CREATE INDEX IF NOT EXISTS builder_events_due ON builder_events (type, at) WHERE type = 'deployed';
-- Append-only: a trigger raises on UPDATE and DELETE (and TRUNCATE).
```

| Type | Written by | Proof | dedupe_key |
|---|---|---|---|
| built | `prepare` on the build path, when the repo first passes the proof line | repo URL (+ commit sha if sent) | `built:<repo_key>:<program_id>` |
| deployed | `deploy.ts` on status `deployed` | tx hash, address in `detail` | `deployed:<contract_deploys.id>` |
| hosted | `hosting.ts` when a site goes `live`; the GitHub Pages fallback when its probe passes | live URL | `hosted:<host_deploys.id>` or `hosted:gh:<url>` |
| entered | the entry write at confirm (`recordSubmission`) | entry page `/p/<id>` | `entered:<project_id>` |
| submitted | tell `submitted` (`markSubmitted`) | the external submission URL | `submitted:<project_id>` |
| won, lost | `syncOutcomeFile` (announcement basis); self-reports are written with `detail.basis = 'self_reported'` and never count | results URL | `outcome:<project_id>:<round>:<basis>` |
| usage_check | the cron (below) | explorer or RPC source in `detail` | `usage:<deployed event id>:<30 or 90>` |

- **Identity.** `github_login` is filled only from a verified source, and `login_basis` names
  which: sign-in, the App, the `earnkit.txt` proof line (push access), or the plain repo owner (the
  weakest basis). It is never guessed. The wallet is only one the builder gave.
- **Backfill.** A one-off local script (`scripts/events-backfill.mts`) writes rows from
  `contract_deploys`, `host_deploys`, `projects`, `submissions` and `entry_outcomes`. Its
  `dedupe_key`s are the same, so it is safe to rerun.
- **Privacy:** see section 9.

## 7. Cron usage checks (30 and 90 days)

**What changes.** A step inside today's cron run adds no new schedule:
`usageChecks(now, { limit: 20 })`.

**What it selects.** `deployed` events whose age has passed 30 (or 90) days and that have no
`usage_check` with that window yet, oldest first, at most 20 a run. Because a due check is written
once, each runs once.

**How it reads use** (all free; facts to confirm in plan Task 0):
- **Base:** Blockscout's `GET /api/v2/addresses/<a>/counters` (`transactions_count`), as v2.10
  does.
- **Arc:** explorer.arc.io's API sits behind a Cloudflare challenge (checked 2026-10-10: 403), so
  the check counts the starter's `usage_event` logs over `eth_getLogs` from the public RPC, in
  block chunks from the deploy block. It records the count and the unique senders. A contract
  with no known event gets `eth_getCode` only.
- **Every chain:** `eth_getCode` (is the contract still there).

**What it writes.** A `usage_check` row with
`detail: { window: 30 | 90, tx_count?, events?, senders?, code: boolean, source }`. A failed read
writes nothing and is retried on the next run. The step is off while no `deployed` event is due,
and costs only RPC and Blockscout reads.

## 8. Fixes from live testing

**8a. tokens.fun is still scored low after v2.10.1 (verified in code).**

The owner's case is a private org repo, a live site, no contract of its own, and an agent that
doesn't send the optional `my_commits_90d`. Here is what happens:
1. In `match-projects.ts` (around line 1292), `contributionRead` gets a 404, so `owned` is false
   and `ownerUnknown` is true. Without `my_commits_90d`, the v2.10.1 stand-in never runs.
2. In `checkLocal`, `productScore` counts active, young, original and deployed: score 4, with
   `owned` and `readme` unchecked. The product tier needs `owned`, so the tier is `project`.
3. `productOdds` returns low odds with `NOT_REAL_YET` ("not enough signs of a real product yet").
4. Traction is 0 (no transactions) + 2 (live) + 1 (last-commit band) = 3, the tipjar's 3.
5. `usersAsk` needs product tier with good odds, so it never asks.

Fix (the agent sends nothing optional):
- **Unknown is not low.** A repo whose only blockers are unchecked signals (`owned` or `readme`
  unchecked, live link passed, active) gets `odds: 'unknown'` and is asked, never labelled low.
  `usersAsk` takes product-tier good-odds repos (as today) and these `unknown` repos. The copy is
  unchanged: `tokens.fun could win up to $5,000 on Base with real users. Does it have real users or revenue? (yes/no)`.
  A yes is the v2.10.1 users claim. `withRealUse` already promotes a repo whose `owned` is
  unchecked, not missing, so it becomes a product with good odds. A no keeps the reason
  "no users yet".
- **Use outranks polish.** The rank becomes odds, then real use (measured or claimed), then
  traction, then difficulty and prize (`present.ts layout`, `match-projects.ts` fits sort,
  `tools.ts matchRows`). A product with users always ranks above a starter, at any traction tie.

**8b. World's Fair gives a starter good odds while it is missing `new_work` (verified in code).**
`rowOdds` (`match.ts:440`) checks the tier, a chain that is only mentioned, and `real_users`, then
returns the repo's own odds. It never looks at `new_work` or `live_url`. `matchRepo` makes every
`new_work_only` program `after_step` with `missing: ['new_work']`, so a repo with good odds
(the tipjar: product tier, Arc transactions unknown, live, active, so good) shows that odds on the
World's Fair row. `qualifies` drops it from "$X", but `matches` and the "show more" heading still
call it good.

Fix: `rowOdds` returns low whenever `v.missing` is non-empty, with the reason of the first missing
item:
- `new_work`: "only new work counts";
- `live_url`: "no live link yet";
- `mainnet_deploy`: "not deployed yet";
- `real_users`: "no users yet".

A row with a missing requirement is never good odds.

## Open decisions for the owner

1. **Turn on the deployer and hosting in production, or the build path can't run.** As of
   2026-10-10, Railway production has none of the variables either feature needs: no
   `DEPLOYER_PRIVATE_KEY`; no `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` or
   `R2_BUCKET`; no `GITHUB_OAUTH_CLIENT_ID` or `GITHUB_OAUTH_CLIENT_SECRET`. The variables that are
   set are `ADMIN_VETO_SECRET`, `BONUS_INDEX_START_BLOCK`, `CAMPAIGN_PAYOUT_PRIVATE_KEY`,
   `CRON_SECRET`, `DATABASE_URL`, `EARNKIT_AUTH_SECRET`, `EARNKIT_URL`, `GAS_WALLET_MIN_WEI`,
   `GITHUB_TOKEN`, `TOKENSFUN_DEPLOY_API_KEY` and Railway's own. `*.earnkit.com` doesn't resolve,
   so the Worker isn't deployed. The owner must:
   - make a new deployer wallet;
   - send it about $5 of USDC on Arc (Base ETH is optional, since no Base program is pickable);
   - set `DEPLOYER_PRIVATE_KEY`;
   - create the R2 bucket `earnkit-sites` (R2 needs a card on file; usage stays inside the free
     tier);
   - deploy `infra/host-worker` on Workers Free with a `*.earnkit.com` route and a proxied wildcard
     DNS record;
   - set the four R2 variables and `EARNKIT_RESERVED_SUBDOMAINS`.

   Cost: $5 to $10 of gas float, at most $10 a month by code cap, $0 hosting.
   **Default: do it before v2.11 ships. Until then, `freshPick` offers nothing (fail closed) and the
   v2.10 line stays.**
2. **Hosting needs a GitHub sign-in click today.** That's an extra step, and it also needs the
   GitHub OAuth app. **Default: on non-shared clients, accept the `earnkit.txt` proof line plus a
   public account-age read instead, and keep sign-in for shared clients. If EarnKit hosting is off
   or refused, the agent falls back to GitHub Pages.** Then the OAuth app isn't needed for the
   build path.
3. **There's almost nothing to pick.** Arc Microgrants is the only pickable program, and it closes
   Oct 14, likely before v2.11 ships. Base Builder Grants wants used products, and everything else
   is a long shot or Hard. **Default: before launch, the owner adds 3 to 5 small, dated programs
   on Base or Arc (bounties, microgrants) through `programs/README.md`. Until one exists, the
   no-repo reply falls back to the v2.10 line.**
4. **"Base -> x402 service" doesn't fit this brief.** The x402 starter is a Next.js server. EarnKit
   hosts static files only, and the service has no contract to deploy. **Default: no x402 build
   path in v2.11. The Base starter is `base-checkin` (contract plus static page), used only when a
   Base program qualifies.**
5. **The wallet for the one yes.** Deploys need the builder's wallet as owner, and EarnKit never
   invents one. **Default:** use a remembered wallet when the client isn't shared. Otherwise add
   the declarative "Add the wallet that should own it." to the twist question, so the reply keeps
   one question. That wallet is also the confirm line's fee wallet, so it is never asked twice. A
   builder with no wallet gets an agent note: the agent may help them create one on their own
   machine, and EarnKit never sees the key.
6. **The event log and deletion.** **Default:** append-only for the app. The owner can redact one
   builder's login and wallet on email request with the script. Disclose this in `/terms` before
   the first row is written.
7. **The sandboxed host CSP may break wallet connect.** Hosted sites get an opaque origin (`sandbox`
   without `allow-same-origin`). Injected wallets and WalletConnect may refuse an opaque origin or

8. **Ship timing.** v2.10 took about 2 days. **Default: ship T1 (the two odds fixes) on its own
