# v4.5 Verified traction: usage and revenue from builders' own contracts: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** EarnKit knows, without asking, how many real people used a builder's own contracts and how much money those contracts took in from them in the last 30 days. Grant drafts carry those numbers as verified facts. Revenue stays private: never on the page, builder.json or any public endpoint.

**Architecture:** Ownership and usage already exist. `sources.ts contractOwnership` counts only contracts EarnKit deployed, contracts a signature-proven wallet created, or contracts named in an App-proven repo's deploy file whose onchain deployer matches (`repo_link`). `used-by.ts contractsUsage` counts distinct outside senders per day into `app_usage`. v4.5 adds three things on top of that:
- Hardhat Ignition deploy files (`ignition/deployments/*/deployed_addresses.json`, the current Hardhat default) as contract clues.
- A daily revenue read, `app_revenue`: ETH and USDC paid into counted Base contracts by outside wallets, with pass-through contracts excluded.
- Both numbers go into `shipLogFacts` / `shipLogBlock`, so every draft gets them. Both also go into the builder's own reply facts.

No new question. Detection and ownership are automatic, as today's contracts already are.

**Tech Stack:** Next.js 16, TypeScript, Postgres, node:test via tsx; Alchemy free tier (`alchemy.ts`), no new paid service, at most one read per builder per UTC day.

**Spec:** the owner-approved answer (2026-10-29), the contract-address idea inspired by trustmrr.com:
- Don't add a setup question; detect contracts and ask only when it wins money.
- Count a contract only with ownership proof.
- Measure unique users, transactions and fees that reach addresses the builder controls; never volume or TVL. Buybacks are never revenue.
- Use the numbers in applications.
- Crypto first, private by default, non-crypto (read-only Stripe keys) later.

## Exact copy

The ship-log block (`shipLogBlock`) gains these lines, after "N weeks in a row" and before "Live:":
- `Used by {N} people in the last 30 days, verified onchain` (`{N}+` when capped), only when users ≥ `USED_MIN`, and only when the newest `app_usage` read is no older than `USED_STALE_DAYS`. It is the larger of the contracts and builder_code sources, as `usedByOf`.
- `{M} came back in a second week`, only when returning ≥ 2 and the usage line shows.
- `${usd} paid into its contracts by outside wallets in the last 30 days, verified onchain`, only when the revenue read is fresh (≤ `USED_STALE_DAYS`), not pass-through, and ≥ $100. Format `usd` as `$1,240` (whole dollars, en-US grouping), with `+` when capped.

Reply facts (`reply-facts.ts replyFacts`): `used_by_30d: number` and `revenue_30d_usd: number` with the same freshness and thresholds, absent otherwise.

## Review Focus

1. A famous contract (e.g. the Uniswap router) named in a builder's repo constants or README is never counted: only deploy files with a matching deployer, a proven wallet's creations or EarnKit deploys count (today's `contractOwnership`, unchanged).
2. A router-style contract that forwards what it receives (outbound to outside addresses ≥ 50% of inbound in the window) shows no revenue line at all.
3. A builder's own wallets, the deployer, and wallets their proven wallets funded never count as paying wallets (same exclusions as `contractsUsage`).
4. A failed or partial read stores nothing (no zero row), so the draft says nothing that day.
5. A hidden page (`builder_profiles.hidden`) still gets the lines in its own drafts and replies (they're private documents), and never anywhere public.

### Task 2: The daily revenue read

**Files:**
- Modify: `apps/frontend/db/schema.sql` (`app_revenue (builder_id integer, day date, usd numeric NOT NULL, inbound_usd numeric NOT NULL, outbound_usd numeric NOT NULL, capped boolean NOT NULL, contracts integer NOT NULL, read_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (builder_id, day))`)
- Create: `apps/frontend/lib/earnkit/revenue.ts`:
  - `contractsRevenue(builderId, now, call): Promise<Revenue | null>`: Base only. Over `contractsOf(builderId)`'s counted contracts, last `USED_DAYS` days. Read inbound ETH (`external` and `internal` categories) and Base USDC (`0x833589fcd6edb6e08f4c7c32d4f71b54bda02913`, 6 decimals) transfers to each contract, and outbound from it, via `alchemy_getAssetTransfers` (add a helper in `alchemy.ts` if none fits, `USED_PAGES` pages each).
  - Inbound counts only from outside wallets (exclusions as `contractsUsage`: proven wallets, each deployer, `fundedBy`). Outbound counts only to addresses that are none of those.
  - ETH is priced with `fees.ts cachedWethUsd`; an unknown price stores nothing.
  - `usd = inbound_usd`, except `passThrough` (`outbound_usd >= 0.5 * inbound_usd`), which stores `usd = 0` with the row, so drafts skip it.
  - `capped` when a page limit was hit. Null on any failure.
  - `runRevenue(now, deps)`: `USED_PER_RUN` builders a run, each at most once a UTC day, those with a counted Base contract first. Upsert `app_revenue`.
- Modify: `apps/frontend/lib/earnkit/cron.ts` (wire `runRevenue` beside `runUsedBy`, same daily gate)
- Test: `apps/frontend/lib/earnkit/v45-traction.test.ts`

**Interfaces:**
- Produces: `type Revenue = { usd: number; inbound_usd: number; outbound_usd: number; capped: boolean; contracts: number }`; `latestRevenue(builderId, now): Promise<{ usd: number; capped: boolean } | null>` (fresh rows only, ≤ `USED_STALE_DAYS`, and `usd` > 0).
