# v3.8 E4: install consent page, GitHub sign-in on the install path

Plan item 2 (L3), PR table row E4 in the build plan. Stacked on E3 (it writes E3's `verified_by`/`verified_at`).

## Why the switch was off

v6.1.21 shipped the install sign-in behind `INSTALL_SIGNIN_ENABLED = false` (C1 of the PR #153 review). Authorize went
to GitHub and the callback issued a code straight to the client. GitHub re-approves a returning user silently, and the
nonce cookie is set by the same browser that follows the link, so it proves nothing: anyone could register a client,
send a victim the authorize URL, and get a code naming the victim's builder. That is account-linking CSRF. The cause
is that no step needed the person to say yes on an EarnKit page.

## Fix

- The callback no longer issues a code. It reads the GitHub user and 303s to `GET /install/consent?s=<state>`. The
  state (HMAC, label `install-consent-state`, 15 minutes) carries the checked authorize request, the GitHub profile
  fields, the nonce and the callback time. Nothing is written.
- The page names the agent (registered or document name), its redirect host and `@login`, with Connect and Not now.
  It is a POST form with `csrf = HMAC(secret, 'install-consent-csrf:' + nonce)`.
- `POST /install/consent` needs our Origin, the nonce cookie equal to the state's nonce, and the CSRF value. Another
  site cannot read the cookie (HttpOnly, SameSite=Lax) or compute the value, and every page is `frame-ancestors 'none'`.
- Connect: `upsertBuilder`, `markVerified({ by: 'github', at: callback time })`, `issueCode(req, { builderId })`.
  One GitHub id is one builder, and the person is keyed by builder, so two installs are one person.
- `INSTALL_SIGNIN_ENABLED` is removed. The `install_signin` flag (`EARNKIT_FLAGS=install_signin`, plus the OAuth app)
  turns it on, so `EARNKIT_FLAGS` is the only switch for the v3.8 ship. The pre-E4 `EARNKIT_INSTALL_SIGNIN` variable is
  no longer read and is gone from the env allowlist. Turning the flag off is the rollback: callback and consent then
  answer the failed page.

## Scope and data

GitHub scope stays `read:user` (no repo scope, no write scope). The token is used for one `GET /user` and dropped.
There is no schema change.

## Pages (plan 23.3)

Plain text, one next step, the cookie cleared: failed (unchanged `INSTALL_FAILED`), denied (GitHub's Cancel,
`error=access_denied`), cancelled (Not now), expired (install state or consent past its time).
