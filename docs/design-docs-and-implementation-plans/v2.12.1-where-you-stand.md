# v2.12.1: Where you stand, from the first message

Status: spec for owner review (2026-10-13, after the owner's consistency review). Replaces v2.12's
onboarding, replies, scoring, profile, card and leaderboard. v2.12's storage, readers, anti-farming,
archives and terms stay unless this file changes them. `EARNKIT_BUILDER_SCORE` stays off in production
until the owner's own install passes the acceptance test.

## Why this exists

The owner tested v2.12 on production on 2026-10-13: "This is the worst update thus far both in terms of
functionality and usage." It started empty, asked for proofs, used random slugs, and showed a
leaderboard of "Builder 0" rows. This update follows the owner's flow step by step.

**The rule:** the first message gives the builder their rank and their work; one tap with X makes it a
public page. Nothing waits on the builder doing work first.

**Honesty rule (owner's guide):** only verified data moves the score and the leaderboard. Anything the
agent reported but EarnKit could not prove is still shown, marked as an estimate, and adds nothing.

**Copy rule:** plain sentences a person understands on first read. Sentence case. No all-caps labels,
no eyebrow labels, no jargon ("outcome", "verified source", "percentile" never appear in builder or
public text). No emojis, no em dashes.

## The flow (owner's, binding)

### 1. Connect
The builder adds EarnKit to their agent. Nothing is asked. In the first `find`, the agent passes what it
can already see, in a new optional `identity` input: GitHub login (git config, `gh auth status`), local
projects (existing `local_repos`), wallets, the contracts those wallets deployed, live sites, packages.
The tool description tells the agent to fill it and never to ask the builder.

### 2. The first reply to "What can I earn?"
Inside that call (10-second budget) EarnKit reads the person's public data and scores it. Anything
slower finishes on the next reply or page view. The answer has three short parts and ends in one yes:

```
Where you stand
You're #4 of 12 builders on EarnKit. You've shipped 6 projects, and 2 of them have real people using
them.
Claim your page with X: earnkit.com/claim/<code>

Ways to earn right now
Your tip jar qualifies for Arc Microgrants. It pays 500 USDC and closes in 3 days.
Avalanche Team1 gives up to $10K to apps on Avalanche, and it's open all year.

How to move up
tokens.fun's contract isn't counted yet. If I add it, everyone who has used it counts toward your rank
today. Want me to add it?
```

If nothing is found:
```
Where you stand
I couldn't find anything you've shipped yet, so you're not ranked.

Ways to earn right now
Arc Microgrants pays 500 USDC for a small app, and I can build one with you in about an hour.

How to move up
Tell me your GitHub or wallet and I'll rank you right now.
```

Rules:
- **Rank wording.** While fewer than 50 builders are ranked: "#N of M builders on EarnKit". From 50 on:
  "top N% of people building with AI" (shown only when N is 50 or less, otherwise "#N of M").
- At most 3 programs, each with the reason it fits. Programs the person already entered, closed
  programs, and programs an agent can't complete are never shown.
- "How to move up" is the single step that moves the rank the most, and it only promises what EarnKit
  can deliver at once (see step 3). It ends the reply with one yes.
- **The page link is the X sign-in (owner ruling).** "Claim your page with X" opens Sign in with X
  (OAuth 2.0 with PKCE, `GET /2/users/me`, about $0.01 a confirmation on X's pay-per-use API). One tap
  confirms the handle and lands them on `earnkit.com/<x-handle>`, already filled. It is a link, not a
  question, so the reply still ends in one yes. The claim page says what is public and how to hide
  before the tap. Once claimed, later replies say "Your page: earnkit.com/<x-handle>".
- Before the claim, the rank shows in replies only; there is no public page.
- "Projects" = distinct things shipped (Score, Shipped). "Real people using them" = projects with at
  least one counted user.

### 3. They say yes: count a project's users
Two kinds of step, picked by what moves the rank now:

- **Count past users now (preferred).** The project has a contract EarnKit isn't tracking yet (found
  through the person's wallet or named by the agent). Tracking it counts every past caller at once,
  through the existing contract reads and anti-farming. Reply: "Done. 140 people who used tokens.fun
  now count toward your rank. You're now #3 of 12."
- **Count future users (builder codes).** For new traffic, the agent adds the ERC-8021 suffix to the
  app's transactions (`dataSuffix` on its viem or wagmi client):
  - Base: the builder's Base code plus the `earnkit` code. The builder's code comes from
    `POST https://api.base.dev/v1/agents/builder-codes` with their wallet, called once and stored
    (owner: "Option 1").
  - Other chains (Arc, Monad, Tempo): an `ek_<person code>` code in the same suffix format, which
    EarnKit decodes itself.
  - EarnKit only reads tags on transactions to contracts it tracks (the builder's own, plus contracts
    the agent says the app calls). Tags on other contracts are invisible without a paid indexer, so
    the reply never promises them.
  - Reply: "Added. New people using tokens.fun will count as they come in." No rank jump is promised.
- **Every app built through EarnKit** carries both codes from the start, and EarnKit's own Base
  deploys for the builder carry them too.
- If they pick a program instead, the agent prepares the entry from the existing project and they
  submit it themselves (today's flow).

### 3b. The token offer (owner ruling: tied to tracking)
The token is where EarnKit earns (owner, 2026-10-13), so it is offered at every moment a project has
something real behind it, and never buried under another question:
The token offer sits at the moment a project's tracking goes live, because that's when there is
something real to attach a coin to:
- **Built through EarnKit:** in the reply that confirms the project is live and tracked (this replaces
  today's pitch at confirm): "It's live, and people using it count toward your rank. Want to launch a
  coin for it? You'd get 40% of its trading fees."
- **Existing project:** once its tracking is live and it has its first counted users.
- It is that reply's one yes. At most once per project; never again after two declines (existing
  rule). Everything else about the token flow (wallet shown before the yes, fees) is unchanged.
- **A ranked project with users and no coin** that has no bigger "How to move up" step gets the token
  offer as the first reply's one yes instead.
- v2.12's score-20 gate is replaced by these moments (a project with counted users, or built through
  EarnKit). Shared clients and held profiles still never see it.
- Measured: token offers shown, accepted and launched per week, in the v2.12 metric script.

### 4. Their rank changes
EarnKit messages only when something real happens, through the existing daily check and `find`'s
"Since you last checked" opener: "12 new people used tokens.fun this week, and you moved up to #3. Want
a card to share it?"

### 5. They share
X is already confirmed from the claim, so sharing is one yes: "Want a card to share it?" The card
(`earnkit.com/<x-handle>/card.png`) shows the X avatar and handle and links to the page and the
leaderboard. Someone who never claimed gets the claim link first.

### 6. Later, only when it fits
- A new program they qualify for. A win or a payout.
- An opt-in email when their rank changes (the existing digest).
- When the flag goes on, existing installs get one message in their next daily check: "Your EarnKit
  page is ready. Claim it with X: <link>."

## Identity

- **One page per person, even across agents.** Installations join one person only on proven ties: the
  same confirmed X account (immutable X user id), the same proven GitHub login (sign-in or proof line),
  or the same EarnKit deploy wallet. An agent-reported login or wallet never merges anyone (it would let
  anyone join someone else's record). The owner's split record is merged by these rules.
- **The page is `earnkit.com/<x-handle>`**, case-insensitive with a redirect to the canonical case. A
  handle equal to a site route is served at `/b/<handle>`. An X rename updates the page at the next
  sign-in or daily refresh; the old handle redirects for 90 days.
- **Verified vs estimate**, shown plainly on the page ("140 people used it" vs "about 40 people, not yet
  confirmed"):
  - Verified: onchain reads of contracts the person proved (EarnKit deploys, or a wallet that signed
    once on the claim page), data EarnKit hosts, tagged transactions, a GitHub account proven by
    sign-in or proof line, or whose public X field matches the confirmed X.
  - Estimate: anything from what the agent reported but EarnKit could not prove. Shown, never scored.
  - The claim page offers two optional one-tap upgrades: sign a message with the wallet, and sign in
    with GitHub. Either turns estimates into verified numbers on the spot.

## Score

0 to 100 in four parts (owner's guide), verified data only. Shown as a rank, never as "0/100".

| Part | Max | Counts | Sources in this update |
|---|---|---|---|
| Shipped | 20 | Live site, deployed contract, published package, hosted demo. Front-loaded so the first ship lands real points | EarnKit deploys and hosting; contracts by verified wallets; homepages of verified repos that resolve; npm and PyPI of verified repos |
| Used | 40 | Unique real users, repeat users, transactions. Self-use and linked wallets never count | Callers of tracked contracts; tagged transactions to tracked contracts; package downloads (capped) |
| Earned | 20 | Fees, revenue, grants and prizes won | tokens.fun creator fees; fees into their contracts; wins from `programs/outcomes` matched to entries |
| Consistency | 20 | Weeks with a ship or with users, and streaks, from any source | EarnKit's event log; commit weeks of verified GitHub; deploy and transaction weeks |

- Stars, forks and merged PRs no longer score (they aren't use). They still show on the page as work.
- v2.12 anti-farming carries over (self-exclusion, one per account, spread over days, fresh accounts,
  rings, review hold).
- Points fade with a 90-day half-life from the last week that earned them.
- Score 0: "not ranked yet" plus the one step. The first verified ship ranks them at once.
- **Fresh within minutes.** `find`, `score` and a page view re-read that person's sources when the last
  reading is older than 10 minutes (inside the run's GitHub budget), then rescore and rerank. The hourly
  job covers everyone else. No new schedule.

## Profile `earnkit.com/<x-handle>` (the design is the deliverable)

The owner: "I want the profile to be amazing and look well designed... No AI slop, capital letter
subheadings or anything that can't be well understood by humans. Simplicity in communication."

- EarnKit's navy design system with the orange and purple accents from v2.12. One dominant thing at the
  top: the rank in words ("#4 of 12 builders on EarnKit") with the score ring beside it.
- Under it, one sentence: "Shipped 6 projects. 2 have real people using them."
- Then the projects, each as a plain card: name, what it is in a few words, people using it, money
  earned, programs entered and won. Estimates are marked "not yet confirmed". Most-used first.
- A quiet line of where the numbers come from ("From GitHub, Base and earnkit.com"). No badges, no
  labels in capitals, no jargon.
- Loading: the header renders at once; project cards show skeletons while readings finish.
- A design review against these rules, and owner sign-off on screenshots, before the flag goes on.

## Card and leaderboard

- **Card:** X avatar, @handle, the rank in words, the best project in one plain line ("1,100 people used
  tipjar"). Funnel Display, readable at X's mobile preview size. Offered from the moment someone is
  ranked.
- **Leaderboard `/leaderboard`:** one list. Rank, avatar and @handle, the best project in plain words.
  Only people with a confirmed X and a verified score above 0. No filters, no tabs, no capital labels.
  Goal: 20 or more real builders at launch, measured, never seeded.

## Acceptance test (binding)

On production, with the flag on, the owner installs EarnKit in their own agent, asks "What can I
earn?", and checks each launch requirement:
1. The rank and work are filled on the first message; one tap with X makes the page.
2. One page per person, even across agents (reconnect, and a second agent).
3. Counting a project's users takes one yes, and the rank moves at once when past users exist.
4. Ranks update within minutes.
5. The page shows which numbers are confirmed and which are not.
6. The reply reads like the owner's example: three short parts, one yes.
The leaderboard's real-builder count is reported against the goal of 20.

## Before launch (owner)

1. An X developer app at console.x.com: verified phone, a few dollars of credits, `X_CLIENT_ID` and
   `X_CLIENT_SECRET` in Railway, callback `https://earnkit.com/x/callback`.
2. The `earnkit` builder code on base.dev, and a note to Base asking whether issuing a code per builder
   through the agents API is fine.
3. Two or three open programs an agent can win (dated or rolling). Arc Microgrants closes 2026-10-15
   and Monad Metropolis on 2026-10-13, so without new ones "Ways to earn right now" is nearly empty.

## Out of scope (next update)

The website snippet (counting real users on sites needs wiring into sign-up and login, and is the most
gameable source), read-only connections (Stripe, Lemon Squeezy, analytics tools, GitLab, Vercel and
Netlify), Chrome Web Store and Farcaster or Base App listings, badges, boards by chain or tool, a
newcomers group, a paid indexer for builder-code tags on other contracts.

## Cost

About $0.01 per X confirmation. Refresh on demand reuses the existing readers inside the GitHub budget.
Everything else uses free APIs and the existing hourly job.
