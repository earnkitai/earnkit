# v2.12.1: Where you stand, from the first message

Status: spec for owner review (2026-10-13, tailored to the target user). Replaces v2.12's onboarding,
replies, scoring, profile, card and leaderboard. v2.12's storage, readers, anti-farming, archives and
terms stay unless this file changes them. `EARNKIT_BUILDER_SCORE` stays off in production until the
owner's own install passes the acceptance test.

## Who this is for (owner, 2026-10-13)

A person who uses AI to build now and then. Lazy. Has a GitHub with little activity. Ships a project
every now and then, with no traction or revenue. Builds for fun, often apps for themselves, but still
wants to earn from what they make. Not technical.

What that means for every screen and reply:
- **They have shipped things but have no users.** So the first thing they see is what they made, not a
  rank they lose on. Rank is shown only when it flatters ("#3 of 40", "top 20%"); otherwise the reply
  leads with their projects and money.
- **Their projects are mostly websites and small apps, not contracts.** Counting people on a website
  is the main tracking step; onchain tracking is there for those who have it.
- **They do nothing technical.** Every step is done by their agent after one yes. Builder text never
  says contract, wallet address, builder code, repo, commit, snippet, onchain or chain names unless the
  builder used the word first.
- **They ship rarely.** What they shipped keeps counting; it never fades to nothing because they took a
  month off.
- **They want money, not metrics.** Every reply has a way to earn with the project they already have,
  and the token is offered as soon as one of their projects has real people using it.
- **Getting a first user is the big win.** "How to move up" for this person is usually "get your first
  5 people using it", with the agent doing the work (a share link and a short post they can send).

## Why this exists

The owner tested v2.12 on production on 2026-10-13: "This is the worst update thus far both in terms of
functionality and usage." It started empty, asked for proofs, used random slugs, and showed a
leaderboard of "Builder 0" rows. This update follows the owner's flow step by step.

**The rule:** the first message shows the builder what they made, how they can earn from it, and one
step up. One tap with X makes it a public page. Nothing waits on the builder doing work first.

**Honesty rule (owner's guide):** only verified data moves the score and the leaderboard. Anything the
agent reported but EarnKit could not prove is still shown, marked "not yet confirmed", and adds
nothing. Confirming is the agent's job, not the builder's (step 3).

**Copy rule:** plain sentences a person understands on first read. Sentence case. No all-caps labels,
no eyebrow labels, no jargon ("outcome", "verified source", "percentile" and the technical words
above never appear in builder or public text). No emojis, no em dashes.

## The flow (owner's, binding)

### 1. Connect
The builder adds EarnKit to their agent. Nothing is asked. In the first `find`, the agent passes what it
can already see, in a new optional `identity` input: GitHub login (git config, `gh auth status`), local
projects (existing `local_repos`), live links it can find (deploy configs, Vercel, Netlify, Lovable,
Replit, GitHub Pages), packages, and any wallet. The tool description tells the agent to fill it and
never to ask the builder.

### 2. The first reply to "What can I earn?"
Inside that call (10-second budget) EarnKit reads the person's public data. Anything slower finishes on
the next reply or page view. Three short parts, ending in one yes.

The typical target user (shipped a few apps, no users yet):
```
Where you stand
You've shipped 3 apps with AI: a recipe planner, a budget tracker and a tip jar. Nobody else is using
them yet, so you're not ranked yet.
Claim your page with X: earnkit.com/claim/<code>

Ways to earn right now
Your tip jar fits Avalanche Team1 mini grants: up to $10K, open all year. I can prepare the entry.
Your recipe planner fits <program>: <prize>, closes <date>.

How to move up
Your apps can't count the people who use them yet. Want me to set that up on all 3? You won't have to
do anything.
```

Someone who already has users:
```
Where you stand
You're #3 of 40 builders on EarnKit. You've shipped 6 projects, and 2 of them have people using them.
Claim your page with X: earnkit.com/claim/<code>

Ways to earn right now
...

How to move up
tokens.fun has people using it who aren't counted yet. Want me to count them? Your rank goes up today.
```

If nothing is found:
```
Where you stand
I couldn't find anything you've made yet.

Ways to earn right now
Arc Microgrants pays 500 USDC for a small app, and I can build one with you in about an hour.

How to move up
Send me a link to something you've made and I'll add it.
```

Rules:
- **Lead with the work.** "You've shipped N apps" names them in a few plain words. Rank appears only
  when the person is ranked and it reads well: "#N of M builders on EarnKit" while fewer than 50 are
  ranked, then "top N% of people building with AI" when N is 50 or less. Otherwise no rank line.
- At most 3 programs, each tied to one of their projects with the reason it fits. Programs that need
  traction they don't have, programs they already entered, closed programs, and programs an agent
  can't complete are never shown.
- "How to move up" is the single step that helps most now, and it only promises what EarnKit can
  deliver. It ends the reply with one yes.
- **The page link is the X sign-in (owner ruling).** "Claim your page with X" opens Sign in with X
  (OAuth 2.0 with PKCE, `GET /2/users/me`, about $0.01 a confirmation on X's pay-per-use API). One tap
  confirms the handle and lands them on `earnkit.com/<x-handle>`, already filled. It is a link, not a
  question. The claim page says what is public and how to hide before the tap. Once claimed, later
  replies say "Your page: earnkit.com/<x-handle>".
- Before the claim, everything shows in replies only; there is no public page.

### 3. They say yes: the agent sets up counting
One yes, and the agent does all of it, for every project it can reach, then reports in one line.

- **Websites and web apps (most target users).** The agent adds EarnKit's small script to each app and,
  where the app has sign-up, login or a save action, one call so EarnKit counts a person when they
  really use it. The same script carries a per-site code, which confirms the site is theirs (it
  replaces asking for `earnkit.txt`). Reply: "Done. When people use your 3 apps, they'll count toward
  your page. Want a link you can send to friends?" (the share link is the next step, see step 4).
- **Projects with people already using them onchain.** The agent names the contract (or EarnKit finds
  it through the person's wallet), and tracking it counts every past user at once. Reply: "Done. 140
  people who used tokens.fun now count. You're now #3 of 40."
- **New onchain traffic.** The agent adds the attribution line to the app's transactions:
  - Base: the builder's Base code plus the `earnkit` code (ERC-8021). The builder's code comes from
    `POST https://api.base.dev/v1/agents/builder-codes` with their wallet, called once and stored
    (owner: "Option 1").
  - Other chains (Arc, Monad, Tempo): an `ek_<person code>` code in the same format, which EarnKit
    decodes itself.
  - Tags are read only on contracts EarnKit tracks; replies never promise more.
- **Every app built through EarnKit** has the script and the attribution line from the start.
- If they pick a program instead, the agent prepares the entry from the existing project and they
  submit it themselves (today's flow).

### 3b. The token offer (where EarnKit earns)
The token is where EarnKit earns (owner, 2026-10-13). For the target user it comes at the first
moment a project has something real behind it, as that reply's one yes:
- **Built through EarnKit:** in the reply that confirms the app is live and counting: "It's live, and
  people using it count toward your page. Want to launch a coin for it? You'd get 40% of its trading
  fees."
- **Existing project:** the reply that reports its first 5 real people: "5 people have used your recipe
  planner. Want to launch a coin for it? You'd get 40% of its trading fees."
- **A project with people using it and no coin**, when no bigger step exists, gets the offer as the
  first reply's one yes.
- At most once per project; never again after two declines (existing rule). The wallet is shown
  before the yes (existing rule). Shared clients and held profiles never see it.
- v2.12's score-20 gate is replaced by these moments.
- Measured weekly in the metric script: offers shown, accepted, launched.

### 4. Getting the first people
For a builder with no users, the next step after counting is set up is the first 5 people, because
that is what unlocks a rank, the card and the token. The agent does it:
- A share link per project (`earnkit.com/<x-handle>/<project>` once claimed) that opens the app.
- A one-line post or message they can send, written by EarnKit in plain words.
- When the first real person is counted: "Someone new used your recipe planner." At 5: the token
  offer (step 3b).

### 5. Their page changes
EarnKit messages only when something real happens, through the existing daily check and `find`'s
"Since you last checked" opener: "12 new people used tokens.fun this week, and you moved up to #3. Want
a card to share it?" No nudges when nothing happened.

### 6. They share
X is confirmed from the claim, so sharing is one yes: "Want a card to share it?" The card
(`earnkit.com/<x-handle>/card.png`) shows the X avatar and handle and links to the page and the
leaderboard. Someone who never claimed gets the claim link first.

The card is offered at moments worth bragging about, not only rank:
- their first claimed page with at least one shipped project ("Shipped 3 apps with AI"),
- their first real users,
- a rank change into a range that reads well.

### 7. Later, only when it fits
- A new program they qualify for. A win or a payout.
- An opt-in email when something real happens (the existing digest).
- When the flag goes on, existing installs get one message in their next daily check: "Your EarnKit
  page is ready. Claim it with X: <link>."

## Identity

- **One page per person, even across agents.** Installations join one person only on proven ties: the
  same confirmed X account (immutable X user id), the same proven GitHub login (sign-in or proof line),
  the same EarnKit deploy wallet, or the same EarnKit script code on a site. An agent-reported login or
  wallet never merges anyone.
- **The page is `earnkit.com/<x-handle>`**, case-insensitive with a redirect to the canonical case. A
  handle equal to a site route is served at `/b/<handle>`. An X rename updates the page at the next
  sign-in or daily refresh; the old handle redirects for 90 days.
- **Confirmed vs not yet confirmed**, shown plainly on the page:
  - Confirmed: sites carrying their EarnKit script, apps EarnKit hosts or deploys, contracts deployed
    by EarnKit or by a wallet that signed once on the claim page, a GitHub account proven by sign-in or
    proof line or whose public X field matches the confirmed X.
  - Not yet confirmed: anything else the agent reported. Shown, never scored. The counting step (step
    3) confirms most of it without the builder doing anything.

## Score

0 to 100 in four parts (owner's guide), confirmed data only. Shown in plain words, never as "0/100".

| Part | Max | Counts | Sources in this update |
|---|---|---|---|
| Shipped | 20 | Live sites and apps, deployed contracts, published packages, hosted demos. Front-loaded so the first ship lands real points | Sites with the EarnKit script; EarnKit deploys and hosting; contracts by confirmed wallets; packages of confirmed repos |
| Used | 40 | Real people using it, repeat use, transactions. The builder's own use never counts | People counted by the script (capped at 15); callers of tracked contracts; tagged transactions to tracked contracts; package downloads (capped) |
| Earned | 20 | Fees, revenue, grants and prizes won | tokens.fun creator fees; fees into their contracts; wins from `programs/outcomes` matched to entries |
| Consistency | 20 | Weeks with a ship or with users, from any source | EarnKit's event log; commit weeks of confirmed GitHub; deploy weeks; weeks with counted people |

- Stars, forks and merged PRs no longer score. They still show on the page as work.
- **What they shipped doesn't vanish.** Shipped points keep at least half their value forever; Used and
  Consistency fade with a 90-day half-life. Taking a month off never resets someone to nothing.
- v2.12 anti-farming carries over (self-exclusion, one per account, spread over days, fresh accounts,
  rings, review hold).
- **Ranked = at least one real person used something they made.** Shipping alone shows on the page and
  in the card ("Shipped 3 apps with AI") but doesn't put them on the leaderboard.
- **Fresh within minutes.** `find`, `score` and a page view re-read that person's sources when the last
  reading is older than 10 minutes (inside the run's GitHub budget), then rescore. The hourly job covers
  everyone else. No new schedule.

## Counting real people on websites

The script (`<script src="https://earnkit.com/t.js" data-ek="<site code>">`) never counts page views.
A person counts when they really use the app:
- the site calls `ek('user', id)` on sign-up, login or wallet connect (the id is hashed in the browser;
  EarnKit stores only the hash), or `ek('action')` on a real action (save, post, pay, send);
- for apps with no accounts, a device counts once it comes back and acts on a second day.
Limits: one count per person per site, the builder's own devices excluded (their first device is
marked at setup), script counts capped at 15 of the 40 Used points, writes batched per site per minute
and rate-limited, so cost stays flat. The script is EarnKit's own file, immutable per version in the URL, and the agent adds it with its
`integrity` hash and `crossorigin="anonymous"` so a changed file never runs on a builder's site.

The owner: "I want the profile to be amazing and look well designed... No AI slop, capital letter
subheadings or anything that can't be well understood by humans. Simplicity in communication."

- EarnKit's navy design system with the orange and purple accents from v2.12.
- The top line is what they made, in their words: "Jenil has shipped 6 apps with AI." Under it, when
  there is one, the rank with the score ring ("#3 of 40 builders on EarnKit"), and the people line
  ("2 of them have people using them").
- Then the projects as plain cards, a screenshot or icon of the app when there is one, its name, what it
  does in a few words, people using it, money earned, programs entered and won. "Not yet confirmed"
  shown quietly where it applies. Most-used first, then newest.
- A quiet line of where the numbers come from. No badges, no labels in capitals, no jargon.
- Loading: the header renders at once; project cards show skeletons while readings finish.
- A design review against these rules, and owner sign-off on screenshots, before the flag goes on.

## Card and leaderboard

- **Card:** X avatar, @handle, the headline that fits ("Shipped 3 apps with AI", "5 people use my
  recipe planner", "#3 of 40 builders on EarnKit"), Funnel Display, readable at X's mobile preview
  size.
- **Leaderboard `/leaderboard`:** one list. Rank, avatar and @handle, the best project in plain words.
  Only people with a confirmed X and at least one real person using their work. No filters, no tabs,
  no capital labels. Goal: 20 or more real builders at launch, measured, never seeded.

## Acceptance test (binding)

On production, with the flag on, the owner installs EarnKit in their own agent, asks "What can I
earn?", and checks:
1. The first message names what they shipped, a way to earn with it, and one step; one tap with X makes
   the page.
2. One page per person, even across agents (reconnect, and a second agent).
3. One yes sets up counting on their existing projects, with the builder doing nothing.
4. The page updates within minutes of a real person using a project.
5. The page shows which numbers are confirmed and which are not.
6. No technical word appears in any reply or on the page.
7. The token offer appears at the moments in step 3b and nowhere else.
The leaderboard's real-builder count is reported against the goal of 20.

A second test with a fresh account shaped like the target user (a few small apps, little GitHub, no
users) must also pass 1, 3, 5 and 6.

## Before launch (owner)

1. An X developer app at console.x.com: verified phone, a few dollars of credits, `X_CLIENT_ID` and
   `X_CLIENT_SECRET` in Railway, callback `https://earnkit.com/x/callback`.
2. The `earnkit` builder code on base.dev, and a note to Base asking whether issuing a code per builder
   through the agents API is fine.
3. Two or three open programs that small, early apps can win (dated or rolling). Arc Microgrants
   closes 2026-10-15 and Monad Metropolis on 2026-10-13, so without new ones "Ways to earn right now"
   is nearly empty for the target user.

## Out of scope (next update)

Read-only connections (Stripe, Lemon Squeezy, analytics tools, GitLab, Vercel and Netlify), Chrome Web
Store and Farcaster or Base App listings, badges, boards by chain or tool, a newcomers group, a paid
indexer for builder-code tags on other contracts.

## Cost

About $0.01 per X confirmation. Script writes are batched and capped. Refresh on demand reuses the
existing readers inside the GitHub budget. Everything else uses free APIs and the existing hourly job.
