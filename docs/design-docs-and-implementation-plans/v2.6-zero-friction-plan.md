# v2.6 Zero Friction: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A non-technical builder goes from "anything worth building?" to a submitted entry with a coin in the fewest steps: every program has a builder bonus by default, the first message says "$X is open right now" or "matches you to $X ... you qualify for", and one yes at submission confirms both the coin and the wallet.

**Architecture:**
- **One bonus rule** (`bonusOn`: active, not opted out with `builder_bonus: false`, not a campaign) replaces "has a `submission_proof` pattern" everywhere the bonus is decided: booking, the first message, the coin row, the board and the cron.
- **The coin gate** reads `earnkit.txt` through GitHub's contents API (raw URL only when rate-limited), needs a ticker-free `token: <code>` line, a repo with real code, and no longer a live link or a wallet line.
- **Submission proof becomes a bonus check:** a page EarnKit can't fetch, or a program with no public pages, counts on the builder's confirmation, recorded in a new `projects.submission_basis`. Owner test installations (`EARNKIT_TEST_INSTALLATIONS`) are never ranked, paid or counted in stats.

**Tech Stack:** Next.js 16, postgres.js, zod v4, viem 2.57, node:test via `tsx --test`.

**Spec:** `docs/design-docs-and-implementation-plans/v2.6-zero-friction.md` (approved, binding).

**Execution method (chosen by the owner):** subagent-driven. A fresh implementer works on each task, a fresh reviewer checks it before the next task starts, and a whole-branch review runs at the end.

**Plan format note (Ruling 0, as in v2.5):** every task gives exact interfaces, behaviours, values and test cases. Full code is given only for novel arithmetic or logic:
- T1: `bonusOn` and `bookingFor`.
- T2: `youCould` and the headline.
- T3: the token code, the parser line, the contents-API read and the repo-with-code rule.
- T4: the coin row, the wallet line and the after-submission text.
- T5: the proof outcome and the basis/recheck transitions.
- T6: the test-installation parser.

Implementers write the remaining code to these interfaces, following the v2.5 modules they extend.

- **The with-repo hook:** keep "qualify" in it. "You could" appears only when there are no repos and no GitHub user.
- **No custody and no placeholder wallets.**
- **Infra cost near zero:** no new services.
- **No broadcasts on real chains in tests.**
- **No secrets in logs.**
- **Production DB safety:** additive migrations only, and existing v2.5 rows keep working.

## Plan Rulings (spec gaps)

- **Ruling 1 (plan), existing coins.**
  - A launched coin is never re-gated: `runTokenFlow` stops at `existingTokenUrl` before the gate. That doesn't change, so no v2.5 coin can be invalidated.
  - The new code is ticker-free and versioned: HMAC input `token-line:v2:<installation>:<normalized repo>`, the first 16 hex characters, line `token: <code16>`.
  - The v2.3–v2.5 line `token: <SYMBOL> <code10>` stays accepted for the ticker being launched. So a builder who pushed the old line before the deploy can still launch.
  - Sixteen hex characters can never parse as a v2.5 symbol (at most 10), so the two forms can't collide.
- **Ruling 2 (plan), open rounds.**
  - Deposits already booked to the Safe under Ruling 9 (Base, Circle and Monad had no proof pattern) **stay with the Safe**. There is no retroactive rebooking and no migration of `bonus_ledger` rows.
  - From the v2.6 deploy on, a deposit is booked by its block time (`bookingFor`, unchanged), so the first deposit after the deploy creates the program's current round row. Its key is the same `windowKey` or UTC month it would always have had.
  - The pool shown is round bookings only, so it starts from the v2.6 deposits.
  - Safe-booked rows already swept, or waiting for the sweep, are untouched.
- **Ruling 3 (plan), the repo-with-code gate.** A coin needs a public GitHub repo that:
  - is not empty: `GET /repos/{o}/{r}/commits?per_page=1` returns at least one commit (409 means empty);
  - and is either a non-fork, or a fork with commits ahead of its parent (`GET /repos/{parent}/compare/{parent_branch}...{owner}:{branch}`, `ahead_by > 0`).

  Cost: the repo read and the commits read, plus the compare only for forks. The spec's "commit by the repo owner" is not checked by author, because org-owned repos have no owner author. Push access is what the ticker-free token line proves (only someone who can push can add it).
- **Ruling 4 (plan), unverified page.**
  - A confirmed entry whose proof page can't be fetched is stored with `projects.submission_basis = 'unverified_page'` and counts as eligible.
  - At freeze, `finalRanking` adds the review flag `unverified_page`. It goes into `bonus_payouts.flags` (the review page's Flags column), **never** into `terms.flagged`. So it never puts a round in `needs_owner`, and never makes the cron answer 503 by itself.
  - The review page gets a Submission column: "page checked", "unverified page" or "builder confirmed".
  - The daily re-check keeps reading an `unverified_page` entry while its round is open:
    - the page links the entry: it becomes `page`;
    - the page loads without the link: it is no longer eligible;
    - still unreachable: no change.
- **Ruling 5 (plan), builder confirmation.**
  - `record_submission` gets a new optional field `builder_submitted`; only `true` counts. It means "the builder confirmed the entry is submitted on the program's site". It is stored as `projects.submission_confirmed_at`.
  - It is not derived from `builder_confirmed`, which is consent to the coin row given *before* the submit, nor from `submission_data`. An explicit field can't be implied by accident.
- **Ruling 6 (plan), test installations.**
  - `EARNKIT_TEST_INSTALLATIONS` is split on `,` and each part trimmed; empty parts are skipped.
  - A part counts when it is 1 to 10 digits and a positive integer at most 2147483647. Anything else is ignored.
  - Each distinct value of the variable gets one `console.warn`, naming only the count and the positions of the malformed parts, never their text.
  - The coins of test installations are real, and their fees are booked like any coin's.
- **Ruling 7 (plan), one bonus rule.**
  - `bonusOn(p)` = `p.status === 'active' && p.builder_bonus !== false && p.campaign == null`. EarnKit and sponsor campaigns stay out: they pay their own prizes.
  - The SQL twin is `g.status = 'active' AND g.builder_bonus AND g.campaign IS NULL`.
  - `submission_proof` now only decides *how* an entry's submission is checked, never *whether* the program has a bonus.
- **Ruling 8 (plan), windowed programs.** `program-file.ts`'s refine "a windowed program with a bonus needs `starts_at`" now applies when `builder_bonus !== false` and the program isn't a campaign, instead of when `submission_proof` is set. Every current file passes: Arc, Colosseum and Monad have `starts_at`; Base and Circle are rolling.
- **Ruling 9 (plan), pre-v2.6 entries on programs without a pattern.**
  - They are not back-filled: they have no `submission_confirmed_at`, so they aren't eligible.
  - The agent can call `record_submission` again with `builder_submitted: true`. An earlier ineligible row never blocks a repo (v2.5 Ruling 15).
- **Ruling 10 (plan), wallet memory.**
  - `installations.payout_wallet` is reused as "this installation's last wallet". It is written on every `record_submission` that names a valid wallet, and whenever the token flow keeps a creator wallet (`saveCreatorWallet`).
  - Outside campaigns it is prefilled. The coin row shows it shortened, `0xAB12…ef01`, and the consent footnote under the table names it in full, as v2.3 does.
  - Campaign entries still ask about it in full and never prefill it (I8, unchanged).
- **Ruling 11 (plan), when "You could" shows.**
  - The no-repo template ("You could win" column) shows only when `repos === null` and no GitHub user or repo list was given *or remembered* (`githubGiven`).
  - A GitHub user with 0 repos found, or a matching error, gets the same headline "$X is open right now." with a "Prize" column and no "could".
  - Local repos reported and none fitting keep v2.5's "None of your N repos fits..." text.
- **Ruling 12 (plan), the leaderboard link.**
  - Builder-facing links use the slug `<program id>-<YYYY-MM-DD | YYYY-MM>` (`boardSlug`: the round key's `:` becomes `-`), for example `earnkit.com/bonus/arc-microgrants-2026-09-16`.
  - `/bonus/[round]` accepts both the slug and the v2.5 `:` form (`roundKeyFromSlug`), so v2.5 links and the sitemap keep working.
- **Ruling 13 (plan), `local_repos[].url`.**
  - It is optional. It is kept only when `githubRepo(url)` parses it, stored as `https://github.com/<owner>/<repo>`.
  - Any other value is ignored and never fails `list_programs`. A dropped url leaves `repo_url: null`, as in v2.5.
- **Ruling 14 (plan), the contents-API fallback.**
  - The raw URL is read only when the API is rate-limited: 429, or 403 with `x-ratelimit-remaining: 0`.
  - An API 404 is "missing", with no raw read. A redirect, another status or a network failure is a retryable error.
  - When `EARNKIT_OWNERSHIP_BASE_URL` is set (dev/test only), the gate reads that override as today, so `token-e2e` keeps its mock.
- **Ruling 15 (plan), what counts as unreachable.**
  - "Unreachable" (the builder's confirmation counts, and the entry is flagged) means any fetch failure: network, timeout, any non-2xx status such as DoraHacks' 405, or an oversize page.
  - "Not eligible" means a wrong host, a path mismatch, no repo or live link to match, or a page that loaded without the entry's link.
  - An entry on a pattern program still needs an `external_submission_url`.
- **Ruling 16 (plan), stats.**
  - `/api/stats` gains `bonus_programs_open`: open programs with `bonusOn`. Its label is "programs with a builder bonus".
  - Test installations are excluded from `installs`, from `coins_launched`, and from the bonus deposits behind `fees_to_safe_eth`.
- **Ruling 17 (plan), `bonusLive`.**
  - With the bonus on every active program, `bonusLive` is true whenever any non-campaign program is active. So a missing or malformed payout key makes the cron answer 503 (`BONUS_WALLET_UNSET`).
  - Production has had the key since v2.5. The owner steps say to confirm it before the merge.
- **Ruling 18 (plan), no wallet at submission.**
  - The entry is recorded and the coin is skipped, with the note `No coin yet: send a wallet with launch_token to add it before <Mon D>.` The date is the last day of the program's open round (`roundFor(...).ends` minus 1 ms).
  - With no open round, or no bonus, the note ends `...to add it.` instead.

```ts
/**
 * v2.6 §4, Ruling 7 (plan): whether a program's entries can earn the builder bonus. One rule for
 * booking, list_programs, the coin row, the board and the cron. SQL twin:
 * `g.status = 'active' AND g.builder_bonus AND g.campaign IS NULL`. Pure.
 */
export function bonusOn(p: { status: string; builder_bonus?: boolean | null; campaign?: unknown }) {
  return p.status === 'active' && p.builder_bonus !== false && (p.campaign === null || p.campaign === undefined);
}

/**
 * Where a deposit at `at` from a coin entered in `program` goes: its open round, or the Safe (no
 * rollover). The Safe when the program opted out (builder_bonus: false) or is a campaign, and
 * whenever it isn't 'active'. v2.6 drops v2.5's "no submission_proof → Safe" (Ruling 9); deposits
 * booked under it stay with the Safe (Ruling 2 (plan)). Pure.
 */
export function bookingFor(
  program: Window & { status: string; builder_bonus?: boolean | null; campaign?: unknown },
  at: Date,
): { destination: 'round'; round: Round } | { destination: 'safe'; reason: string } {
  if (program.builder_bonus === false || (program.campaign !== null && program.campaign !== undefined))
    return { destination: 'safe', reason: 'builder bonus off' };
  const round = program.status !== 'active' ? null : roundFor(program, at);
  return round ? { destination: 'round', round } : { destination: 'safe', reason: 'no open round' };
}
```

```ts
// token-gate.ts
export const TOKEN_CODE_LENGTH = 16;

/**
 * v2.6 §3, Ruling 1 (plan): the earnkit.txt code, bound to the launching agent and the repo, never
 * the ticker: the first 16 hex of HMAC-SHA256(EARNKIT_AUTH_SECRET, "token-line:v2:<installation>:
 * <normalized repo>"). Null when the secret is unset (launches fail closed).
 */
export function tokenCode(installationId: number, repoUrl: string, secret = process.env.EARNKIT_AUTH_SECRET) {
  if (!secret) return null;
  return createHmac('sha256', secret)
    .update(`token-line:v2:${installationId}:${normalizeRepoUrl(repoUrl)}`)
    .digest('hex')
    .slice(0, TOKEN_CODE_LENGTH);
}
export function tokenLineFor(installationId: number, repoUrl: string): string | null {
  const code = tokenCode(installationId, repoUrl);
  return code && `token: ${code}`;
}

export function ownerProblem(repo: string, got: FetchResult, code: string, legacy: { symbol: string; code: string } | null) {
  const line = `token: ${code}`;
  if (got.status === 'error')
    return `EarnKit couldn't read ${OWNERSHIP_FILE} in ${repo} (${got.message}). Say 'launch the token' to retry.`;
  const file = got.status === 'ok' ? parseOwnershipFile(got.text) : null;
  if (!file)
    return `A coin needs proof you can push to ${repo}: add a file named ${OWNERSHIP_FILE} at its root (default branch) with the line "${line}", push it, then call launch_token.`;
  // payout_wallet / creator_wallet lines are campaign business (checkOwnership); a coin needs only the code.
  const ok =
    file.codes.some((c) => sameCode(c, code)) ||
    (legacy !== null && file.tokens.some((t) => t.symbol === legacy.symbol && t.code !== null && sameCode(t.code, legacy.code)));
  return ok ? null : `Add the line "${line}" to ${OWNERSHIP_FILE} at the repo root (default branch), push it, then call launch_token.`;
}
```

```ts
export type RepoCode = { fork: boolean; hasCommits: boolean; aheadOfParent: number | null };

/** Ruling 3 (plan): the repo, its first commit, and (forks only) how far it is ahead of its parent. */
export async function repoCodeFacts(fullName: string): Promise<RepoCode> {
  const r = await gh<Repo & { parent?: { full_name: string; default_branch: string } }>(`/repos/${fullName}`);
  const hasCommits = await repoHasCommits(fullName);
  if (!r.fork || !r.parent || !hasCommits) return { fork: r.fork, hasCommits, aheadOfParent: null };
  const owner = r.full_name.split('/')[0];
  const c = await gh<{ ahead_by: number }>(
    `/repos/${r.parent.full_name}/compare/${encodeURIComponent(r.parent.default_branch)}...${encodeURIComponent(owner)}:${encodeURIComponent(r.default_branch)}`,
  );
  return { fork: true, hasCommits, aheadOfParent: c.ahead_by };
}
```

```ts
// submission-proof.ts
export type ProofOutcome = { kind: 'ok' } | { kind: 'unreachable'; problem: string } | { kind: 'refused'; problem: string };

/**
 * proofProblem's checks, with Ruling 15 (plan)'s split: a fetch that fails for any reason (network,
 * timeout, non-2xx such as a bot wall's 405, oversize) is 'unreachable' (the builder's
 * confirmation counts, flagged); every other failure is 'refused' (not eligible).
 */
export async function proofCheck(...same params as proofProblem): Promise<ProofOutcome> {
  // Body = today's proofProblem. Each `return '<text>'` becomes `return { kind: 'refused', problem: '<text>' }`,
  // the fetch catch returns { kind: 'unreachable', problem: <oversize text or RETRY_NOTE> },
  // and `return null` becomes `return { kind: 'ok' }`.
}
export async function proofProblem(...same params): Promise<string | null> {
  const o = await proofCheck(program, url, repoUrl, liveUrl, deps);
  return o.kind === 'ok' ? null : o.problem;
}

export function recheckUpdate(row: { ok_at: Date | null; basis: string | null; confirmed: boolean }, o: ProofOutcome, now: Date) {
  if (o.kind === 'ok') return { ok_at: row.ok_at ?? now, basis: 'page' };
  if (o.kind === 'refused') return row.ok_at === null && row.basis === null ? null : { ok_at: null, basis: null };
  if (row.ok_at === null && row.confirmed) return { ok_at: now, basis: 'unverified_page' };
  return null;
}
```

```ts
export function testInstallationIds(
  env: Record<string, string | undefined> = process.env,
  warn: (line: string) => void = console.warn,

  const raw = env.EARNKIT_TEST_INSTALLATIONS ?? '';
  const ids = new Set<number>();
  const bad: number[] = [];
  raw.split(',').forEach((part, i) => {
    const s = part.trim();
```
