# v2.8: Win engine. Strong applications, the token as the bonus ticket, more payouts per project

Status: draft for review (2026-10-07). Builds on v2.7.2 (`main` 1658be4).

## Goals, in order

1. **Installs.** Visitors install EarnKit because it gets them paid more.
2. **The token at submission.** Builders launch a token, because the token is their ticket to the builder bonus.

Everything else leads to these two with no friction.

The persona is a lazy builder who only wants money. EarnKit does not help them build. It raises their odds of winning, and makes entering and the token launch effortless.

## Rules for every part

- **Facts only.** Every program fact has a `source_url`. A rating that EarnKit makes itself is labelled "rated by EarnKit" and never shows a made-up statistic.
- **Copy.** Short and money first. No emojis. Never "coin", never "Clanker", never an em dash (a test enforces this). Builder text never names tools, fields or files.
- **Lazy builder test.** Every part must pass this check: can the builder breeze through applications to several programs, with a strong application each time, while saying very little? If a step adds reading, choices or typing that the agent could do itself, cut it.
- **Same for every program.** Each part runs off the program file and a fixed vocabulary. Adding a program means filling its file, never writing code.
- **Cost stays flat.** No new services, and no LLM calls on the server. All writing happens in the builder's own agent. Outcomes are captured by the existing weekly routine and the hourly cron.
- **Additive DB changes only.**
- **Never** handle credentials, solve captchas, submit without the builder, or break a platform's terms.

## Part C. The token is the builder bonus ticket

**At the confirmation**, which is the moment the builder is talking to their agent, one combined offer replaces the separate token row:

```
Want the builder bonus? It comes with a token.
Yes: your entry gets a token on Base. You earn 40% of its trading fees and compete for the builder bonus (top 10 on each program, paid in ETH).
Skip: no token, no builder bonus.
Wallet for fees and any bonus: 0xab12…0123 (used last time), or tell me another.
```

- **The token launches on this "yes".** It no longer waits for `record_submission`.
  - The launch needs a public repo with real code, the ownership line (which the agent pushes), a wallet, and a ticker. The ticker is re-checked right before deploy.
  - The v2.7 C7 gate on the entry's required items moves from token launch to **builder bonus eligibility**. The token launches; the bonus still pays only entries that are complete, submitted and proven.
- **The first message names the token's money once:** "Every entry gets a token: you earn 40% of its trading fees, and its fees fund the builder bonus."
- **No wallet:** "No wallet? Make one at keys.coinbase.com, then send me the address." Still no custody, and only the shown wallet is used.
- **Agents that can't push the ownership line** (for example Grok Bot without GitHub write access): one line, "To launch your token, open this in Claude Code or Cursor." The entry still records.

## Part D. Application coach (replaces the scored entry check)

Turns a scattered idea or an average project into a strong application, for every program.

**1. Form map.** Each program file lists its form fields under `submission_requirements` (it already does). Each field gets a `kind` from a fixed vocabulary:

`name`, `one_liner`, `problem`, `solution`, `how_it_works`, `traction`, `team`, `why_you`, `use_of_funds`, `milestones`, `demo_video`, `links`, `contact`, `other`.

**2. Guidance per field kind.** There is a built-in default for every kind. A program may add its own, sourced from its rubric and past winners. Each field's guidance has three parts:
- **What judges look for**, in one line.
- **Questions to ask the builder:** at most 2. They are asked only when the repo and onchain data can't answer them, e.g. "Who has used it so far?" or "Why are you the one to build this?"
- **A strong-answer pattern and the limit**, e.g. "Lead with the user and the number. One sentence of how. One proof link."

**3. Draft.** The agent drafts every field from the repo, onchain data (users, contracts), commit history and the builder's short answers. EarnKit returns the guidance and the facts it has, such as user counts, chain and live link status. The agent writes.

**4. Check before submitting.** Pure rules, in at most 3 fixes, never blocking:
- a claim with no number;
- a missing proof link;
- an answer over its limit;
- a judging criterion that no answer addresses;
- a required field left empty.

**5. Saved.** The final answers and the check result are stored on the entry at submit time. This is the dataset that outcomes are matched against.

**Answer bank: breeze through every program.**
- The coach saves the builder's answers per project, keyed by field kind.
- The next program reuses them. The coach only asks what's new for that form, which is usually nothing or one question, and re-angles the existing answers to the new program's judges.
- The second application should take seconds, not another interview.

**Simplicity limits:**
- At most 3 questions for the first program, and at most 1 for each later program.
- At most 3 fixes.
- One draft shown as a short table (field, answer); the full text sits behind "show all".
- No step needs the builder to read guidance. The guidance is for the agent.

**Builder-facing flow:**

```
Arc Microgrants: 3 quick questions, then I'll write your application.
1. Who has used TipJar so far?
2. What would you build next with the grant?
3. Anything that makes you the right person for this?
```

Then the draft, then: "Ready. Want the builder bonus? It comes with a token." (Part C).

## Part E. Submit kit (the hand-off to the program's form)

EarnKit returns the form URL and the final answers mapped field by field, plus a `submit_mode` taken from a platform registry keyed by host. The registry is the same for every program on that host.

| submit_mode | Platforms | What happens |
|---|---|---|
| `prefilled_link` | Google Forms without sign-in, Airtable, Tally | EarnKit builds a prefilled URL. The builder opens it, reviews it and clicks submit. |
| `agent_fills` | ETHGlobal, Devfolio, Colosseum Arena, Monad (Metropolis host), Akindo/WaveHack, TAIKAI, Google Forms with sign-in | If the agent has a browser tool, it fills the form in the builder's own logged-in browser. It stops at login, captcha, wallet signing and file uploads. The builder clicks submit. |
| `copy_paste` | DoraHacks, Questbook (Arc Microgrants, Circle) | Their terms ban automated use. EarnKit gives a clean field-by-field list to paste. This changes only if the platform approves in writing. |
| `api` | Superteam Earn (agent-allowed listings), Karma GAP | Uses the platform's official agent API with keys held by the builder's agent, never by EarnKit. |

Program files gain `submit_host`, or it is derived from `submission_url`. Optimism (OP Atlas, shut down) is never listed.

**Proof.** EarnKit captures the public entry URL where the platform has one: DoraHacks, ETHGlobal, Devfolio, Colosseum, Akindo, TAIKAI, Karma. For plain forms, the agent asks the builder for the confirmation screenshot or email, which counts as builder-confirmed under v2.6 rules.

## Part F. More payouts per project ("Also qualifies")

After an entry is recorded, EarnKit shows at most 3 other open programs the project already qualifies for. It decides this from chain, `existing_work`, the deadline, not already being entered, and the items still missing. Each row offers "enter it here too", which reuses the coach answers already written.

The token stays one per repo, and its fees fund the builder bonus of the first program (owner decision A). Other entries show "builder bonus counts in <program>".

## Part G. Outcomes (minimal now, the moat over time)

- **Table `entry_outcomes`** (additive):
  - `project_id`, `program_id`, `round_label`;
  - `result`: one of `won`, `placed`, `finalist`, `not_selected`, `unknown`;
  - `prize_usd`, `source_url`, `captured_at`;
  - `basis`: one of `announcement`, `self_reported`.
- **Capture:**
  1. **Weekly routine.** Program files gain `results_url` and `results_expected`. When results are due, the routine reads the announcement, updates `past_rounds` and labels every EarnKit entry by repo, name or live link.
  2. **The builder.** After `results_expected`, the agent asks once: "Did TipJar win anything in Arc Microgrants?" The answer is stored as self-reported, is never shown in public stats, and the next weekly run checks it.
- **Builder alerts** fire only for sourced wins: "you won $500 in Arc Microgrants with TipJar".
- **`/api/stats`** gains `labelled_entries` and `entries_won`.
- **The public win-rate claim** is withheld until there are at least 30 labelled EarnKit entries and a baseline exists.
- **Deferred:** per-platform result parsers and automatic answer-pattern learning. Both wait until there are enough outcomes to learn from.
