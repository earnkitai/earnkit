# v2.8: Win engine — more payouts per project, better odds per entry, outcomes we keep

Status: draft for review (2026-10-07). Builds on v2.7.2 (`main` 1658be4).

## Goal

Raise what a builder earns from the programs they enter, through three generic parts:

1. **More payouts per project.** Find every other open program a project already qualifies for, and enter it there too.
2. **Better odds per entry.** Before submitting, score the entry against what wins that program and name up to 3 fixes.
3. **Outcomes we keep.** Record the result of every entry, so the first two improve over time and EarnKit can later prove it helps builders win.

Every part runs off data in the program file and a fixed vocabulary of signals. No program gets custom code: adding a program means filling in its file.

## Principles

- **Facts only.** Every winning signal and every result has a `source_url`. A builder's own word is labelled self-reported and never feeds public stats.
- **Never blocks.** The review advises. Submitting is always the builder's call.
- **Short, money-first builder copy.** Tables and pills; no tool, field or file names; "token", never "coin".
- **Cost stays flat.**
  - No new services and no request-time LLM calls on the server.
  - Outcome capture runs inside the existing weekly re-verification routine and the hourly cron.
  - GitHub and RPC reads stay bounded per entry, using the existing token and free RPCs.
- **Additive DB changes only.**

## 1. More payouts per project ("Also qualifies")

**When it runs**
- After an entry is recorded.
- Whenever the builder asks "What can I earn?" and has entered projects.

**How EarnKit decides a project qualifies for another program.** It uses the existing match engine with these inputs:
- the project's chain or contracts, plus the program's `chains`;
- the program's `existing_work`. `allowed` qualifies. `new_work_only` does not, unless the project was created after the program's `starts_at`. `unknown` shows as "check rules".
- the deadline isn't past;
- the required items the project already has: repo, live link, chain. These come from `submission_requirements`, and the missing ones are listed.
- not already entered in that program.

**Builder-facing output.** One table, at most 5 rows, sorted by top prize:

```
TipJar also qualifies for $12,500 more:

| Program | Top prize | Needs | Ends |
|---|---|---|---|
| Base Builder Grants | up to $5,000 | a 1-min Loom | rolling |
| Circle Developer Grants | $5K–$100K | nothing new | rolling |

Want me to enter it in both?
```

**Entering.** The agent uses the normal prepare → record flow for each program, which creates one entry per program.

**Tokens.** One token per repo, as today.
- The token's fees fund the builder bonus of the program it launched for.
- Other entries for the same repo show "builder bonus: counts in <program>". This is the existing Ruling 25.
- **Owner decision:** keep it this way, or let one token's fees be split across every program its repo enters.

## 2. Better odds per entry (entry review)

**Signal vocabulary.** These are fixed and apply to every program. EarnKit checks each one from data it already reads.

| Signal | Checked from |
|---|---|
| `live_mainnet`: a live link that loads, on the program's chain mainnet | probe plus chain id/RPC where a contract exists |
| `demo_video`: a video link given (Loom, YouTube, X video) | answers / links |
| `open_source`: a public repo with a README of 200+ words | GitHub API |
| `real_users`: N or more distinct wallets used the contracts in the last 30 days | the existing users signal (v2.4) |
| `sponsor_tech`: uses the program's named tech (e.g. USDC, CCTP, x402) | repo search for package or contract names listed in the program file |
| `recent_shipping`: commits on 3 or more distinct days in the last 14 | GitHub API |
| `track_fit`: the entry names a track that exists | answers vs `tracks` |
| `complete_answers`: every required item filled | readiness (v2.7) |

**Per program, in its file** (sourced; validated by `programs:check`):

```json
"winning_signals": [
  { "signal": "live_mainnet", "weight": 3, "evidence": "Judges cited live mainnet demos for 3 of 4 winners", "source_url": "https://…" },
  { "signal": "sponsor_tech", "weight": 2, "terms": ["USDC", "CCTP"], "evidence": "Track requires USDC", "source_url": "https://…" }
],
"judging_criteria": { "items": ["Technical execution", "Use of USDC", "Impact"], "source_url": "https://…" }
```

- Weights are 1–3, set at listing time from the rubric and past winners.
- A program with no sourced signals uses the default set (`complete_answers`, `live_mainnet`, `demo_video`, `open_source`) at weight 1. The review is then labelled "general checks".

**Score and output.** Shown in `prepare_submission` once the entry is ready, above the token row:

```
Entry check: Fair — 2 quick fixes would make it stronger
- Add a live mainnet link: judges cited live demos for 3 of 4 past winners
- Add a 1-minute demo video: 9 of 10 past winners had one
```

- **Strength label.** Strong is 80% or more of the weighted signals met. Fair is 50–79%. Weak is under 50%.
- **Fixes.** At most 3: the unmet signals with the highest weight. Each gets one line of evidence quoting the program file.
- **The agent fixes them.** The agent gets machine-readable fixes in `agent_note`, so it can make the fix itself (record the video, deploy to mainnet) and re-check.
- **Never blocking.** "Submit anyway" always works, and no wording implies otherwise.
- **Snapshot.** The score and the met and unmet signals are stored on the entry at submission time. They are the features that outcomes get matched against.

## 3. Outcomes we keep

**Table `entry_outcomes`** (additive): `project_id`, `program_id`, `round_label`, `result` (`won` | `placed` | `finalist` | `not_selected` | `unknown`), `prize_usd` (nullable), `source_url`, `basis` (`announcement` | `submission_page` | `self_reported`), `captured_at`.

**Capture runs in every program's cycle, as three generic layers:**

1. **Submission page.** When a program's `submission_proof` host shows a result badge on the entry's own page, the hourly cron reads it. This is the same page EarnKit already fetches, via a per-host parser keyed by host, not by program. DoraHacks and Colosseum come first. It is bounded at once per entry per day for 14 days after the deadline.
2. **Announcement.** Program files gain `results_url` (where winners get announced) and `results_expected` (a date).
   - The weekly re-verification routine reads announcements that are due and writes the winners into `past_rounds`. That keeps the public guide current.
   - It also marks the outcome of every EarnKit entry in that round, matched by repo, project name or live link. Unmatched entries become `not_selected` once the full list is published, or stay `unknown` if the list is partial.
3. **The builder.** After `results_expected`, the next time the agent talks to EarnKit, the agent asks once: "Did TipJar win anything in Arc Microgrants?" The answer is stored as `self_reported`.
   - It is never used in public stats.
   - It triggers a check of layer 2 on the next weekly run.

**What outcomes unlock**
- **Builder alert.** "you won $500 in Arc Microgrants with TipJar · nice", only when the outcome has a `source_url`. A win also feeds "Since you last checked".
- **Better reviews.** As outcomes accumulate, `winning_signals` evidence can cite EarnKit's own data. For example: "EarnKit entries with a demo video won 3× as often (12 entries)". This applies only when each comparison side has 10 or more labelled entries, and the routine proposes the update in the weekly re-verification.
- **The public win-rate claim** ("EarnKit entries win X% more often") is withheld until there are 30 or more labelled EarnKit entries plus a published baseline for the same programs. `/api/stats` exposes `labelled_entries` and `entries_won` from day one, so progress is visible to the owner.

## 4. Builder journey changes (summary)

1. **First message, for builders with entered projects:** the "Also qualifies" table comes right after "Since you last checked".
2. **prepare_submission:** the entry check (Strong / Fair / Weak, plus up to 3 fixes) sits above the token row when ready.
3. **After recording:** "Also qualifies for $X more" if any other program matches.
4. **After results:** win alerts. One "Did it win?" question per entry, per round.
5. **Program guide page:** a "What judges reward" row of pills from `judging_criteria`, and "Signals that win" pills from `winning_signals`.

## 5. Listing process (applies to every program)

`programs/README.md` gains these steps:
- `judging_criteria` from the rubric, sourced.
- `winning_signals` from past winners and judging, each with evidence and a source.
- `results_url` and `results_expected` from the program page.
- Optional `sponsor_tech` terms.

`programs:check` enforces:
- sources;
- weights between 1 and 3;
- known signal names;
- at most 6 signals;
- at most 12 words of evidence each.

The weekly routine refreshes all of these.

## 6. Testing

- **Unit:**
  - each signal checker, using stubs for GitHub, the probe and RPC;
  - score bands and fix ordering;
  - the default-signal fallback;
  - "Also qualifies" eligibility: `existing_work`, deadlines, chains, already entered;
  - the outcome matcher: by repo, name and live link; partial versus full lists;
  - the per-host result parsers, against saved fixture pages;
  - the alert only firing with a source.
- **DB:** the `entry_outcomes` migration on v2.7 data; the snapshot stored at submit; stats fields.
- **Journey:** a builder enters Arc, sees "Also qualifies", enters Circle, gets an entry check with fixes, and later gets an outcome that triggers a win alert.
- **Copy review:** the new strings use no tool names, never "coin", no emojis, and stay short.

## Out of scope

- Running EarnKit's own campaigns.
- Request-time LLM judging.
- Submitting on the builder's behalf without the agent.
- The public win-rate claim, until the data threshold is met.
