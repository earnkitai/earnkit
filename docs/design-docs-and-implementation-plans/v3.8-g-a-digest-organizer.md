# v3.8 G-A fix D: the digest lists the day's writes; a tied domain re-marks new-organizer programs

Acceptance run G-A (H4), items 8 and 9. Approval: earnkitai/earnkit#159, jenil04/jenil.ai#33.

## Item 8: the digest read showed nothing after four live creates

Observed: GET /api/programs/digest at ~9:42 PM IST on Nov 24 answered `day 2026-11-24, lines [], changes []` while
GET /api/programs/writes listed four creates from ~9:39 PM IST (16:09Z, the same UTC day).

Root cause: the digest's only source for program activity is `program_changes`, and `upsertProgram` writes a
`program_changes` row only when an existing program's tracked fields change (`CHANGE_FIELDS`). A create writes none, and
neither do refusals or handle records, so a day of creates reads as an empty digest. It was not the day boundary
(the window is "since the last digest of an earlier day, else 24 hours", not the UTC day), not the lane (auto_live off
or on, the automated lane and the approval lane both create through `upsertProgram`), and not a live/pending filter.

Fix: `owner-digest.ts` reads the write API's own audit log, `program_writes`, over the same window
(`digestWrites`), and adds `DigestWrites` to the gathered digest:

- `New live programs`: each program a write created that is still listed, with the check's labels (`new organizer`,
  `information only`) and its revert (`(revert: write N)` in the read, the signed link in the email).
- `Organizers confirmed`: programs re-marked by item 9, with why.
- `Writes since the last digest: {n} refused, {m} held for approval, handles recorded: @h domain.` (counts only;
  GET /api/programs/writes has the reasons).

GET /api/programs/digest adds `writes: { created: [{ program_id, title, write_id, labels }], confirmed, refused,
pending, handles }`; `changes` is unchanged (updates only). The email gains the same blocks.

Why not write a `program_changes` row on create: `since.ts` feeds builders' "what changed" from that table, and a
create is not a change to something a builder saw.

Day boundary: the window is rolling, so the owner's IST midnight does not split a night: a create at 23:30 IST and
one at 00:30 IST are both in the 7:30 IST read (test). `day` stays the UTC date (the email's idempotency key).

## Item 9: a handle recorded later re-marks the program

Observed: Fe went live as new organizer at 9:39 PM; `@official_fe -> fe-lang.org` was recorded after, and Fe stayed
new organizer, because organizer status is computed only on a write, and only from a handle the write itself names.

Fix (`official-page.ts`):

- `remarkOrganizer(tx, { domain, organizer?, why, now, skip? })` drops `new_organizer` from listed API programs whose
  official page (official_url, else source_url) is on that registrable domain. Called by the `handle` action (every
  such program: the handle's profile domain is the organizer's own site) and by an automated-lane write that went
  live confirmed (that organizer's programs only, by `organizerKey`). Each re-mark is upserted and audited as
  `organizer` / `confirmed` with the reason, and the catalog is revalidated. The `handle` reply adds `confirmed: [ids]`.
- `organizerStatus` also confirms when any tracked handle's profile domain is the page's domain, so a re-marked
  program stays confirmed when Growth writes it again without naming the handle.
- Never on a shared or platform domain (`ownableDomain`: github.io, devpost.com, dorahacks.io, ... from
  `submit-hosts.ts`), where anyone can publish.

What a re-mark does not change, on purpose:

- `submit` stays `builder`. `labelled()` forced it when the program went live; the writer's own value is not stored
  (the write row's body is the labelled record), so it cannot be restored safely. The builder keeps sending with their
  own tap until the program is written again, when the check now confirms it and the writer's `submit` applies.
- `info_only` is never touched (a link off the page is a separate finding).
- No `program_changes` row: the label is not a builder-facing field (`since.ts`); the digest lists it from
  `program_writes`.
- Revert: an `organizer` row is not an applied write (`appliedSql`), so reverting the create still closes the
  program, and reverting a later update restores an earlier body that carries `new_organizer` (the safe direction).

Fe after the fix: re-posting `@official_fe fe-lang.org` (the record is an upsert) re-marks fe-builders-challenge
confirmed; it stays `submit: builder`.

## Flags, schema

Safe with EARNKIT_FLAGS unset: the approval lane is untouched (an approval-lane create also appears under New live
programs). No schema change.

## Known gap (not changed here)

The existing rule "the write names a tracked handle whose profile domain is the page's" does not check for a shared
platform domain; a handle whose profile links github.io would confirm any github.io page named with it. Left as is.
