# v3.1 Highlights: "Used by" (2026-10-27)

Owner: "agreed and go". The strongest thing a builder can brag about, cheaply verified: real people use what they
built. One new Highlights row, read daily from two free sources. Builds on v3.1-highlights-competence.md (its rules
stand: chain-agnostic competence, never anything coin related, a row with no data is hidden, every row links to proof).

## The row

- Title: `Used by <N> people in the last 30 days` (N with toLocaleString('en-US'); shown only from USED_MIN = 10).
- Sub: `<P>% came back` where P = round(100 * returning / N), returning = wallets active in 2 or more distinct ISO
  weeks inside the 30 days; when P is 0 the sub is the source label instead (`On Base`, `On 2 chains`).
- Icon: a new `users` icon (lucide users stroke paths) in HighlightsCard.tsx.
- Link: the explorer page of the busiest counted contract; for a Builder Code number, the repo file the code is in
  while the repo is public (githubFileHref may need to come back), else no link.
- Order in highlightsOf: live, **used by**, contracts, products, consistency, won, experience (max 5, unchanged).
- When both sources have a number, show the larger one (they overlap; never sum).

## Source 1: the builder's own contracts (any chain, Alchemy)

- Contracts: the builder's wallet_contracts rows with counts = true, plus their verified builder_sources contracts
  (kind 'contract', state 'verified', ref "<chain>:0x...") on a WALLET_CHAINS chain. Never a token (wallet_contracts
  already excludes them; for builder_sources contracts apply alchemy.ts contractCounts' token test too).
- Users: distinct `from` of external transactions sent to those contracts in the last 30 days
  (alchemy_getAssetTransfers toAddress, category external, excludeZeroValue false, order desc, withMetadata, paging
  until a transfer is older than 30 days; at most USED_PAGES = 5 pages of 1000 per contract, at most USED_CONTRACTS =
  10 contracts per builder (the newest)). A capped read still counts what it saw; mark it capped so the title reads
  `Used by 5,000+ people ...`.
- Excluded wallets (anti-farming): the builder's proven wallets (person_wallets), each contract's deployer wallet, and
  every wallet a proven wallet sent ETH to (one alchemy_getAssetTransfers fromAddress=<proven wallet>, category
  external, excludeZeroValue true, per chain, capped at 1 page).
- Networks not enabled in Alchemy are skipped (AlchemyNetworkOff), as in alchemyWalletContracts.

## Source 2: Base Builder Code (CDP SQL API)

- Endpoint: `POST https://api.cdp.coinbase.com/platform/v2/data/query/run`, headers
  `Authorization: Bearer <CDP_CLIENT_API_KEY>`, `Content-Type: application/json`, body `{"sql": "..."}`; response
  `{ metadata: { rowCount }, result: [ {...} ] }`. Env `CDP_CLIENT_API_KEY` (owner sets it on Railway; add it to the
  test guard's CLEARED list; without it this source is off and nothing else changes).
- Free tier is 1,000 queries a month, so **one query per day for all builders together** (a GROUP BY builder_code
  over an IN list of every known code), never per builder, never more than once a day (store the day read; a
  second run the same day is a no-op).
- Tables (ClickHouse SQL): `base.transaction_attributions` (builder_code, transaction_hash, block_timestamp, action)
  joined to `base.transactions` (transaction_hash, from_address, action) for EOA senders, and
  `base.decoded_user_operations` (builder_codes Array, sender, block_timestamp, success, action) for smart-account
  senders. Only `action = 1` rows; only the last 30 days; user ops only `success = 'success'`. Per code: distinct
  users (lowercased addresses, union of both tables) and returning users (2+ distinct ISO weeks). Exclude the
  builder's proven wallets (pass them in the query, or return per-code wallet counts excluding them).
  Validate code strings before putting them in SQL: only `^[a-z0-9_]{1,64}$`; escape nothing else in (no user text
  in SQL).
- Whose code (security review 2026-10-27, binding; replaces "written in the builder's repo" and the "two builders
  claim it, neither counts" rule): a code in repo text is not proof (anyone can paste a popular app's code, and the
  neither rule let an attacker cancel the real owner). A code counts for a builder only when Base's Builder Codes
  registry on Base mainnet (`0x000000BC7E6457e610fe52Dcc0ca5b3ce59C8E80`, ERC-721, github.com/base/builder-codes)
  pays one of that builder's signature-proven wallets: `payoutAddress(string code) view returns (address)`,
  lowercased, is in their person_wallets (ownerOf is Base's custodian, so ownership = payout address). Read with
  eth_call over alchemyCall (Base). A revert (Unregistered) is not owned; a failed read keeps the previous verdict and
  never grants one. Verdicts are stored in `builder_code_claims(code, builder_id, told, payout, owned, verified_at,
  created_at, PK (code, builder_id))` and re-read at most daily in the usage step (the payout can change). Two builders
  can name one code; a wallet belongs to one builder (person_wallets.wallet is the key), so at most one owns it.
- Code candidates: the repo scan's extracted codes (builder-codes-check.ts scans App-proven repos daily: a hex
  data-suffix literal decoded with builder-code.ts codesIn, and `codes: ['...']` / `codes: ["..."]` arrays;
  repo_builder_codes gains `codes text[]`), plus a code the builder names through tell (`builder_code`, validated
  `^[a-z0-9_]{1,64}$`), verified the same way. The tell reply: "Saved. Your Builder Code counts once its payout wallet
  is one you proved." A code read from an env var cannot be seen in the repo; the builder can name it through tell.

## Storage and schedule

- New table (append to db/schema.sql) `app_usage(builder_id int, source text CHECK (source IN ('contracts',
  'builder_code')), day date, users int, returning int, capped boolean, href text, PRIMARY KEY (builder_id, source,
  day))`. Highlights reads the newest day per source (at most 3 days old, else hidden).
- A daily step in the existing cron (follow how the Builder Codes daily step is wired and time-sliced), only for
  Bench-confirmed builders, contracts source per builder, Builder Code source as the one batched query. Stays inside
  Alchemy's free tier: caps above.

## Copy rules

Sentence case, no em dashes, no emojis, "1 person" never shown (USED_MIN 10), never a wallet address.
