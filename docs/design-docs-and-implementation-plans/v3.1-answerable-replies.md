natural asks x 3 builder states, real MCP path; scratchpad gtm/matrix/) read cold by the controller shows one root
cause: most questions route to find/score, whose reply carries almost no facts, so the agent can only show the status

my wallet, how much I earned, who backed me, how to get backers, what EarnKit is, how ranking works, programs that fit.

## 1. Facts the agent can answer from
find and score replies carry `facts` (only what is true and known; omit unknown keys; never private data of others):
- `page`: the builder's page URL (earnkit.com/<slug>), and whether it is public.
- `points`: { total, this_week (if known), what_for } where what_for is EarnKit's existing points description (reuse the
  wording already on the site/docs about points; never invent a conversion rate or date that isn't in the code/docs).
- `rank`: the public rank line and score if ranked; `streak`.
- `shipped_last_week`: the approved/drafted summary or titles of the newest week row (titles only when the page shows
  them: private repo titles only with the titles setting on).
- `wallet`: the reward wallet, short form (0x12ab…abcd), if proven.
- `coin`: { symbol, url (tokens.fun), backers, fees_to_you } when launched; else null.
- `earned`: the existing Earned figure (fees claimed + prizes) if any.
- `applications`: [{ program, status }] from the builder's own entries/statuses.
- `about`: one line each, from existing copy (site-copy/docs-copy), never new claims: what EarnKit is, how ranking works,
  what a Builder Code is ("a one-line tag Base uses to see your traffic"), how to get backers ("post real progress";
  the post draft path).
ANSWER_FIRST_NOTE: answer the builder's question in one short line from show_to_builder and `facts`; if the answer
needs a link, use the one in facts (the reply still shows at most one https link of its own). Keep descriptions under
800 characters; the note itself can be longer (it's in the result, not the description) but keep it tight.
