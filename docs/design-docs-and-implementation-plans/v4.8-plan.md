# v4.8 The agent adds payments: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A builder whose product is live but takes no money gets one question offering the payment method that suits that product. A yes has their own agent add it, following the provider's guide. A no is never asked again.

**Architecture:**
- **Stack signals.** Discovery already reads `package.json` and `pyproject.toml` (`discovery.ts`). It now also keeps a small stack summary in the repo's cached `product` facts: `stack: { kind, payments }`.
- **The picker.** `pickPayment` is pure and maps stack plus EarnKit's own signals to one method:
  - signals: verified site, counted Base contract, hosted starter, live no-code tool
  - methods: `stripe_checkout`, `stripe_link`, `x402`, `base_pay` or none
- **The ask.** A one-time ask of kind `payments` carries the method. The yes path follows v4.3's Builder Codes yes: one line with the guide, then an agent note.

**Tech Stack:** Next.js 16, TypeScript, Postgres, node:test via tsx. No new reads: the files are already fetched in discovery.

**Spec:** the owner-approved scope (2026-10-30):
- Builders choose a "payment mechanism based on what suits their product".
- This ships as its own release, after v4.6.

## The picker (`pickPayment`)

| Product (first match wins) | Method | Guide constant |
|---|---|---|
| Already has a payment dependency (`stripe`, `@stripe/*`, `x402*`, `@coinbase/x402`, `@base-org/account` with `pay`, `@lemonsqueezy/*`, `@paddle/*`, `@polar-sh/*`; Python `stripe`, `x402`) | none | none |
| MCP server or API: `@modelcontextprotocol/sdk` or Python `mcp`; or an HTTP server (`express`, `hono`, `fastify`, `koa`; Python `fastapi`, `flask`) with no web framework | `x402` | `X402_GUIDE` |
| Onchain app: a counted Base contract (`contractsOf`) | `base_pay` | `BASE_PAY_GUIDE` |
| Web app with a server: `next`, `@remix-run/*`, `@sveltejs/kit`, `nuxt`, `astro` with an adapter, or a web framework plus an HTTP server | `stripe_checkout` | `STRIPE_CHECKOUT_GUIDE` |
| Site with no server: `vite` / `react` only, a hosted EarnKit starter, a live no-code tool (`v.liveTool`), or a verified site with no `package.json` | `stripe_link` | `STRIPE_LINK_GUIDE` |
| Package, library or CLI only (npm/pypi source, no site) | none | none |

**Why each method fits:**
- `x402`: agents and scripts pay per request in USDC on Base, with no accounts or checkout page.
- `base_pay`: payments stay onchain, in the place the builder already works.
- `stripe_checkout`: subscriptions and one-off payments for products where users sign in, and v4.6 can verify them.
- `stripe_link`: a payment button with no code on the server.
- Libraries are never asked, because charging for one rarely fits and the ask would be noise.

**Guide constants:** `payments.ts` holds the guide URLs. Task 2 Step 3 checks each against the provider's current docs, then pins it. The starting points:
- `docs.stripe.com/checkout/quickstart`
- `docs.stripe.com/payment-links`
- `docs.cdp.coinbase.com/x402`
- `docs.base.org/base-account/guides/accept-payments`

## Exact copy

- **Lead line:** `{N} people used {name} in the last 30 days, and there's no way to pay yet.`
  - Shown only when `usedBy` shows (v4.5 rules: at or above `USED_MIN`, fresh).
  - Otherwise there is no lead line.
- **Then by method:**
  - `stripe_checkout`: `Want me to add Stripe checkout to {name}, so people can pay for it?`
  - `stripe_link`:
    - Line 1: `{name} can take payments with a Stripe payment link, no server code needed.`
    - Line 2: `Want me to add one?`
  - `x402`:
    - Line 1: `{name} can charge per request in USDC on Base with x402, so agents can pay without an account.`
    - Line 2: `Want me to add it?`
  - `base_pay`:
    - Line 1: `{name} can take USDC payments on Base with Base Pay.`
    - Line 2: `Want me to add it?`
- **Yes reply:** `Adding {method label} to {name}. Guide: https://{guide}`. It contains no question.
  - Method labels: `Stripe checkout`, `a Stripe payment link`, `x402`, `Base Pay`.
- **Agent note (`PAYMENTS_NOTE(method, wallet)`)** tells the agent to:
  1. Add it in this repo following the guide, and start in test mode (Stripe test keys, or Base Sepolia for x402 and Base Pay).
  2. Never ask for a secret in chat, and name the env var the builder sets themselves.
  3. For x402 and Base Pay, pay to `{wallet}` (their proven wallet) and confirm it with them first. If there is no proven wallet, ask which address they want paid.
  4. If the code shows the product is a different kind than this method suits, use the picker table's method instead and say so in one line.
  5. Show the change, and don't ask about payments again.
  6. If the method is Stripe: once it's live, mention that EarnKit can verify the revenue for grant drafts with `tell {stripe: 'connect'}` (v4.6).

## Rules

- **Who gets the ask (kind `payments`):** ranked builders whose main project has all of these:
  - a method from `pickPayment`
  - no revenue of any kind (no fresh `latestRevenue`, no `stripe_connections` row)
  - not `declined['payments']`
  - not asked before (`seen.payments_asked`)
- **Placement:** in `stateAsk`, after `qualify` and before `ship`, under the same `quiet && !more` gates. Money first: grants and applications always win the slot.
- **Answers:**
  - A yes writes `seen.payments_asked` and returns the yes reply with the note.
  - A no writes `declined['payments']`.
  - Either way it is never asked again.
- **Stack signals:**
  - Stored in `github_repo_facts.product.stack`, cached per `pushed_at`.
  - A repo read before v4.8 has no `stack`, and gets no ask until its next push or read.
  - Not guessing is the safe default.

## Review Focus

1. A repo that already depends on `stripe` (or any listed payments package) never gets the ask, including the Python `stripe` package.
2. A library or CLI with no site never gets the ask.
3. The yes reply and note never request a key in chat. For x402 and Base Pay the note names the proven wallet. With no proven wallet, it says to ask the builder.
4. A builder with fresh v4.5 onchain revenue or a Stripe connection never gets the ask.
5. The ask never displaces `apply`, `qualify` or the wallet and token setup steps. It shows only when nothing ahead of it fires.

## Parked (owner decision)

**x402 and Base Pay revenue isn't counted yet.**
- v4.5 counts only money paid into the builder's contracts. Payments to a wallet aren't counted.
- Counting them safely means a dedicated payments address, proven by signature, with v4.5's payer exclusions.
- That is a candidate v4.9.
