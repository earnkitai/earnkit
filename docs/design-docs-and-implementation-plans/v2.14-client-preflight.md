# v2.14 client preflight: X sign-in during connector OAuth

Goal: confirm each target client completes a browser sign-in during connector OAuth, and design the one fallback for a client that can't.
Status key: "docs" = read from public docs on 2026-10-18; "needs a human" = cannot be checked without running the client.

## Timeouts and spec points (docs)

- No client documents a timeout for the interactive part of authorize (our page, the trip to X and back). Whether one exists needs a human (check 1).
- Claude documents 10 seconds for the discovery, registration and token endpoints (30 for refresh), so the token exchange must stay fast (T4 binds in one transaction).
- MCP spec 2025-11-25 leaves the authorization server's user interaction out of scope (a third-party IdP in between is allowed), requires exact redirect matching and PKCE S256, and says the consent screen must show the redirect host when CIMD is used (A4's interstitial does this for unknown hosts).

## What our server needs

- Accept every redirect form above. Today's `isAllowedRedirectUri` already does (https, loopback http, custom schemes). Test 1.1 in `apps/frontend/lib/earnkit/oauth.test.ts` pins the eight documented URIs so T4 can't refuse a real client.
- Keep the pending authorize request server side, keyed by our own X state (T4 `x_signins`).
- A `SameSite=Lax` cookie (X's return is a top-level GET).
- A 15-minute window.
- `iss` in the authorization response (A22).

## Redirect URIs T4's `redirectClass` classifies

The warning page ("You're connecting EarnKit to <host>. Only continue if you started this from your own agent.") is skipped only for (ruling S6, refined by the controller on 2026-10-19):

- the three exact documented callback URIs below (`redirectClass` gives `agent_host`; the registered string must equal one of them exactly, so no other path, query, port or subdomain matches);
- loopback redirects `http://localhost:<port>/...`, `http://127.0.0.1:<port>/...`, `http://[::1]:<port>/...`, any port (`loopback`): the code lands on the builder's own machine;
- known agent app schemes only (`oauth.ts AGENT_APP_SCHEMES`: `cursor`, `vscode`, `vscode-insiders`, `windsurf`, `claude`; `app`), such as `cursor://anysphere.cursor-mcp/...`: the code lands in that app on the builder's own machine. Fix round 1: every other non-http(s) scheme (browser trampolines such as `microsoft-edge:`, `x-safari-https:`, `googlechrome(s):`, `firefox:`, `opera*`, `web+*`, `intent:`, or anything unknown) is `other`, because it can reopen an attacker's https page with the code.

Exact documented callbacks (`oauth.ts AGENT_REDIRECT_URIS`):
- `https://claude.ai/api/mcp/auth_callback`
- `https://www.cursor.com/agents/mcp/oauth/callback`
- `https://chatgpt.com/connector_platform_oauth_redirect`

Every other redirect gets the warning page (`other`), which names the host with its port and shows the full registered redirect URI (escaped), including any subdomain or other path on those hosts (`https://cursor.com/...`, `https://forum.cursor.com/...`, `https://platform.openai.com/...`) and `https://chatgpt.com/connector/oauth/<callback_id>` (a per-connection path; whether ChatGPT ties it to the signer's session is not documented: check 6 below).

Clients serving many builders (`servesMany`: a hosted bot's name, or a redirect host under grok.com, x.ai, x.com or meta.ai) never see X at all: they keep the anonymous approval (A1).

## What can't be verified without a human (runbook section 0, copied by T11)

Run once, when T4 is on a preview or production.

1. Full X round trip in each of the five clients, including one where the person waits 2 minutes on X before approving.
   - Do: add the connector, start the sign-in, sign in on X, wait 2 minutes on the X approval screen, then approve.
   - You should see: the client returns to its own chat with the connector connected.
   - If not: note the client and the error. A hidden timeout or state expiry in the client means that client uses the fallback below.
2. Whether Claude Desktop and Cursor open the system browser or an embedded window.
   - Do: start the sign-in in each and see where X opens.
   - You should see: the system browser, already signed in to X.
   - If not (embedded window): the person types their X password once. Record it; no code change.
3. Whether ChatGPT's DCR registration is per user or per workspace, and whether Plus can add a custom MCP server at all.
   - Do: add the connector from two users in one workspace; try on a Plus account.
   - You should see: a separate client id per user; Plus either adds it or shows no option.
   - If a workspace shares one client id: treat ChatGPT as a shared client (no person binding). If Plus can't add one: drop Plus from the supported list.
4. Whether claude.ai shows a reconnect prompt for a 401.
   - Do: revoke a token on our side, then use the connector in claude.ai.
   - You should see: a reconnect prompt. (We issue no refresh tokens and tokens don't expire, so this only matters if a token is revoked.)
   - If not: the person must remove and re-add the connector; note it in the docs.
5. That each client lands back on its own chat with the connector shown as connected, and that the first reply shows the page link.
   - Do: finish sign-in in each client, then send any message.
   - You should see: connected, and a first reply with one link to the person's page.
   - If not: use the fallback for that client and file the client's behaviour.
6. Which callback ChatGPT registers, and whether its dynamic callback is tied to the signer's session (ruling S6).
   - Do: add the connector in ChatGPT and read the `redirect_uris` in its registration (server log of the register call shows only the host; read it from the warning page or the authorize URL).
   - You should see: `https://chatgpt.com/connector_platform_oauth_redirect` (we return `iss` and advertise `authorization_response_iss_parameter_supported`), so sign-in goes straight to X.
   - If ChatGPT registers `https://chatgpt.com/connector/oauth/<callback_id>`: the builder sees the warning page once before X. Keep it unless ChatGPT documents that this callback only finishes in the session that started it; then add that rule to `redirectClass` with a test.

## The fallback

For a client that can't finish a browser step, and for installations from before v2.14. Built in T5.

- The first reply's stand line is "You're not on the Bench yet." and its question is "Sign in with X to get your page (one click): <link>" then "Want me to put your work on the Bench once you're in?" (the link is the reply's one link).
- The link is `https://earnkit.com/signin/<code>`: 16 random bytes, only its sha256 kept, valid 24 hours, one per installation at a time (an open one is shown again).
- The page names the agent as what the agent says about itself: "an agent that calls itself <name>, connected 3 minutes ago." It never presents that name as verified (ruling S2).
- The page warns plainly: "Anyone who holds the code you get next can act as your page. Only continue if your own agent gave you this link." Then one "Continue with X" link. The X state is bound to this browser's cookie, as at install.
- After X the page says "Signed in as @handle." and "Paste this code to your agent: ABCD-EFGH-JKMN" (12 characters, 15 minutes, one use). The agent sends `find { sign_in_code }`; only the installation that minted the link can use it.
- Then the installation is bound exactly as an X-signed token is (T4 `attachToX`).
- If the X account already has a page, the installation attaches alone and its old data is never merged (ruling A7 superseded).
