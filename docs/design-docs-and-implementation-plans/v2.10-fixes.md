# v2.10: One thing per reply

Status: implemented on branch v2.10 (2026-10-10); plan: v2.10-fixes-plan.md.

Approved (owner, 2026-10-09). Builds on v2.9 (main e50ca1c).

Source: the owner's own v2.9 test run. It found repeated pitching, blindness to private repos, weak matches ranked as fits, and sloppy descriptions and logos. Goals stay in order: installs, then token launches. EarnKit has one user (the owner) and isn't launched, so each fix is the smallest one that works.

Paths are relative to `apps/frontend/lib/earnkit/`. Exceptions: `app/` is under `apps/frontend/`; `programs/` is at the repo root.

## Owner decisions (binding)

- **Token pitch:** once, at confirm, as one line inside the single yes. This reverses v2.9 B10. No WETH, gas or terms lines in replies.
- **Deploy gas:** EarnKit may deploy the builder's contract from its own deployer (cents), with the builder as owner. Arc and Base only, capped. No money ever goes to the builder's wallet. Wallet top-ups stay banned.
- **Reminders:** weekly email only. Deadlines show inside agent replies.
- **Copy:** no addresses, hashes or stat dumps in description fields. Token logos never use the text tile.
- **Cost:** flat or near zero, plus the approved cents of deploy gas. Free tiers, hard caps in code, no new cron or service.
- **Carried from v2.9:** builder 40%; only the token is skippable; the owner is the only decider.

## Changes

### A. Reply shape

1. **One plain bonus line.** Today the bonus is said in up to four forms: `bonusClose` ("Every entry gets a token that pays you, and its fees fund the builder bonus. 0.60 ETH so far."), `bonusCell` ("new pool"), the guide's `Builder bonus: <cell> · <board link>` (`guide.ts` guideText) and Also qualifies' `bonusRidesOn` + `BONUS_MOVES` (`entry-text.ts`).
   - One pure `bonusLine(pool)` in `present.ts` replaces them. With no tokens yet in the round: "Builder bonus: no tokens yet, so yours would be first". With some: "Builder bonus: 0.18 ETH so far" ("under 0.01 ETH so far" below 0.01).
   - At most once per reply. The board link stays on the guide page and the site, not in replies. Also qualifies loses both bonus sentences.
   - Needs a count of tokens in the open round next to `roundPoolsWei` (same grouped read, one more column).
2. **One thing per reply** (first reply, `presentFirstMessage`). The first reply is one lead line plus one question: "Your tipjar can win 500 USDC on Arc by Oct 14. Want me to finish it?"
   - The lead is the top row by the item 6 rank. The prize uses the program's own unit (`prizeOf`), and "by" uses `formatDeadline`'s short form.
   - Everything else (the matched table, Also open, ideas, sponsored, updates) moves behind "show more" (`find` with `more: true`). It renders today's tables unchanged.
   - A returning builder's news, entries and deadline line (item 14) come first, one line each, then the lead.
   - With no fit: "No repo fits yet. $1.1M+ is open; want the 3 easiest?" (`openMoneyUsd`).
3. **Guide after the pick, server-driven.** Today `get_program` returns `guide.text` with `GUIDE_NOTE` ("show it when the builder asks"), so the agent decides. In v2.10, the first `prepare` reply for a program prepends `guideText` to `show_to_builder`: what won, what the program wants, best bet. The coach questions follow.
   - "First" means the program wasn't in `installations.working_on` before this call: `setWorkingOn` returns whether it added the program.
   - The guide shows only sourced parts. Without `past_rounds` or `focus`, it shows the top 2 `rules` as "What it wants".
   - `GUIDE_NOTE` goes.
4. **Fold the 8 tools into 4** (`mcp.ts`, `tools.ts`). `sponsor_campaign` is unchanged: dormant and registered only when escrow is configured.

   | New | Absorbs | Notes |
   |---|---|---|
   | `find` | `list_programs`, `get_program` | `program_id` returns the program and its guide in `show_to_builder`; `repo` keeps the eligibility check; `more` shows the full tables |
   | `prepare` | `prepare_submission` | plus `host` (v2.9) and `deploy` (item 12) |
   | `confirm` | `confirm_entry`, `launch_token`, `record_submission`'s entry write | `yes` records the entry and launches the token; `check` polls a pending launch |
   | `tell` | `tell_earnkit`, `pick_up_entries`, `record_submission`'s "I submitted" | `submitted: { program_id, external_submission_url? }`, `pickup: <code>`, statuses and repo facts as today |

   - Handlers are reused, not rewritten. Each new tool dispatches to today's functions.
   - `SERVER_INSTRUCTIONS` and the descriptions are rewritten for 4 tools, under 800 characters each.
   - **Aliases:** `app/mcp/route.ts` maps an old tool name in a `tools/call` body to the new tool and its arguments, for 30 days, and logs each use. Old names never appear in `tools/list`. Decision: cheap (one map, no extra registrations), so it's kept.
   - Decision: `record_submission` splits by meaning. The entry write moves to `confirm` and the later "I submitted, here's my link" moves to `tell`, so "Yes submits your entry" is literally true.

### B. Token at confirm

5. **One yes, pitched once.**
   - Remove the first-reply offer: `firstTokenOffer`, `tokenOffer`, `tokenOfferAgain`, `TOKEN_OFFER_NOTE` and the `token_offer` field (`tools.ts` around line 1280; `present.ts` B10 block). Also remove `TOKEN_LINE`/`TOKEN_LINE_NO_BONUS`.
   - `confirmOffer` (`confirm.ts`) becomes one line: "Yes submits your entry and launches $TIP (Tip Jar): 40% of its fees to you, plus the builder bonus. yes / skip the token". Without a bonus program, it drops ", plus the builder bonus".
   - The wallet is asked in that line only when none is known ("Say yes with your wallet address"). A remembered wallet is shown short on non-shared clients only (v2.9 G13).
   - These go from replies: `COIN_FOOTNOTE`, `tokenFootnote`, `EARNINGS_LINE`'s "paid in WETH ... tokens.fun pays the gas", "Want the builder bonus? It comes with a token." and `SKIP_LINE`.
   - The terms stay on tokens.fun and are added to the entry page `app/p/[id]` (TOKEN_TERMS, one footer line). They are no longer in any reply.

   - Decision: "skip the token" is the only skip word, keeping v2.9's rule that only the token is skippable.

### C. Matching

6. **Traction scoring.** Today `productScore` (`match.ts`) counts 6 yes/no signals. A starter-like repo with a homepage, a README and a push this week reaches "product". Nothing measures use.
   - Add 3 measured signals to `RepoFacts`:
     - `tx_count`: total transactions to the repo's contracts that passed `eth_getCode`, from Blockscout's free `GET /api/v2/addresses/<addr>/counters`.
     - `commits_90d`: commits by any author in 90 days, from one `/commits?since=<90d>&per_page=100` read that replaces `builderActive`'s read (item 8).
     - `live_ok`: the link probe passed with no error text (item 13).
   - `traction = 3·band(tx_count: 0, 1-49, 50+) + 2·live_ok + 1·band(commits_90d: 0, 1-9, 10+)`, from 0 to 9.
   - Odds per row:
     - **good odds**: product tier and traction 4 or more.
     - **low odds**: otherwise. Shown only behind "show more", labelled "low odds: <reason>" (for example "no users yet").
     - A low-odds row is never the lead, never called a fit, never alerted, and never in "$X you qualify for".
   - The rank is good odds first, then traction, then row difficulty, then prize. A starter tip jar (traction 0 to 3) can't outrank a live product with users.
   - **Starters:** a repo whose README's first heading or `package.json` name matches an EarnKit chain-kit example (`earnkitai/chain-kits`, list in `earnkit-orgs.ts`) loses `original`.
   - **Budget:** Blockscout counters are read only for contracts with code: at most 2 per `find`, 1 per entry step, cached 24 h. The commit read reuses the existing slot, so there are no new GitHub calls.
   - `url_checks` gains a nullable `n integer` (key `txcount:<chain>:<addr>`).
   - Decision: only Base has a known free Blockscout. On other chains, `tx_count` is unknown, which scores as 0 but is never named as missing. Live traffic isn't measured: there's no free source for third-party sites.
   - The cached `product` jsonb gains `traction` and `odds`. `match_shown` logs `traction` for the v2.9 A8 floor.
7. **Private repos.** Verified cause: in `matchProjects` (`match-projects.ts`), a named repo is read with `Promise.all(names.map(repoByName))`. One private repo's 404 rejects the whole read. `list_programs` then shows only "Couldn't read your repos: GitHub: /repos/x not found (or private)", and the agent's `local_repos` view of that same repo is thrown away too.
   - **Per-repo reads:** each repo read is caught on its own. A 404 for a repo that `local_repos` also names scores it from the local view (`checkLocal`), with one line: "TipJar is private, so I matched it from your local copy."
   - A 404 with no local view is never dropped silently: "I can't see TipJar (private?). Allow read access: <link>" (final fix M5: declarative, so the reply keeps one question; it was "Describe it, or allow read access"). The link appears only when item 7b is on.
   - The agent instruction becomes "for private repos, report local_repos facts: name, chains, contracts, live link, last commit".
   - **7b. Read-only GitHub App (optional, free, off until set).**
     - A GitHub App with Contents: read and Metadata: read and nothing else, installed by the builder on selected repos. Env: `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_APP_PRIVATE_KEY`; all three are needed or the App is off.
     - Install link: `github.com/apps/<slug>/installations/new`, with the v2.9 sign-in nonce as `state` (bound to entry and repo, single-use, 15 min). The setup callback reuses `app/github/verify`.
     - Proof: the builder's v2.9 GitHub sign-in login equals the installation's account, or the repo read returns `admin` for that login. The installation lists the repo. It's stored in `github_verifications` with `via = 'app'`. `token-gate.ts` and `repoCodeFacts` read through a 1-hour installation token, minted per call and never stored.
     - Private repos get full scoring (tree, README, config files, commits). EarnKit caches facts only, never code.
     - Privacy rules:
       - A private repo's name and URL never appear on public pages. The bonus board and the entry page show the project name only.
       - tokens.fun gets the live link as `website`, never the repo URL.
       - The wallet binding is unchanged (v2.9 G11).

8. **"No commits in 90 days" on a fresh push.** Verified cause: `builderActive` (`match-projects.ts`) asks `/commits?author=<login>&since=<90d>`. GitHub matches `author` only for commits whose email is linked to that account, so commits made with a local email that isn't on the account return nothing. The result is `false`, not `null`, so the `pushed_at` fallback never runs. `since` also filters by commit date, so imported history with old dates misses too.
   - Fix: on an owned repo, `active` is any commit by any author in 90 days (the item 6 read) or `pushed_at` within 90 days.
   - The author-matched read stays only for repos owned by someone else (the v2.9 A1 contribution rule).
9. **Chain credit needs a deployment.** Verified cause: `detectChains` (`match.ts`) marks a mainnet from any `viem/chains` or `wagmi/chains` import, any RPC or explorer host, or a chain id in `package.json`, `.env.example` or constants files. A wagmi template that imports `base` counts as built for Base.
   - `Detection` gains `basis: 'deployed' | 'deploy_config' | 'mention'`. Only these credit a chain:
     - **deployed:** `eth_getCode` passes on that chain (v2.9 A5).
     - **deploy_config:** a network entry in `hardhat.config.*` with the chain's id or RPC; `[rpc_endpoints]` in `foundry.toml`; `broadcast/*/<chainId>/`; `ignition/deployments/chain-<id>/`; or `deployments/<network>/`. Folder hits come from the tree that's already read, so they're free.
   - A mention gives no fit. The row is at most `after_step` with "deploy to Base first" (effort: hours) and is low odds.
   - Agent-reported mainnets stay claims (v2.9 A3).
10. **Avalanche Team1 Mini Grants re-rated.** `programs/avalanche-team1-mini-grants.json` has `difficulty_override: { level: Easy, rated_by: earnkit }` but no `past_rounds`, `focus` or odds. Its own rules say high volume doesn't guarantee funding, and it pays up to $10,000.
    - Remove the Easy rating, as v2.9 did for Base. It becomes Medium at program level, and Hard on rows missing real users (`rowDifficulty`).
    - `programs:check` gains a rule: an EarnKit Easy rating needs a program at or under $1,000 per winner, or sourced odds.

### D. Copy quality

11. **Plain description fields.** Today `preSubmitCheck` (`coach.ts`) checks numbers, dates, links and length, never content. Agents paste addresses and stat dumps.
    - A pure `plainProblem(text, kind)` flags any of: an address (`0x` + 40 hex), a hash (`0x` + 64 hex), a hex run of 16 or more, 4 or more numbers in one sentence, `key: value` lists, or a URL in a non-link field.
    - It applies to `name`, `one_liner`, `problem`, `solution` and `how_it_works`. `how_it_works` keeps its one proof link but no raw address.
    - Length follows the form's `max_chars`, else `limit_words`.
    - A hit is an agent fix ("One-sentence description: rewrite in plain words, no addresses or numbers lists"). `confirm` refuses `yes` until it's fixed, with `agent_note` only. The builder never sees it.
    - The same check runs on the token description sent to tokens.fun (`tokens.ts`). It's capped at 280 characters. On a hit it falls back to the cleaned one-liner, else "<Name> on Base".
12. **Token logo.** Today `deployToken` (`tokens.ts`) sends the agent's upload, else the `token-image` route: a next/og text monogram, which is the text tile. tokens.fun accepts `tokenURI` and `imageUrl` as `https://` or `ipfs://` URLs (`app/api/v1/deploy/route.ts` line 309). The image goes onchain at deploy (`image: body.imageUrl || body.tokenURI`, line 611), so it can't change later.
    - Order:
      - the agent's upload;
      - the live site's `apple-touch-icon`, else its largest PNG/JPEG/WebP `<link rel=icon>` of 128 px or more, else `og:image`;
      - the repo's custom social preview (GraphQL `usesCustomOpenGraphImage`, one call, only when true; through the App for private repos);
      - a generated mark.
    - The page is fetched with `safeFetchText` (512 KB). The image is fetched once (1 MB, byte-checked by `decodeImage`, no SVG) and stored in `projects.token_image`, so the URL EarnKit gives tokens.fun is stable: `/api/projects/<id>/image`.
    - The generated mark replaces the monogram: a geometric shape and gradient from the project id, with no letters. `token-image` stays only for old links.

### E. Contract deploys

13. **EarnKit deploys the builder's contract** (`prepare` with `deploy`, new `deploy.ts`). It's off until `DEPLOYER_PRIVATE_KEY` is set.
    - **What's allowed:**
      - Only the builder's own compiled artifact, from a repo that passes ownership (proof line, v2.9 sign-in or the App): `{ chain: 'arc' | 'base', bytecode, abi, constructor_args }`.
      - Size limits: initcode of 48 KB or less (EIP-3860), and deployed code of 24 KB or less (EIP-170), checked after the deploy.
      - `value` is always 0. No call after the deploy except `transferOwnership(builder)`.
      - Refused: bytecode exposing all of the ERC-20 `transfer`, `approve` and `totalSupply` selectors (no tokens from EarnKit's deployer), and any constructor marked `payable`.
    - **Owner:** if the ABI has `owner()`, it must return the builder's wallet after the deploy, else EarnKit calls `transferOwnership(builder)` once. If it still isn't the builder, the address is reported and flagged for the owner. A contract with no owner concept is fine, since the deployer holds no rights.
    - **Key handling:**
      - A new hot key on Railway, separate from `CAMPAIGN_PAYOUT_PRIVATE_KEY` and every escrow key. The feature refuses to start if the derived address equals any of them.
      - Its balance is held at about $5 per chain: ETH on Base, USDC (Arc's gas token) on Arc. The owner tops it up by hand.
      - A balance under one deploy's cost adds a `TOP_UP` line to `needs_owner` (the v2.9 D17 path).
      - The key never signs anything but these deploys and `transferOwnership`.
    - **Limits** (`free-tier.ts` counters plus `rate-limit.ts`):
      - 1 deploy per builder per chain per day, keyed by verified GitHub login, else repo key;
      - 3 per builder per 30 days;
      - 20 per day in total;
      - an estimated fee over $0.25 is refused ("Deploy costs are high right now; try tomorrow").
    - **Cost ceiling:** $10 a month in total, enforced by a month counter of the gas units spent from receipts. A hard stop at the ceiling says "Deploys are paused until next month". This is within the approved cents.
    - The deployed address goes straight into the v2.9 A5 check (cached pass), so it counts as `deployed`. It doesn't count as users.
    - Builder sees: "TipJar is deployed on Arc: 0x12ab…9f3e. You're the owner." The address appears only in this one line, never in a description field.
    - Decision: the agent compiles; EarnKit never builds code. Explorer source verification stays the agent's job.

### F. Checks and reminders

14. **Error pages that load.** Verified cause: `safeFetchText` in probe mode (`safe-fetch.ts` line 296) returns at a 2xx status without reading the body, so a page showing "404: NOT_FOUND" or "Application error" passes.
    - The probe reads up to 64 KB, strips `<script>` and `<style>`, and checks `<title>` and visible text against a short list:
      - `404`, `not found`, `NOT_FOUND`, `DEPLOYMENT_NOT_FOUND`;
      - "There isn't a GitHub Pages site here";
      - "Application failed to respond";
      - "Internal Server Error", "Bad Gateway", "Cannot GET /", "Site not found";
      - "This page could not be found".
    - The list is checked only when the visible text is under 5 KB, so a real page that mentions "404" passes.
    - A hit is cached as a failure with the matched text: "Your live link loads but shows an error ("This page could not be found"). Fix it and tell me."
    - There's no JS execution, so an error drawn by client JS isn't caught. That's stated once in the architecture guide.
15. **Deadlines in replies.** One line, first in any reply on a non-shared client (or for a signed-in login on a shared one): "Arc closes in 2 days; your entry isn't submitted."
    - It covers the soonest unsubmitted entry closing within 3 days. Only one line, and only once per entry per day (`installations.deadline_shown jsonb`).
    - It uses the entries read `withAlerts` already does, so there's no new query on the hot path.
    - The weekly email is unchanged, and there are no new emails.

  - every reply has at most one bonus line, matching "Builder bonus: no tokens yet, so yours would be first" or "Builder bonus: N ETH so far";

  - with the App on, a private repo launches; a private repo's name never appears on `/bonus` or `/p`;
  - a repo with commits by an unlinked email, pushed today, is `active`;
  - a `viem/chains` `base` import alone credits no chain; a `broadcast/*/8453/` folder does; a passing getCode does;
