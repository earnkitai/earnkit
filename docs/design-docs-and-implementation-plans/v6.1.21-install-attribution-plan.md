# v6.1.21: install attribution (people)

## Problem

`/api/stats` `installs` is `count(*) FROM installations`. The owner's people tracker reads the Postgres view
`owner_people` (role `earnkit_ro`), which v3.1/v4 defined over `builder_profiles`, written by v4's `ensureProfile` at X
sign-in. The v5 cut deleted that code and the view's definition, but left the legacy tables and the view in the
database, so nothing writes `builder_profiles` any more and the tracker stopped at 26 people (none after Oct 24). In v6
authorize is anonymous; a person (`builders`) exists only if the builder opens a link code and signs in with GitHub.
There is also no flag for the owner's, the CTO bot's and the journey campaign's installs.

## Design

- `people` (one row per person) and `installations.person_id`. Every install makes a person in the same transaction
  (`saveInstallation` -> `ensurePerson`). Linking (`linkInstallation` -> `linkPerson`) joins the installation to the
  builder's person (carrying a test reason), or makes the installation's person the builder's. Unlink leaves
  `person_id`; `deleteBuilder` sets `people.builder_id` NULL. The app never deletes a people row (the repro cleanups remove the ones they made).
- `testReasonFor` (`lib/v6/people.ts`, pure): `test_reason` NULL is real; else owner, dogfood, persona, repro or test.
  Sources: `EARNKIT_OWNER_LOGINS`, `EARNKIT_DOGFOOD_LOGINS`, `EARNKIT_TEST_INSTALLATIONS` (all optional; the logins
  match proven identities only, a builder's GitHub login or a legacy X sign-in, never a claimed repo owner), then the
  client name: a lane prefix `l<n>-` is repro; `persona`, `journey`, `dogfood`, `repro`, `test` count only as a whole
  word between dashes, underscores, spaces or the ends, in a name that has a separator (`Personal Assistant`,
  `my-personal-agent`, a bare `Journey` are real). Applied at install (name, id) and at link (login, id). Only env-list
  reasons reach a builder's person at link; a client-name reason stays on the installation's old person. Nothing
  automatic clears a reason.
- Proven identity at install (`EARNKIT_INSTALL_SIGNIN=github`) is built but disabled in this release
  (`INSTALL_SIGNIN_ENABLED = false`): it has no EarnKit consent step, so a builder who had authorized the GitHub app
  before could be linked to an attacker's client in one click (review C1). The value is read and logged
  (`install sign-in is disabled in this release`); authorize stays anonymous whatever it is, and an install state at
  the callback gets the install failure text and no code. The code is kept: authorize validates as before, sets a
  `__Host-ek_install` nonce cookie and goes to GitHub with a signed state of kind `install` (own MAC label,
  `k: 'install'`, the pending request, 15 minutes); the callback checks the nonce, exchanges the GitHub code,
  `upsertBuilder`, and `issueCode` with the builder in the signed code (`b`); `installOnce` links in the same
  transaction that spends the nonce. A failure is the plain install failure text, never /link/failed. A link state
  never verifies as an install state or the reverse. Turning it on waits for a consent page (`Connect {client}
  ({redirect host}) to @{login}?`, a POST with a CSRF token tied to the nonce).
- `owner_people` is recreated over `people`, keeping the tracker's column names; see the architecture guide.
- `/api/stats` appends `installs_real`, `people`, `people_real`.
- `scripts/people-backfill.mts` (`lib/v6/people-backfill.ts`): dry run (READ ONLY transaction, rolled back) or
  `--apply` (one transaction, idempotent) gives each installation without a person one, from its builder, the legacy
  `builder_profiles` row keyed by the installation id (when the table exists; only existing columns), the owner of its
  last GitHub repo (claimed, unproven) or nothing (with the reason). `--reflag [--apply]` re-evaluates every person's
  reason (never clears; only a stronger one replaces it: owner over dogfood over test, persona, repro); `--unflag
  <b:id | i:id | p:id> [--apply]` clears one by hand (source `unflagged`, never flagged again automatically). The
  script reads the env lists from its own shell, never Railway's.

## Owner steps

1. Deploy (migrate adds `people`, `installations.person_id`, recreates `owner_people`). Before merge, check nothing
   else depends on the legacy `owner_people` view and that the migrate role owns it (review M1).
2. Export `EARNKIT_OWNER_LOGINS`, `EARNKIT_DOGFOOD_LOGINS` and `EARNKIT_TEST_INSTALLATIONS` in the shell, then run the
   backfill dry run, read it, and `--apply`; then `--reflag` (dry run, then `--apply`).
3. Optionally set the same three lists in Railway, so new installs and links are flagged too.
4. Leave `EARNKIT_INSTALL_SIGNIN` unset: the install sign-in waits for a consent step.

## Limits

- The legacy group root `COALESCE(old builder_id, id)`: `installations.builder_id` now holds the v6 builder, so the old
  v4 root id of a non-root installation is not recoverable; the backfill matches a profile by the installation's own id.
- `programs_accepted` is NULL (EarnKit has no accepted status). Every old-only column (wallet, points, referrals, streak,
  commit weeks, coin, score, check-in, email opt-in) is a typed NULL, never 0 or false: missing data reads as unavailable.
- Installations created by raw SQL (no `saveInstallation`) have no person until the backfill runs.
