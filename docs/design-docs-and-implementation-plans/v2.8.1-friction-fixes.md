# v2.8.1: Friction fixes

Status: approved (owner, 2026-10-08). Builds on v2.8 (`main` 4ccf437).

Source: two audits run 2026-10-08, a simulation of 10 builder journeys and a failure-mode review. Goals, in order: installs, then token launch.

## Owner decisions

- **Default tab:** Grok Bot stays the default install tab.
- **Launch limits are set for EarnKit.** tokens.fun's rules change for launches made with EarnKit's deploy key; EarnKit does not shrink to fit tokens.fun.
- **The builder bonus continues after a program ends** (option B). When a round ends, a token's fees go to the repo's next open entry, not to the Safe.
- **Shared hosted installs:** decided by EarnKit (see item 17).

## Fixes

### A. Token launch

1. **Stuck launches.**
   - When tokens.fun says nothing was minted (any 5xx before broadcast, a 503 for pending transactions, or a revert before deploy), release the repo's launch claim and retry once automatically.
   - Alert the owner if a launch is still pending after 10 minutes.
   - The builder sees "Your token didn't launch yet; say go to try again", never an endless "launching".
2. **Name before launch.** The Yes line shows the ticker and the name: "Yes: launches $TIP (TipJar) on Base. You earn 40% of its trading fees, plus a shot at the builder bonus."
   - Use better fallback names. Never use "XXX2 Token"-style names when a readable variant exists.
3. **Proof line.**
   - Read `earnkit.txt` from the default branch, else from the most recently pushed branch.
   - When the line is missing, say exactly what's missing ("push the line to your default branch") and keep the launch open.
   - Never tell a coding agent to "open this in Claude Code or Cursor".
4. **Launch limits.**
   - **tokens.fun**, for EarnKit-key launches: 10 per wallet per day. Its own website launches keep their current limits.
   - **EarnKit:** 10 per wallet per day. One token per repo still applies.
   - **When a limit hits,** the builder sees when they can retry: "Try again after 14:20 UTC".
5. **Timeouts.** Bound the launch path so that it replies within 50s. If the deploy is still running, return "launching" with a check-back, and let the next call return the result.

### B. First message and discovery

6. **"What can I earn?" never fails on agent input.** Accept any chain string and ignore unknown chains. Accept dates without a timezone. A non-0x wallet is ignored with a note.
7. **Investment programs never lead.** The opening offer is the Easy program with the most money. Speedrun shows only in the table.
8. **No-repo builders.** Rows that need a repo say so ("needs a repo"). The offer prefers programs the builder can enter as they are.
9. **Returning builders.** A short "Your entries" line comes first. Programs already entered are marked "entered" and never offered again.
10. **"$X you qualify for"** excludes programs whose `existing_work` is `new_work_only` when the builder only has existing repos.

### C. Applying, and applying to more programs

11. **The wallet is asked once, in the coach round**, with the other builder-only questions. Confirmation is then a single yes.
12. **Base: no surprise second round.** The Loom demo and the Base Builder Code are asked in the first round.
13. **The bonus note is said once**, in the Also qualifies block, and positively: "Your builder bonus rides on your Arc entry." No "don't add to it", and no repeated "(no builder bonus: …)" notes.
14. **Speedrun kit.** It says the application continues on a16z's site after the email step.
15. **Bugs:**
    - a pre-submit fix that asks for a link in the email answer;
    - deadlines are displayed in the program's local time zone ("Oct 14, 11:59 PM ET");
    - the safety line that makes agents refuse to make a repo public is reworded;
    - unexpected errors are logged on the server with an id, and the agent sees a plain message.

### D. Builder bonus after a program ends (option B)

16. **Round end.** When a token's first program round ends, its later fee deposits book to the earliest still-open round where the same repo has a submitted, complete entry. If there is none, they go to the Safe, as today.
    - Eligibility for that round needs the entry to be complete and submitted, as for every entry.
    - Copy: "Your builder bonus moves to your next entry when a program ends."

### E. Installs and identity

17. **Rate limits keyed by agent client.**
    - Registration and new-installation limits are keyed by OAuth client, not IP: 500 new installs per client per day, and 50 per IP per hour as an abuse floor.
    - **Hosted clients** (Grok Bot, Muse, and any client whose redirect host is a known hosted service) are flagged `shared_client`. For flagged installs:
      - saved answers and contact details are only reused after a yes/no that names them;
      - no answer is filled in silently;
      - the remembered wallet is never suggested.
    - This removes the privacy risk if one registration serves many users.
18. **Reinstall and agent switch.**
    - A builder's identity follows their GitHub user, or their wallet, when given.
    - On a new install that gives the same GitHub user or wallet, earlier entries are linked after a yes/no ("Pick up your 2 earlier entries?"), so the answer bank and entries carry over.

### F. The "40%" figure

19. **It appears once per entry**: in the confirmation Yes line (item 2).
    - Removed from the first message, the reply after launch and the "Entered in…" reply.
    - Policy and docs pages keep it, with "after the launch protocol's share", unchanged.

## Testing

- **Each fix has a regression test.**
- **The journey simulation is re-run** (all 10 journeys plus the agent switch) as a test.
- **Assertions:**
  - "40%" appears exactly once per entry flow;
  - the bonus note appears at most once per reply;
  - no reply over 50s in the mocked slow-deploy case.
- **tokens.fun:** unit tests for the EarnKit-key wallet limit.
