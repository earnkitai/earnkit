# v2.1: Sponsor campaigns (anyone funds, EarnKit takes 10%)

Status: spec, 2026-10-01 (revised: OpenZeppelin parts + an isolated clone per campaign). Approved in
conversation section by section; awaiting review of this file.

## Goal

Anyone can create and fund a builder campaign through their agent. The prize pool sits in an
escrow contract on Base until winners are paid. EarnKit keeps 10% of the pool, earned only when
prizes are paid out.

Success:

- A sponsor launches a funded campaign without talking to the owner.
- Builders can see that the prize is real (in escrow onchain).
- The 10% arrives without anyone chasing it.

Campaign #1 (MINI, EarnKit-funded) stays `closed`; once MINI is allowlisted it can run through
this same escrow later.

## Decisions (owner, 2026-10-01)

| Question | Decision |
|---|---|
| Where the pool sits | Escrow contract on Base; EarnKit never holds funds in a wallet |
| Who picks winners | The sponsor; EarnKit is the fallback 7 days after the end |
| Prize tokens | USDC plus tokens the owner allowlists, each with a per-campaign cap |
| Listing | Live as soon as funding is confirmed (no pre-review); takedown + refund exists |
| Fee timing | Paid to EarnKit only on payout; full refund (fee included) if refunded |
| Judging | Sponsor's own theme and criteria (any of the 5 chains); EarnKit's score guides; picks and reasons are public |
| Contract shape | OpenZeppelin building blocks + about 100 lines of our own: a timelock-owned factory, one isolated escrow clone per campaign, per-token caps (start: USDC $10k) |

## Non-goals (v2.1)

- Partial payouts or multiple award rounds.
- Mobile wallets / WalletConnect (browser wallets only at first).
- New scoring metrics (score stays unique wallets on Base where contracts are given).
- Self-serve token allowlisting (the owner allowlists tokens).
- Pre-review of campaigns before they go live.

## 1. Escrow contracts (Base): OpenZeppelin parts + a small amount of our own code

Foundry project at `contracts/` in the monorepo. OpenZeppelin Contracts v5 is pinned to an exact
version.

There is no upgrade path (no proxy) and no inline assembly. Token transfers are the only external
calls.

### The audited parts we use

| Concern | OpenZeppelin piece |
|---|---|
| Moving tokens safely | `SafeERC20` |
| Reentrancy | `ReentrancyGuard` (factory) and `ReentrancyGuardTransient`, or a simple state lock, on campaigns |
| One isolated escrow per campaign | `Clones` (EIP-1167 minimal proxies; non-upgradeable copies of one implementation) |
| One-time setup of each clone | `Initializable` |
| Admin control | `Ownable2Step` on the factory |
| No instant admin changes | `TimelockController` owns the factory: 48 h minimum delay; owner's wallet is proposer and executor; no admin |
| Emergency stop | `Pausable` on the factory: stops new campaigns only |

Our own code is only the rules: who may award or refund and when, sums, and the fee. That's
roughly 80–100 lines.

### `EarnKitCampaigns` (the factory, one deployment)

**Configuration** (owner = the timelock, so every change is public 48 h ahead):

- `capOf[token]` sets the max amount per campaign; 0 means the token isn't allowed. Changed with
  `setCap(token, cap)`.
- `operator`: EarnKit's key, kept local and never on the server. Used for the fallback award,
  refunds, and takedowns. Changed with `setOperator`.
- `treasury`: where fees go (the owner's wallet). Changed with `setTreasury`.
- `setOperator` and `setTreasury` only affect campaigns created *after* the change: each clone
  snapshots the current `operator` and `treasury` into its own storage at `initialize` time and
  always uses that snapshot, never a live read of the factory. So rotating either one can never
  reach into a campaign that's already funded.
- `pauser`: can `pause()` instantly in an emergency. Only the owner (timelock) can `unpause()`.
- Initial caps, operator, treasury, and pauser are set in the constructor. The deploy script then
  hands ownership to the timelock, so the first setup doesn't wait 48 h.

**`createCampaign(bytes32 ref, address token, uint256 amount, uint64 endsAt) returns (address campaign)`:**

- `whenNotPaused` and `nonReentrant`.
- Requires `0 < amount <= capOf[token]`, `block.timestamp < endsAt <= block.timestamp + 180 days`,
  and that `campaignOf[msg.sender][ref]` is unused. Keying by sender means nobody can squat
  another sponsor's ref.
- Deploys a clone with `Clones.clone(implementation)` (not deterministic, so nobody can pre-send
  tokens to the address). It then calls
  `initialize(msg.sender, token, amount, endsAt, operator, treasury)`, handing in the factory's
  *current* `operator` and `treasury` so the clone can snapshot them.
- Pulls `amount` from the sponsor straight into the clone with `safeTransferFrom`. It requires
  the clone's balance increase to equal `amount`, which rejects fee-on-transfer tokens.
- Emits `CampaignCreated(ref indexed, sponsor indexed, campaign, token, amount, endsAt)`.

`implementation` is an `EarnKitCampaign` deployed by the factory's constructor. The factory holds
no funds and has no function that can move a campaign's funds.

### `EarnKitCampaign` (one clone per campaign, holds only its own pool)

**State** (set once by `initialize`):

- `sponsor`, `token`, `endsAt`.
- `prize = amount - amount / 10` and `fee = amount / 10` (rounded down).
- `state`: one of `Funded`, `Awarded`, or `Refunded`.
- `operator` and `treasury`: a snapshot of the factory's values *at creation time*. Later
  `setOperator`/`setTreasury` calls on the factory never change an existing clone's copy.
- `factory` is an `immutable` set in the implementation's constructor, so every clone shares it
  and only that factory can call `initialize`.

**`award(address[] winners, uint256[] amounts)`:**

- Requires `state == Funded` and `block.timestamp >= endsAt`.
- Caller is the `sponsor`, or this campaign's own (snapshotted) `operator` once
  `block.timestamp >= endsAt + AWARD_GRACE` (7 days).
- 1 to 50 winners, no zero addresses, equal lengths, and `sum(amounts) == prize`.
- Sets `state = Awarded` first (checks-effects-interactions), then pays each winner and sends
  `fee` to this campaign's own (snapshotted) `treasury`.
- Emits `Awarded(winners, amounts, fee)`.

**`refund()`:**

- Requires `state == Funded`.
- Caller is this campaign's own (snapshotted) `operator` at any time (takedown, or "no eligible
  entries"), or the `sponsor` once `block.timestamp >= endsAt + RECLAIM_AFTER` (60 days).
- Sets `state = Refunded`, then sends `prize + fee` to the sponsor.
- Emits `Refunded(by, amount)`.

There are no other state-changing functions and no owner. Tokens sent to a clone by mistake
(outside `createCampaign`) aren't accounted for and stay there. That's documented, not handled.

### Properties the tests and proofs must show

- Each clone's money leaves only two ways: to the listed winners plus the treasury on award
  (exactly `prize` plus `fee`), or to the sponsor on refund (exactly `prize + fee`). Each happens
  at most once.
- The fee is all or nothing: paid in full with an award, refunded in full with a refund. This is
  the approved "paid on payout" rule, since an award always pays the whole prize.
- Neither the factory owner (timelock), the pauser, nor anyone else can move a campaign's funds
  except through those two paths and their time rules.
- Pausing never blocks awards or refunds.
- A bug or a bad token in one campaign can't touch another campaign's pool, because each pool is
  at its own address.

### Known risk the contracts can't stop

A sponsor can award the prize to their own wallets. The leaderboard publicly flags any winner
address that isn't an entry's payout wallet.

## 2. Data model

`programs` gets sponsor campaigns as ordinary rows, so list/get/submit keep working:

- `programs.source text NOT NULL DEFAULT 'file'`: `'file'` (programs/*.json) or `'sponsor'`.
  `programs:sync` only upserts file programs and never touches sponsor rows; it already doesn't
  delete rows.
- A sponsor campaign's program row is created when funding is confirmed, with
  `status = 'active'` and `campaign` set.

New table `sponsor_campaigns`:

| column | notes |
|---|---|
| `ref` text PK | random 32-byte id (`0x` + 64 hex); the same 32 bytes go onchain as the `bytes32 ref` (no hashing) |
| `program_id` text | set when live (`sponsor-<first 16 hex of the ref>`; funding refuses to publish over an existing program id) |
| `installation_id` int | the agent that created it |
| `sponsor_name`, `sponsor_url` text | shown publicly |
| `draft` jsonb | title, theme, criteria, chains, planned winners, starts_at, ends_at |
| `token`, `token_symbol`, `token_decimals`, `amount` | the pool as requested (`amount` is a decimal string in token units, e.g. `"100.5"`) |
| `chain_id` int | 8453 (Base) or 84532 (Base Sepolia) |
| `escrow_address` text, `fund_tx` text, `sponsor_wallet` text | the campaign's clone, from `CampaignCreated` once funded |
| `state` text | `draft`, `live`, `awarded`, `refunded`, `expired`, `taken_down` |
| `award_tx` text, `created_at`, `funded_at`, `awarded_at` | |

`projects` gains `prize_amount text` and `prize_reason text`, set from the award. Existing
`prize_tx` / `prize_paid_at` drive "you won".

Allowlisted tokens are mirrored in code (`lib/earnkit/escrow.ts`: address, symbol, decimals per
chain), so the app can validate before the contract does.

Env: `ESCROW_FACTORY_ADDRESS`, `ESCROW_CHAIN` (`base`, `base-sepolia`, or `local` for anvil with
`ESCROW_LOCAL_TOKEN`; default `base`), plus the existing `BASE_RPC_URL`. The server never has a
private key. Until `ESCROW_FACTORY_ADDRESS` is set and `ESCROW_CHAIN` is valid, sponsor campaigns
are off: the MCP server lists only the 5 builder tools, `/fund` and `/award` return 404, and the
confirm API returns 503 ("Sponsor campaigns aren't open yet"). An invalid value is a readable
config error, never a crash.

## 3. Tool: `sponsor_campaign` (EarnKit's 6th tool, registered only once the escrow is configured)

`action` is one of:

- `create`:
  - **Input:** `sponsor_name`, `sponsor_url?`, `title`, `theme` (what to build), `criteria` (how
    winners are chosen), `chains[]`, `token` (`USDC` or an allowlisted symbol), `amount`,
    `winners` (planned count, 1–50), `starts_at?` (default now), and `ends_at` (3–90 days out).
  - **Validates:** the token is allowed, `amount` is within the cap, the dates, and text lengths
    (title ≤ 80, theme ≤ 1,000, criteria ≤ 1,000).
  - **Stores:** a `draft`.
  - **Returns:** the `fund_url` (`earnkit.com/fund/<ref>`), the raw transactions (approve the
    factory + `createCampaign`)
    for agents that hold the sponsor's wallet, a `show_to_sponsor` summary (title, pool, the split:
    "winners get X; EarnKit's 10% = Y only when prizes are paid; full refund if nobody qualifies",
    planned winners, the deadline, `fund_url`) and a `next_step` (fund it, then `status` with the
    tx). Every `sponsor_campaign` reply uses `show_to_sponsor` (the agent shows it to the sponsor
    as written) and, where there is one, `next_step`; never `show_to_builder`.
- `status` (`ref`):
  - Funding state; if live, entries with scores and time left. `show_to_sponsor` is one line per
    state: draft (deposit link and when the draft expires), live ("<N> entries; winners picked
    after <date>", the escrow address and explorer link), after the deadline (`next_step`: award
    with winners adding up to the prize, or sign the prepared award at `award_url`), and one line
    each for awarded, refunded, taken_down and expired.
  - Re-scores entries with Base contracts when the last score is over 6 hours old.
  - Confirms funding or an award onchain when given the transaction hash (`tx`). The receipt
    decides which it is: a `CampaignCreated` for this `ref` is funding (the token, amount, and end
    date must match the draft; a draft that lazily expired is rescued; re-sending the funding tx
    of a live campaign returns the live result), an `Awarded` from the campaign's escrow is the
    award. A `CampaignCreated` for this `ref` from a second wallet is reported as a second escrow,
    by address, and the operator refunds it. Without `tx`, `status` does not search the chain for
    an unreported deposit; that automatic lookup is a pre-mainnet item (section 8).
- `award` (`ref`, `winners: [{entry_id, amount, reason}]`):
  - Only the creating installation can call it, and only after `ends_at`.
  - **Validates:** every `entry_id` is an entry of this campaign, and the amounts add up exactly to
    the prize.
  - **Returns:** the `award_url` (`earnkit.com/award/<ref>`) plus the raw `award` transaction, built
    from each entry's payout wallet. The
    sponsor's wallet must sign it, because the contract checks the sponsor onchain.
    `show_to_sponsor` lists each winner (project name, entry, amount, reason) and EarnKit's fee;
    `next_step`: sign at `award_url` (or send the transaction), then `status` with the tx.

Errors use the existing pattern (zod + typed errors → readable `isError` results).

## 4. Builder side (mostly existing)

- **Listing:** sponsor campaigns show in `list_programs` like any program, flagged `new` through
  "Since you last checked". Their line reads "by <sponsor> · 5,000 USDC pool in escrow ·
  closes …". When two of a builder's fits are equally quick, the larger known per-winner award
  wins "Fastest" (a USDC campaign's prize / winners; for program files, an optional
  `max_award_usd`, stored as `programs.max_award_usd`; unknown counts as 0).
- **Details:** `get_program` adds `campaign.sponsor`, `pool` (with the escrow link on BaseScan),
  `criteria`, and `judged_by: "the sponsor, using EarnKit's score as a guide; picks and reasons
  are public"`. It makes no `verified_at` claim for a sponsor campaign: `verified_note` says "Set
  by the sponsor; the prize is held in escrow onchain (campaign.escrow)."
- **Entering:** builders enter with `record_submission`. Required fields are project name,
  description, repo, live link, and payout wallet. Contracts are optional; Base contracts are
  validated as deployed during the campaign and scored. One entry per repo per campaign (both
  kinds; the repo link is compared lowercased, without `www.`, a trailing `/` or `.git`).
- **Status:** "Your campaign entries" never shows "#N of M" for a sponsor entry unless it's
  scored. It says "entered · winners picked after <date>" while live, "not picked this time" once
  awarded, "no winners; the sponsor was refunded" once refunded, and "removed by EarnKit; the
  sponsor was refunded" after a takedown.
- **Winning:** the existing "you won <amount> <token> with <project>" alert appears once the award
  is confirmed.

## 5. Web pages

- `/fund/[ref]`:
  - **Shows:** the campaign, the pool, and the split (90% prize / 10% fee, paid only on payout),
    plus a sponsor-terms checkbox.
  - **Wallet:** connects a browser wallet (viem, injected provider) and switches to Base.
  - **Sends:** `approve` (factory) then `createCampaign`, then confirms (same check as `status`)
    and links to the live campaign.
  - A draft whose deadline is under 10 minutes away (or past) can't be funded: it shows "This
    draft's deadline has passed. Ask your agent to create a new campaign." and no deposit button.
- `/award/[ref]`: shows the winners (project name, entry number, wallet), amounts, and reasons
  exactly as the sponsor's agent sent them, plus EarnKit's fee released on payout; connects the
  sponsor's wallet and sends `award` to the campaign's clone. After a confirmed payment only
  "Paid N winner(s). Done." remains.
- `/campaigns/[slug]` (existing):
  - Headed "Sponsored campaign · agents only" (EarnKit's own: "EarnKit campaign").
  - Adds the sponsor and the escrow link.
  - Until some entry is scored, a plain entry list (project, links, status) with no rank or
    wallet count. Status: "entered", "won <amount>", "not picked", "no winners — sponsor
    refunded". A taken-down campaign is 404, as is a closed EarnKit campaign with no entries.
  - After the award, adds winners with amounts and reasons, flagging any winner whose address isn't
    an entry's payout wallet.
- `/sponsor-terms`: short terms the fund page links to.

Wallet-facing pages render only plain text from sponsors and only http(s) links (same rule as
`/p/[id]`).

## 6. Admin (local, operator key)

`pnpm campaign` gains:

- `award <ref> --winners id:amount,… [--execute]`: the fallback after the 7-day grace (same checks
  as the tool). Winners are the top eligible entries by score, or the owner's judgement when
  there is no score, published with reasons.
- `refund <ref> --reason no-eligible|takedown [--execute]`: a takedown also sets
  `state = taken_down` and hides the campaign right away. `--escrow <address>` refunds a specific
  escrow for this ref instead (checked onchain to be the factory's clone for this ref), such as a
  second deposit from another wallet; the campaign's own row is left unchanged.
- `sync <ref>`: prints the database state next to the chain state.
- `sync <ref> --tx <hash>`: repair. Confirms that funding transaction (including the rescue of an
  expired, funded draft) or award transaction exactly as `status` would, then prints both states.

All are dry runs without `--execute` and sign with `OPERATOR_PRIVATE_KEY` (0x + 64 hex) from the
local shell only. `--help` lists every command. Errors print one readable line and exit 1. Before
signing, `award` checks the escrow is Funded and chain time is past `endsAt + 7 days` ("The
fallback opens on <date>."), and `refund` prints who receives the money and refuses unless the
escrow is Funded.

Unfunded drafts expire after 7 days, or once their deadline is under 10 minutes away
(`createCampaign` would revert). This is checked lazily: on `status`, and when `fund_url` is
opened. A late funding receipt still rescues an expired draft.

Human-facing dates use one format ("Oct 6, 2026, 06:51 UTC"); machine fields stay ISO.

## 7. Testing

- **Contracts (Foundry):**
  - Unit tests covering every branch and every revert, at 100% branch coverage of our code.
  - Invariant fuzzing (random call sequences by sponsor, operator, owner, pauser, strangers) for
    every property in section 1.
  - Symbolic checks (Halmos) of the core properties for all inputs: award pays exactly
    `prize + fee`, refund pays exactly `prize + fee`, at most once, and only by the allowed
    callers and times.
  - A fork test with real Base USDC.
  - Static analysis with Slither and Aderyn: no high or medium findings left unexplained.
  - An independent audit of our code (factory + campaign) before any mainnet deployment.
- **App:**
  - Unit tests for draft validation, award validation (entries, sums, decimals), presentation
    lines, and fee wording.
  - Integration against anvil with the contract deployed: create → fund (via raw transactions) →
    confirm → enter → award → "you won"; plus fallback, refund, and takedown.
- **Testnet end to end:** a Base Sepolia deployment with test USDC, through the real pages and a
  browser wallet.

## 8. Rollout

1. Contract and tests.
2. Deploy to Base Sepolia, then run the full end-to-end flow.
3. Before mainnet, all of:
   - an independent audit of the contracts; fix the findings and re-test;
   - a clean Aderyn run (`npx -y @cyfrin/aderyn .`). Aderyn could not run in the build
     environment (its installer exited without installing the binary), so it has not been run
     yet. It adds to the audit; it doesn't replace it;
   - a real-Postgres concurrency check: run `pnpm sponsor:e2e` against a real Postgres (local or
     staging), to prove the `FOR UPDATE` serialization of `confirmFunding` and `confirmAward`
     (the build-time runs used PGlite, a single connection);
   - an automatic onchain lookup of an unreported deposit (`getLogs` or Blockscout for
     `CampaignCreated` by `ref`), so `status` can confirm a funded draft without the tx hash.
     Until then, a deposit whose confirm never ran needs the sponsor's tx hash (`status` with
     `tx`) or the operator's `pnpm campaign sync <ref> --tx <hash>`.
4. The owner deploys to Base mainnet from their own wallet (with a script I prepare):
   - the `TimelockController` (48 h; the owner's wallet as proposer and executor);
   - the factory, with USDC capped at $10k plus the operator, treasury, and pauser, then ownership
     handed to the timelock;
   - verified source on BaseScan, and `ESCROW_FACTORY_ADDRESS` set on Railway.
5. The owner runs the first real campaign as a small sponsor (e.g. 100 USDC).
6. Raise caps (through the timelock) only after a track record; then add a bug bounty.

## Risks

- **Contract bug:**
  - Our code is about 100 lines on OpenZeppelin parts.
  - Each campaign is isolated, so a bug can't drain other pools.
  - Caps limit exposure.
  - Invariants, Halmos, and Slither ran during the build; an independent audit, plus a clean
    Aderyn run, comes before mainnet.
- **Admin key compromise:** the owner can only change caps, operator, treasury, and pauser, and
  only after a public 48 h timelock. Because each clone snapshots `operator`/`treasury` at
  creation, the owner can't redirect an existing campaign's operator or fees by rotating either
  one — `setOperator`/`setTreasury` only ever apply to campaigns created afterwards, so the owner
  can't touch deposited funds. A stolen operator key can only refund sponsors, or award after the
  grace period, still paying the whole prize to someone; it can't move money to itself unless it
  names itself a winner, which the leaderboard flags. Mitigation: the operator key stays offline
  except when used. Trade-off: a compromised operator key can't be rotated out for campaigns
  created before the rotation — those clones keep using the old (compromised) key. This is
  mitigated by keeping the operator key offline in the first place, and because the sponsor can
  always award the campaign first, during the 7-day grace, before the operator's fallback window
  opens.
- **Sponsor self-dealing:** public flags on the leaderboard; takedown for obvious abuse.
- **Misleading or spam campaigns** (no pre-review): the takedown command refunds them, and sponsor
  text is plain and length-limited.
- **Legal:** EarnKit takes a fee for prize escrow. Before mainnet, a sponsor terms page is required
  on funding; a quick legal read is recommended (the owner's call).
- **Agents without the sponsor's wallet:** the fund and award pages exist for that; raw
  transactions are for agents that do have one.
