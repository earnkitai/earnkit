# v3.8: additive-only guard for the deploy migration

Approval: earnkitai/earnkit#159. No flag (a build/deploy check, no runtime behavior).

## Why

Every deploy runs `apps/frontend/db/schema.sql` (railway.toml `preDeployCommand` -> `pnpm predeploy` ->
`db:migrate`). The file is meant to be additive and idempotent, but nothing enforced it: one stray `DROP COLUMN` or
unscoped `UPDATE` would run against production on the next deploy.

## Design

- `lib/v6/schema-guard.ts` (static, no DB): strip `--` and `/* */` comments (quotes and `$tag$` bodies respected), split
  into top-level statements, normalize (whitespace collapsed, trimmed). A statement trips a rule if it is a `DO` block,
  a `CREATE [OR REPLACE] FUNCTION/PROCEDURE/TRIGGER/RULE`, or contains `DROP TABLE|COLUMN|SCHEMA|TYPE`, `TRUNCATE`,
  `DELETE`, `UPDATE`, `ALTER ... TYPE`, `RENAME`, `SET NOT NULL`, `REVOKE`, any other `DROP`, or is a `CREATE TABLE` /
  `CREATE [UNIQUE] INDEX` without `IF NOT EXISTS`. Rules match anywhere in the statement, so DO bodies are covered too.
- `lib/v6/schema-allowlist.ts`: the 31 statements in today's file that trip a rule, each keyed by its exact normalized
  text with a one-line reason (drop-then-add constraint pairs, `DROP INDEX IF EXISTS` replacements, `DROP NOT NULL`,
  `WHERE ... IS NULL` backfills, the two dedupe `DELETE`s before unique indexes, the owner `SET NOT NULL` DO block, the
  `owner_people` drop/re-create, the grant DO block). Editing any of them, or adding a new one, fails.
- `scripts/db-migrate.mts` runs `checkSchema` before importing the DB module; on a violation it prints one line per
  statement (cut to 160 chars) and exits 1, so Railway stops the deploy before any SQL. It takes an optional schema path
  (argv only) so the test can feed an injected file.
- Fail closed by construction: anything matching a rule and not listed is a violation. Over-matching (e.g. a string
  literal containing `UPDATE`) only costs an allowlist entry.

## Not covered

- `ADD COLUMN` without `IF NOT EXISTS`, `CREATE VIEW` without `OR REPLACE`: not destructive; a rerun fails loudly.
- Semantics of allowlisted statements are reviewed by people, not proven idempotent by the guard.

## Tests (lib/v6/schema-guard.test.ts)

Current file passes; no stale allowlist entry; each injected kind fails with its rule (DROP TABLE, DROP COLUMN, DROP
SCHEMA, DROP TYPE, TRUNCATE, DELETE, UPDATE, ALTER COLUMN TYPE, ALTER TYPE, RENAME, SET NOT NULL, unlisted DROP
CONSTRAINT, DROP INDEX, CREATE TABLE/INDEX without IF NOT EXISTS, DO, CREATE FUNCTION); an edited allowlisted statement
fails; comments ignored, quotes and `$$` bodies not mistaken for comments/terminators; `db-migrate.mts` exits 1 on an
injected `TRUNCATE` without connecting; the real file applied twice on the test DB succeeds and `applications` has
`stage`, `held_reason`, `proof`, `round`, `draft_text`, `draft_check`, `final_hash`.

## Production effect

None on data: schema.sql is unchanged. The deploy now stops if a future destructive statement is added unlisted.
