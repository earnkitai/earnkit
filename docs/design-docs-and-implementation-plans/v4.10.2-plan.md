# v4.10.2 Fits one reply Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Fix the five problems from the owner's CTO dogfood of v4.10.1 in production (2026-11-02):
- the ready set fits one short reply;
- programs the builder isn't eligible for drop out;
- the Builder Code is asked and the GTM plan isn't invented;
- the deadline and shipping data are right;
- API edits to live programs can be reverted from a daily digest.

**Architecture:** The root causes, with file:line references and the tests that pin current behaviour, are in `docs/design-docs-and-implementation-plans/v4.10.2-findings.md` (items 1 to 5). Every implementer reads its item first.

**Tech Stack:** Next.js 16, TypeScript, Postgres, node:test via tsx.

**Spec:** The CTO's report (quoted under each task) and the owner's answers on 2026-11-02:
1. "Only include if ≤4 asks": the set holds only programs the builder can finish with one short reply, at most 4 answers across the set. Bigger programs move to "also open" with one line, e.g. "Base needs 9 answers from you, want to start it?".
2. GTM plan: "You give 1 line, agent expands". EarnKit asks one short question ("your plan for the next 3 months, one line?") and the agent writes the full answer from it.
3. Live edits: "Live, with 1-click revert". Reward and deadline edits on an approved live program go live. The owner gets a daily digest email of the changes, with a one-click revert per change.

## Global Constraints

- Copy: short, money first, no emojis, never em dashes, never "coin" or "points". Exactly one easy reply, last. Never claim the builder qualifies or that an application was sent. Under 48 hours, say the hours left, never a day in a zone.
- Honesty: never say "Ready" or "every answer is filled" unless true. Never invite an answer the builder can't truthfully give.
- Costs flat: no new service, no new cron (the digest rides the existing cron), no server LLM call. Email goes only to the owner (`owner-mail.ts ownerMail`).
- Tests: `cd apps/frontend && DATABASE_URL=postgresql://localhost:5432/earnkit_test node lib/earnkit/fixtures/test-db-template.mjs && <files via xargs> DATABASE_URL=... npx tsx --test --import ./lib/earnkit/fixtures/test-guard.ts`. Known failures that may stay: R9 "Bench", v4-nudges "fix round 1 (2, 4)" and "fix round 2: not counted yet", and the v46-stripe "failures store nothing" flake (passes alone).
- Stage explicit paths. Never commit zz-* files. Commits end with "Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>".

## Rulings (controller, 2026-11-02; the owner can reverse them)

- R1: "Asks" counts every answer only the builder can give for a program, contact item included, after held data fills what it can. The set is filled greedily in rank order while the running total stays at most 4. A program that alone needs more than 4 never enters the set; it goes to "also open". The opener says how many answers the set needs ("I need 3 answers from you first"), or "Ready" when it needs 0. The agent JSON (`ready.programs[].asks`) and READY_ASK_NOTE carry only the in-set asks, never more than 4, and the "After that I'll ask for..." line goes.
- R2: The Builder Code is asked as a need whenever the form requires it and the repo check hasn't found one. It counts toward the 4.
- R3: A program whose eligibility rule requires a chain or product the project doesn't use is "not eligible": it never enters the set, and the reason can show in "also open" in one line. This needs a new program-file flag (`chain_required: true`), set on Circle Developer Grants because its source says Arc and Circle products must be core. A soft chain mismatch stays a long shot.
- R4: `arbitrum` is added to the allowed chain list, and the Arbitrum Open House São Paulo program is retagged `["arbitrum"]`. This corrects a data error; it doesn't change the curation focus. Cost if wrong: one more chain chip.
- R5: `closes_in` reads hours under 48 ("closes in 19 hours"), whole days from 48 hours ("closes in 16 days"), and "rolling" for rolling programs. It is never empty for an open program.
- R6: `shipped_last_week` names the last finished ISO week. When that week's ship-log row isn't written yet (Monday before 15:00 UTC), it comes from the repo reading for that week (commit count, no AI summary), never from an older row.
- R7: The revert digest runs from the existing cron once a day. It lists each applied API write from the last 24 hours that changed a live program: create, reward, amount, deadline or link. Each row has a revert link, signed like the approve link (HMAC with EARNKIT_AUTH_SECRET, a confirm page, POST to act, single use, 7 days). Reverting re-applies the previous applied body, or closes the program if the write created it. No digest is sent when nothing changed.
- R8: `prepare` agrees with the ready set. It never counts a held field such as the email as "you add".

## Review Focus

- A set whose top program needs 5 asks while the next needs 2: the set holds the second, and the first goes to "also open" with its count.
- A builder who answered some asks in an earlier session: the bank fills them, and the count drops.
- Circle for a project on Arc: it stays eligible. For a project not on Arc, it's out.
- A revert of a write whose program has had a later write: revert only the latest, or refuse plainly.
- The digest on a day with no changes sends nothing. The cron runs more often than daily (about every 6 hours), so the digest must send at most once per day.
