### Where the "9" comes from: three surfaces, all real

**(a) Raw opener JSON: `ready.programs[0].asks` holds 9 entries for Base.**
- The entries are full_name, telegram, founding_team, usage_numbers, demo_loom, contract_address, revenue, primary_challenge and credits.
- Source: `bench-find.ts:1344` (readyCommit) maps every `drafts[i].only` field, with no cap.
- `READY_ASK_NOTE` (`ready-copy.ts:18-19`) tells the agent: "If they also give what a program asks of them (ready.programs[].asks), split their words by field into answers". That invites the builder to answer everything on the yes.
- readyAnswer takes every program's items on the first yes (the `readyBank` comment: "on the first yes every program's").
- So the 4-item cap (`READY_NEED_MAX`, `bench-find.ts:1065`) applies only to `ready.need`, which the opener does not carry at all.
- Side bug: the opener exposes 11 answer keys across the set (Base 8 incl. `contact`, Circle 3). `READY_ANSWERS` (`program-file.ts:55-58`) refuses more than 8 ("At most 8 answers."). An agent that follows the note fully gets a schema error.

**(b) Shown text: `readyNeedsLater` (`ready-copy.ts:225-226`) names every later field.**
- That is "Final fix 2 (I3: every one, no 'and N more')", called through `needAsk` (`bench-find.ts:1210`) and `readyStillNeeds`.
- The yes names Base's 4 items now (5 fields, since contact has 2 slots) plus Base's 4 later: 9 Base fields in one reply. With Circle's 3, it names 12 fields.
- The cap is on items, not on fields or words. `readyNeeds` (`bench-find.ts:1179-1207`) counts the contact item as 1 however many slots it holds, and the "later" list goes into the same sentence uncapped (`needsList(..., Infinity)`).

**(c) The opener's own line** (`needsOfDraft`) says "... usage numbers and 5 more". This is honest, but it never states the total.

The prepare path is not the cause. The coach's cap holds there (`coach.ts MAX_BULLETS 4`). But prepare's kit itself says "I filled 4 of 16 answers... You add 12 more in the form" (probe2.json). That is the CTO's "about 12".
- prepare does not apply `heldAnswers`, so the held email shows as missing there (`draft-application.ts:124-129` only adds the claimed X handle).
- That contradicts the ready flow's "open with every answer in place".

### Root cause

The opener's head verb is 'drafted' whenever any program has needs (`ready-copy.ts:164`). It never says how many answers the builder owes. The 4-cap governs only `ready.need.items`, while two other channels carry everything:
- the opener's `ready.programs[].asks`, plus `READY_ASK_NOTE`, which invites a full answer on the yes;
- the yes/still sentence `readyNeedsLater`, which names every later field.

### Minimal fix (v4.10.2)

1. **Opener head.** Say the honest count instead of "drafted".
   - Signature: `readyOpener(o: {...; owed: number; askNow: number})`.
   - Text: "Jenil, I've started 2 applications for you, worth up to $5K, plus a $100K long shot. 12 answers only you can give; I'll ask 4 at a time."
   - Compute `owed` in readyCommit as `drafts.reduce((n, d) => n + d.only.length, 0)`.
2. **`readyNeedsLater`.** Name counts only, never fields.
   - Signature: `readyNeedsLater(later: readonly { title: string; n: number }[]): string`.
   - Output: "Then 7 more: 4 for Base, 3 for Circle."
   - Add `n` (the item count) to `ReadyNeed.later` entries at `bench-find.ts:1186` and `:1201`. Keep `phrase` for the next ask.
3. **Opener JSON.** Emit `ready.need: needFields(readyNeeds(drafts))` (the capped first ask).
   - Remove `asks` from `ready.programs[]`, or keep it as `owed: n`.
   - Change `READY_ASK_NOTE` to "If they also give what ready.need.asks lists ...".
   - Make readyAnswer on the first yes take only `readyNeeds(drafts).items`, not every program's items. Then a yes can never carry more than 4 items or 8 keys.
4. (Optional, same theme) In `draftApplication`, merge `heldAnswers(...).held` under the agent's answers, so prepare's "You add N more" agrees with ready.

## 2. Circle asks for "your Circle and Arc integrations"; EarnKit has none

### Code and data

- Circle file: `chains: ["arc"]`, with no `needs_contract`. Its rules say "Arc must be core to your flow of value... Circle products ... must be meaningful building blocks." It is a hard eligibility rule.
- `bench-find.ts:916-918` (planPath): `cardFact(c, needs, myChains(...))` gives `kind 'chain'` for a project not on Arc, and **adds Circle to `longShots`** (v4.10 final fix I2, deliberate). `programNeeds` (`:2944`) gives `[]`, because there is no needs_contract, so Circle has no gap.
- `bench-find.ts:1576` marks it `longShot: true`. `ready-set.ts:47` (`if (g.longShot === true) return [of(g, 'long_shot', ...)]`) keeps it in the set with no gap check.
- v4.10.1 Task 1 made `integrations` a need (file: `from: builder, kind: other`, so `mustGive` is true at `conversation.ts:688-693`). The ready flow therefore asks the builder to describe integrations that don't exist.
- On the pre-sync DB row (`how_it_works`, from project), it was worse: `mustGive` is false, so READY_NOTE told the agent to draft it, an invented answer.

### Root cause

A grant whose chain the project isn't on, where the chain is a hard rule, is put in the ready set as a "long shot" and drafted like any other. Nothing distinguishes "unlikely" from "ineligible". The fit cell already says "not yet, they look for apps on Arc".

### Minimal fix

Leave chain-mismatch grants out of the ready set. They stay in the programs table, which already says "Not yet: they look for apps on Arc".
- `GapGrant`/`MoveProgram` gain `offChain?: boolean`, set at `bench-find.ts:917`: `if (fact.kind === 'chain') { longShots.add(c.id); offChain = true }`.
- In `readySet` (`ready-set.ts:42-50`): `if (g.offChain) return [];` before the longShot branch.
- Optional: one plain line after the set, "Circle funds apps built on Arc with Circle products, so it doesn't fit EarnKit yet." It would be a new `readyOffChainLine(names: string[])` in ready-copy.ts, said once a session.
- Cheaper alternative: answer the integrations field from the chain fact. Pre-fill "None yet" and never ask. That is honest but files a non-qualifying application, so it's not recommended.

### Tests that pin current behaviour

- `v410-find.test.ts:768` (Circle is a long shot, last), `:794` (Circle "Needs your Circle and Arc integrations ..."), `:230` (yes opens a16z and Circle), `:290` (skip 3 parks Circle).

## 4. Data: closes_in empty; shipped_last_week = Oct 19; Arbitrum tagged Robinhood

### closes_in

Computed in four places:
- `entry-text.ts:99-102 closesIn`, used by `withClosesIn` (`:130`). This covers find's `programs` via `tools.ts:2713-2730 agentPrograms`, plus list_programs at `tools.ts:1141/1211`.
- get_program: `tools.ts:1219` through `agentClosesIn` (`tools.ts:2747`).
- The REST API: `programs-read.ts:94/143`.

All four call `deadline.ts:71-79 hoursLeft`, which **returns null at 48 hours or more** (`if (left >= 2 * 24 * HOUR_MS) return null;`) and for rolling programs. That is v4.8.2 R4 by design: the field exists only for urgency.

Snapshot (probe.json, find `ask: programs`): every listed program has `closes_in: null`.
- Alliance (Nov 18) is 16 days out.
- Base, Circle, Arc Builders Fund, Base Ecosystem Fund and Z Fellows are rolling.

Also stale: `arc-microgrants-studio` (ended Nov 2 04:59Z) and `a16z-speedrun` (ended Nov 2 07:59Z) still have `status = 'active'` in `programs`. They are filtered by date, not closed.

Root cause: the semantics, not a bug. A field named `closes_in` that is null for everything beyond 48 hours reads as missing data.

Fix:
- Make `closesIn` always say something for an open, dated program: "in 16 days" when ≥ 48 hours, "rolling" for rolling, null only when closed/upcoming.
- Keep the summary swap (`summaryIn`) under 48 hours only. Signature unchanged.
- In `deadline.ts`, add `timeLeft(endsAt, now): string | null` ("in N days" past 48 hours), used by `closesIn` / `agentClosesIn` / programs-read. `hoursLeft` stays for copy.
- Tests: `v482-fixes.test.ts:225-238` (asserts null at 5 days, rolling and passed) and `:282-288` (null at exactly 48 hours).

### shipped_last_week

- Source: `reply-facts.ts:97-99`. `d.log.find((c) => c.summary || c.text || c.commits)` is the newest ship-log card from `project_updates`, labelled "last week" whatever its week.
- Snapshot: `project_updates` for builder 17 has weeks 2026-09-28, 10-05, 10-12 and **10-19** only. No builder has a row for 2026-10-26.
- The repo reading has the data: `source_readings.signals.commit_counts["2026-W44"] = 88` (the week of Oct 26).
- Why no row: `week-facts.ts:300-301 weeklyFactsStep` writes last week only on Monday at or after `WEEKLY_HOUR_UTC = 15`. `backfillStep` (`:414`) deliberately skips the newest week before then (`all.slice(1)`).
- On Monday, Nov 2 before 15:00 UTC (20:30 IST), and until the next real cron run after it, the newest row is Oct 19. The cron is an "hourly" GitHub schedule that in practice runs about every 6 hours (memory).
- Root cause: the fact is labelled "last week" but reads "newest written week". The week's row is written only at Monday 15:00 UTC.

Fix in `reply-facts.ts`:
- Only `if (last.week === lastFinishedMonday(now))` emit `shipped_last_week`.
- Otherwise emit `{ week: lastFinishedMonday(now), commits: <reading's commit_counts for that ISO week>, pending: true }` (weekCounts / the `readingOf` reading). Or omit it and add `latest_logged_week`.
- Test: `v31-answerable.test.ts:227-228` (asserts week equals lastFinishedMonday; it still holds). Add a Monday-14:00Z pinned-clock case.

### Arbitrum tagged Robinhood

- File: `programs/arbitrum-open-house-sao-paulo.json`, `"chains": ["robinhood"]`, added in #111 (6328d1a0, Programs refresh 2026-11-01).
- Source rule (the same file's `rules[1]`): "Your project must be deployed on an Arbitrum chain to qualify, for example Arbitrum Sepolia, Arbitrum One or Robinhood Chain." Robinhood Chain only gets 1 of 3 reserved prizes.

## 5. Writes have no revert; reward/deadline changes to a live program skip review

### Bypass

- `programs-api.ts:305-307` (applyUpsert): the link check / pending hold runs only `if (mode.kind === 'write' && (!row || row.submission_url !== clean.submission_url || !sameChains(row.chains, clean.chains)))`.
- Every other field goes straight to `upsertProgram(clean, 'api', tx)` (`:328`), live at once. That includes `reward`, `max_award_usd`, `min_award_usd`, `pool_usd`, `ends_at`, `starts_at`, `status` and `summary`.
- The row read at `:304` selects only `source, submission_url, chains`.
- This is ruling R4's last sentence ("Updates to other fields on a live program stay live"), pinned by `v4101-link-check.test.ts:316` (a title change goes live).
- `program-pending.ts` (header, `:10-22`) only knows the link check.
- Snapshot: `program_writes` has 0 rows. No API program exists in prod yet, so the exposure is future-only.

Fix:
- Widen the row read to `reward, max_award_usd, min_award_usd, pool_usd, ends_at, starts_at, status`.
- Add `const reviewed = (row, clean) => moneyOrDateChanged(row, clean)`, a pure function in program-pending.ts: `export function reviewFields(row: Pick<ProgramFile, ...>, next: ProgramFile): string[]` returns the changed sensitive keys.
- Hold the write as pending when the list is non-empty, with the same row, email and approve flow, and `reason` = "reward / ends_at changed on a live program". Do not route it through the link check.
- `pendingMailText` gains a "Changed: reward $5K → $50K" line (old vs new).
- Keep the cosmetic fields (title, description, rules, ideas) live.
- Tests: update `v4101-link-check.test.ts:316` (title stays live) and add "max_award_usd / ends_at change → 202 pending, row keeps old value, approve applies".

### Revert

What exists:
- Every applied write audits the full cleaned body: `audit(tx, {..., result: created|updated, body: clean})` at `programs-api.ts:331-333`. An approval also flips the pending row to `approved`, which keeps its body.
- `unchanged`, refusals and `close` rows have no body.
- The pre-write state is computed (`before = snapshot(tx, id)`, `:325`) but discarded.
- `Envelope` (`:190-193`) has only `upsert` and `close`. No revert is reachable from POST /api/programs/write or GET /writes (`programs-read.ts programWritesGet`, which returns no bodies).

How a revert works with the existing rows:
- "Revert write W" means: find the newest row with `program_id = W.program_id AND id < W.id AND result IN ('created','updated','approved') AND body IS NOT NULL`.
- Re-apply its body with `upsertProgram(prev.body, 'api', tx)` under the same row lock and `source = 'api'` guard. No link check: the body was live before.
- If W was the `created` row (nothing before it), revert means close (`UPDATE programs SET status='closed'`).
- Reverting a `close` re-applies the last body (status restored).
- Audit as `action 'revert', result 'reverted', reason 'reverted write W'`, with the restored body.
- Add `'reverted'` to `NEWER_RESULTS` (`:282`) so an older pending write can't be approved over it.

Minimal surface:
- An owner-only Envelope variant `{ action: 'revert', write_id: string }` behind the same Bearer gate.
- Or, matching R4's email flow: a signed revert link in each applied-write notification (`approveToken` with a `program-revert:v1:` MAC prefix). The confirm page POSTs, as program-approve.ts does.
- Signature: `export async function revertWrite(writeId: string, deps?): Promise<{ kind: 'reverted'; id; restored: 'body' | 'closed' } | { kind: 'not_revertable'; state }>`.
- Optionally start storing `before` (the snapshot) on each audit row, as `body.prev` or a new `prev jsonb` column (migration), so a revert never depends on an earlier row's existence.
- Tests: new cases in `v4101-link-check.test.ts` / `v49-programs-api.test.ts`. No existing test pins the absence of revert, apart from `Envelope` strictness (`v49-programs-api.test.ts`: an unknown action → 400).
