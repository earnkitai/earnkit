# v3.8 E5: X sign-in on the install path

Plan item 2 (X half), PR table row E5. Stacked on E4 (it reuses the consent page and E4's `install_signin` flag).

## Why it is new code

The legacy X sign-in (`lib/earnkit/x-oauth.ts`, `x-install.ts`, `app/x/callback`) was deleted in the v5 cut and stays
deleted (`no-v4.test.ts`). This is a fresh `lib/v6` module.

## The X app (reused, not new)

It reuses the X app the pre-v5 sign-in used: `X_CLIENT_ID` and `X_CLIENT_SECRET` (already set in production), and the
redirect URI exactly `<EARNKIT_URL>/x/callback`, which is what that app has registered (the legacy `xCallbackUrl` was
`${siteUrl()}/x/callback`, and `siteUrl()` and `publicOrigin` both read `EARNKIT_URL` without a trailing slash). So
only `app/x/callback/route.ts` comes back (registered in `no-v4.test.ts` as `x`, `x/callback`), as a thin route to
`lib/v6/x-routes.ts`; `lib/earnkit` stays deleted. The start route stays `/auth/x`. No new Railway variable: the only
switch is `EARNKIT_FLAGS=install_signin,x_signin`. Not verified from here: that the X developer portal still lists
`/x/callback` and has OAuth 2.0 (confidential client) enabled.

## Flow (only with the flags `install_signin` and `x_signin`, and the X app set)

1. `/oauth/authorize` answers a chooser page: Sign in with GitHub (straight to GitHub, as in E4) or Sign in with X
   (`/auth/x?s=<install state>`). The nonce cookie is set here. With the flag off it is E4 unchanged.
2. `GET /auth/x` checks the install state and the nonce cookie, then 302s to `https://x.com/i/oauth2/authorize` with
   scopes `users.read tweet.read`, `state` = the install state, and an S256 PKCE challenge. The verifier is
   `HMAC(secret, 'x-pkce:' + nonce)`, so nothing is stored between the redirect and the callback.
3. `GET /x/callback` (rate limited like the GitHub callback) checks state and cookie, maps `error=access_denied`
   to the denied page, trades the code at `https://api.x.com/2/oauth2/token` (Basic client auth plus the verifier), and
   reads `GET /2/users/me`. The token is dropped. There's no `offline.access`, so no refresh token. Then it 303s to E4's
   consent page with `who = { by: 'x', user }`.
4. Connect: `upsertXBuilder` (keyed by `x_user_id`), `markVerified(by 'x')`, then the code. Same X account twice is one
   builder and one person.

The consent page names the provider ("signed in to GitHub as @login" or "to X as @handle"). The GitHub page's lines
are E4's word for word (pinned in `install-consent.test.ts`), so with `x_signin` off the install path equals main. One
transient difference at deploy: the consent state now carries `who` instead of `user`, so a consent page shown in the
15 minutes before the deploy lands on the failed page (only reachable if `install_signin` is already on).

## Schema (additive, idempotent)

- `builders.github_id` and `login` drop NOT NULL. That's a no-op once dropped.
- `builders.x_user_id`, `x_handle` (new, nullable). Unique index `builders_x_user_id`.
- `builders_one_account` CHECK (added once, in a DO block): there must be a GitHub id or an X id. A GitHub id comes
  with its login, and an X id with its handle. Every production row today has a GitHub id and login, so the check
  validates.
- `owner_people`: `identity_source` is `x_signin` for an X-only builder. `x_handle`, `x_proven` and `slug` read the
  builder's X fields first.

## Safety of nullable login

An X-only builder has `login = null`, never the X handle. That way nothing keyed on GitHub logins (owner lists, team
checks, `/me` delete confirm) can mistake an X handle for a GitHub login. `/me` shows and confirms `@handle` for
such a builder (`handleOf`). The owner/dogfood env lists already match X handles (`envListReason`'s `xHandle`). No
X-only builder gets a `/me` session in this PR: the link flow stays GitHub only.

## Not in scope

- Linking a GitHub and an X account into one builder.
- X on the `/link/<code>` path.
- Revoking the X token after the read. It expires in 2 hours and is never stored.
