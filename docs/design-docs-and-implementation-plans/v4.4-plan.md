# v4.4 Setup order: wallet for payouts, then one token offer: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Setup is X, then code (GitHub or a no-GitHub path), then the wallet, asked only for payouts. After the wallet signs, one optional token offer. A no, or "I already have a token" (its address recorded), ends it forever.

**Architecture:** Step 3 (`walletSetupAsk`, bench-reply.ts) drops the token sentence and never sets `standing_seen.token_offered`, so the wallet proof launches nothing on its own (`launchOnProof` already requires `token_offered`). When the step-3 wallet signs (`afterStep3`, bench-find.ts), and the token offer is due (`tokenOfferDue`), the reply is the wallet's done line plus the offer, stored as the `token` ask with `setup: true`. The answer to that offer (yes, no, or an existing token) then gets the setup-done reply (`setupDoneFor`). The earlier-builder ranked offer (v4.2 Task 6) keeps its place and gets the same body. `builder_tokens.status` gains `'existing'`, written by `tell token: { existing: '0x…' }`.

**Tech Stack:** Next.js 16, TypeScript, Postgres, node:test via tsx.

**Spec:** the owner's message (2026-10-29): "get the X connected, then github or any verifiable source, then wallet and this is posed for asking for grants and future builder campaigns and lastly one token offer and if they already have a token or don't want it they can skip it and we won't ask again", and the approved answer that adds "already have one: record its address".

## Review Focus

1. A builder mid v4.0 step 3 (token sentence shown, `token_offered` set, not yet signed) signs after deploy: the token still launches as promised, and no second offer is shown.
2. Wallet skipped at step 3: no token offer appears then; once a wallet is proven later, the ranked offer appears once (as today's legacy offer).
3. Tokens flag off (`EARNKIT_BUILDER_TOKENS` unset): the sign goes straight to the setup-done reply, no offer.
4. "Already have one" with a bad address, then a good one: the second answer records it; the offer is never asked again; `/api/builder-tokens` never lists an `existing` row; `launchBuilderToken` never launches for an `existing` row.
5. A kindless bare "yes" after the setup offer launches the token (the stored ask is `token`), and the reply after that answer is the setup-done reply with outcome `launched` (or `on_its_way`).
