# v2.12.1: The X-first instant profile

Status: spec for owner review (2026-10-13). Replaces v2.12's onboarding, identity, scoring, profile and
leaderboard behavior. v2.12's storage, readers, anti-farming, cron, archives and terms stay unless
this file changes them. `EARNKIT_BUILDER_SCORE` stays off in production until the owner's own install
passes the acceptance test below.

## Why this exists (the owner's words, 2026-10-13)

v2.12 shipped strict-first: an empty profile until the builder linked proofs, X optional, random slugs, a
leaderboard of "Builder 0" rows. The owner: "This is the worst update thus far both in terms of
functionality and usage." The binding brief, quoted:

> EarnKit creates a profile for builders to keep track of their past work and ongoing future work. The
> profile is a page worth sharing with the username being the same as X. The identity everywhere shown
> is X while the data sources can vary. The profile shows a score, percentile, work of a builder. As
> soon as EarnKit is installed, a profile is created for that user using its X profile (verify it) and
> past work verified from GitHub contributions, wallet activity (if they don't have anything on GH or a
> GH at all). The profile is shareable, it creates a card that's worth bragging about. At the outset, a
> profile is built based on all past data for the builder/user. This should happen instantly without
> the builder having to wait. Add a loading skeleton but don't expect builder to wait or provide
> anything except if the agent does not have the X, wallet or GH. Each profile is a nice simple link
> with the X username in the link, not a slug.

> Don't give a zero builder a low score. Show them as "Unranked, 1 step from your first score" and give
> them a quick first win, so a blank start reads as the first step of the climb rather than a failing
> grade.

**The rule that decides every conflict below:** the first run fills the profile. When verification and
a filled profile pull apart, show the work as pending instead of hiding it.

## Acceptance test (binding, run before anything is called done)

On production, with the flag on, the owner installs EarnKit in their own agent and asks "What can I
earn?". Pass means, with no other input from the owner:
1. The first reply has exactly one yes: claim the profile (Sign in with X).
2. After the one tap, the browser lands on `earnkit.com/<their-x-handle>`; name and avatar render at
   once; sections show loading skeletons and fill within about 10 seconds.
3. The page shows their real past work (GitHub and/or wallet), each item verified or pending.
4. The page shows a score with a percentile, or "Unranked" with one next step; never "0/100".
5. Reconnecting the agent does not create a second profile.
6. The card at `earnkit.com/<handle>/card.png` looks worth posting.
7. `/leaderboard` shows real handles, no filler rows, no all-caps labels, no "outcome".

## 1. Install flow

**First `find`.** New optional input `identity`: `{ x_handle?, github_login?, wallets?[] }`. The tool
description tells the agent to fill it from what it can already read (git config, `gh auth status`,
wallet env or files, the X handle if known) and never to ask the builder for any of it. Agent values
are clues, not proof.

- If the person has no verified X yet, line 1 is the best program as today and line 2 is the one yes:
  "Claim earnkit.com/<handle> (one tap with X)." with `claim_url` for the agent to open. If the agent
  sent no X handle, the line reads "Claim your EarnKit profile (one tap with X)."
- The claim replaces v2.12's consent line. The claim page states what becomes public and how to hide
  (spec §8 of v2.12 carries over), so consent is given by signing in.
- Every reply ends in exactly one yes (owner's list item 8). A pending program question waits for the
  next reply.

**Sign in with X.** OAuth 2.0 with PKCE, scope `users.read tweet.read`, then `GET /2/users/me` for id,
username, name, avatar. One verification costs about $0.01 on X's pay-per-use API (repeat logins the
same UTC day are deduplicated). Owner setup: an app at console.x.com, a verified phone, a few dollars of
credits, `X_CLIENT_ID` and `X_CLIENT_SECRET` in Railway, callback `https://earnkit.com/x/callback`. The
callback binds the X account (immutable X user id) to the installation's person and redirects to
`earnkit.com/<username>`.

**Instant build.** The callback page renders the header (X name, avatar, handle) immediately and
streams the rest with React Suspense and skeletons. In the same request, within a 10-second budget,
EarnKit reads:
- GitHub, for the agent's `github_login`: one GraphQL call (`contributionsCollection` for the last 12
  months, owned public non-fork repos with stars, homepage and last push, merged PRs to others), plus
  npm/PyPI lookups for packages found in those repos.
- Wallets: contracts deployed and transactions on Base and Arc (Blockscout and the existing RPC reads).
- Anything EarnKit already holds: its own deploys and hosted sites, entries, wins, the token.

It scores at once (section 3) and stores the reading. Anything not finished in the budget shows a
skeleton that the next page load fills, and the hourly cron keeps everything fresh. The builder never
gets "ask again in an hour".

## 2. Identity and verification

- **X is the identity everywhere.** Public URL `earnkit.com/<x-username>`, case-insensitive with a 301
  to the canonical case. A handle equal to a site route (`programs`, `terms`, `leaderboard`, `api`,
  `b`, and the rest of the reserved list) is served at `earnkit.com/b/<handle>`. X renames: the next
  sign-in or daily refresh updates the handle; the old handle redirects for 90 days.
- **No X, no public page.** People who haven't claimed still get a private score in `score`, and are
  counted in percentiles, but have no public page and aren't on the leaderboard.
- **One person, one record.** Every installation that signs in with the same X user id joins one
  person (existing `linkInstallations` and `mergeProfiles`). The owner's split (`b-kqibm8dj` vs
  `0x7c047090`) is merged by this rule. Matching GitHub login or wallet only suggests a merge; X
  decides it.
- **GitHub is verified** when its public profile lists the same X handle, or the person signs in with
  GitHub (existing v2.9 flow). Otherwise it's shown as pending.
- **Wallets are verified** by EarnKit's own deploys for this person, or a signed message (one tap in the
  claim page, optional). Otherwise their activity is shown as pending. (Typed wallets never prove
  anything: the v2.12 post-push fix stands.)
- **Pending** work is shown on the profile with a quiet "pending" mark and adds nothing to the score.

## 3. The score (owner's guide, v2)

0 to 100 in four parts. Only verified data moves it.

| Part | Max | Counts (verified only) | v2.12.1 sources |
|---|---|---|---|
| Shipped | 20 | Live site, deployed contract, published package or app, hosted demo. Points per distinct thing shipped, front-loaded so the first ship lands real points | EarnKit deploys and hosted sites; contracts by verified wallets; GitHub repos with a live homepage that resolves; npm/PyPI publishes |
| Used | 40 | Unique real users, repeat users, transactions. Self-use and linked wallets never count | Callers of tracked contracts and builder-code-tagged transactions (section 4); package downloads (capped, as v2.12); outside stars, forks and contributors (as v2.12, capped) |
| Earned | 20 | Verified revenue, onchain fees, grants and prizes won | tokens.fun creator fees; fees into the builder's contracts; wins from `programs/outcomes` matched to entries (a self-reported win stays pending) |
| Consistency | 20 | Weeks with a ship or with users, and streaks, from any source | EarnKit's event log plus commit weeks from GitHub contributions; commits are one source among many |

- v2.12's anti-farming rules carry over unchanged, including the merged-PR caps.
- **Inactivity fade.** A part's points decay with a 90-day half-life from the last week that earned
  them, so the board stays about who is shipping now.
- **Unranked.** A score of 0 is never shown as a number. Profile, card and `score` show "Unranked, 1
  step from your first score" plus the single next step (usually "ship it": the build path, which
  needs no live site of their own). No card is offered while Unranked.
- **Starter tier.** The first verified ship moves a person out of Unranked at once and offers the
  card. The first 5 real users is called out as the big jump.
- **Percentile within a group.** v2.12.1 ships two groups: everyone, and Newcomers (first verified
  ship in the last 30 days). Profile and card show the better of the two ranks with its label, e.g.
  "Top 8% of newcomers". "Top N%" still shows only when N is 50 or less.
- Calibration stays versioned and generous; the old v1 formula's stored scores are recomputed under v2.

## 4. Builder codes on Base (owner: "Option 1")

- When a person has a verified wallet, EarnKit calls `POST https://api.base.dev/v1/agents/builder-codes`
  with it once and stores the code (`bc_...`) on the person. Event `attribution_assigned`.
- EarnKit registers its own `earnkit` code on base.dev (owner step).
- **Every app built via EarnKit carries both codes on Base.** The build kit and `prepare` give the
  agent the ERC-8021 suffix (both codes, schema 0) and the exact viem/wagmi line to add to every
  transaction the app sends. EarnKit's own Base deploys for the person carry it too. Arc and Monad
  get no builder codes (owner accepted).
- **Reading tags.** Transactions to tracked contracts are decoded for the suffix; a tagged transaction
  counts toward Used even when the contract isn't the builder's own (an app built on someone else's
  protocol). Event `tagged_tx_seen`.
- **Open risk.** Base documents this API for agents registering themselves; bulk issuing for users is
  not documented. EarnKit sends at most one request per new verified wallet, caches the code forever,
  and the owner asks Base to confirm. If Base refuses, only the per-builder code drops; the `earnkit`
  code and contract tracking still work.

## 5. Profile, card, leaderboard

**Profile `earnkit.com/<handle>`.** Header: X avatar, name, @handle, score ring (or Unranked), rank with
its group, 7-day change. Then "What they shipped": one card per project with its verified numbers and
pending items, a contribution strip, merged PRs, apps on Base and Arc, programs entered and won. No
all-caps labels, no eyebrows, sentence case.

**Card `earnkit.com/<handle>/card.png`.** X avatar, @handle, score ring, "Top N% of builders" (or of
newcomers), the best work in plain words. Funnel Display, readable at X's mobile preview size.

**Leaderboard `/leaderboard`.** One ranked list: rank, avatar and @handle, score, percentile, best work.
A Newcomers tab is the only control. Only claimed (X-verified) people with a score above 0 are
listed. No chain, program or week filters. Column labels in sentence case.

**Words.** "Outcome" is never shown to builders or on public pages. Use "best work", "what they
shipped", "people using it".

## 6. Fixes from the owner's test list

  (item 7): the build path is the fallback. `earnkit.txt` linking becomes optional and is never the
  first step (items 1, 4).
- Already-connected agents (item 9): `find` and `tell` mention "Reconnect EarnKit to get your profile
  tool" once to clients whose session predates the `score` tool.
- Programs (items 13 to 15): find out why Colosseum still shows and fix it; hide a program the person
  already entered or applied to; a program past its close date never shows as open; facts older than
  14 days are flagged to the owner's daily check.
- Odds and traction (item 12) read the new Used numbers.
