# v2.11 One yes to a shipped entry: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** DRAFT. Don't start until the owner approves the spec and answers its "Open decisions" (`docs/design-docs-and-implementation-plans/v2.11-one-yes.md`). Each task below names the decision it assumes. If the owner picks differently, change that task first.

**Goal:** a builder with no fitting repo says yes once to a small, winnable program. Their agent builds a starter with a personal twist. EarnKit deploys it (capped) and hosts it, the entry is drafted, the token is offered once at confirm, and the submit kit follows. Every shipped step goes into an append-only builder event log, and deployed contracts get 30-day and 90-day usage checks. The two live-test odds bugs are also fixed.

**Architecture:**
- **T1 is the odds fixes** in `match.ts` (`rowOdds`, `productOdds`, `Odds` gains `'unknown'`) and the rank by real use in `present.ts`, `match-projects.ts` and `tools.ts`. It is independent and needs no owner setup, so it can ship alone first as v2.10.2 (decision 8).
- **T2 and T3 build the event log:** the table, its trigger and `events.ts` (T2), then a write from each existing step, plus a backfill script (T3).
- **T4 to T6 are the starters:** facts and spikes first (T4: wallet connect under the host CSP, Arc RPC `eth_getLogs` limits), then the registry and the program field (T5), then the `arc-tipjar` starter in the chain-kits repo (T6).
- **T7 to T10 are the build path:** the no-repo lead (T7), the twist and the build kit (T8), host without a click plus deploy and host in one call (T9), and the drafted entry joined with the confirm line (T10).
- **T11 to T13 close it out:** cron usage checks (T11), terms and redaction (T12), then the journey, metric script and docs (T13).

**Tech Stack:** Next.js 16, postgres.js, zod v4, viem, `@modelcontextprotocol/sdk`, node:test via `tsx --test`, Foundry (starter repo only). No new dependency in the app.

**Spec:** `docs/design-docs-and-implementation-plans/v2.11-one-yes.md`. Brief: `.superpowers/sdd/v2.11-plan/brief.md` (binding). Owner memories: `earnkit-v210-decisions`, `earnkit-v29-wedge-decisions`, `builder-copy-style`, `cost-discipline`, `targets-effort-only`, `earnkit-program-focus`.

## Global Constraints

These carry over v2.10's Global Constraints unchanged: secrets, key separation, copy rules, the G7/G9/G10/G11 shared-client rules, additive schema, tests that keep the suite green, and the commands. Read them in `docs/design-docs-and-implementation-plans/v2.10-fixes-plan.md`. v2.11 adds:

- **Branch:** `v2.11` in `/Users/jenil/earnkit-v210`, from `9dbd372`. Never push, merge or deploy without the owner's go. Never run a bare `git stash`.
- **One question per reply.** Every builder-facing reply on the build path ends in at most one `?`, and the copy sweep checks it. Declarative asks ("Add the wallet that should own it.") are allowed next to the one question.
- **Never invent identity.** A wallet is only one the builder typed into this call or (off a shared client) the remembered one. A login is only one with a `login_basis`. A name, ticker or handle comes from the agent's build fields, which come from the builder's twist. The server never makes one up.
- **No LLM on the server.** The agent turns the twist into the name, description and feature. The server only checks them.
- **The builder signs nothing in EarnKit.** The only builder click outside chat is the program's own submit. On non-shared clients this includes no GitHub sign-in on the build path (decision 2).
- **Fail closed.** `freshPick` returns nothing unless `deployEnabled()` is true for the starter's chain, and either hosting is on (`r2Enabled()`) or the starter's site can fall back to GitHub Pages. Without a pick, the v2.10 reply stays byte for byte.
- **The event log is append-only.** No code path issues UPDATE or DELETE on `builder_events`. Writes are idempotent by `dedupe_key` (`ON CONFLICT DO NOTHING`). A failed event write is logged by class name and never fails the builder's step.
- **Cost.** No new service, no new cron schedule. The usage checks run inside today's cron, at most 20 reads a run. Deploy caps stay as in v2.10.
- **Facts only.** Arc's RPC limits, the CSP wallet behaviour and the starter's event signature come from a real run or the official docs, recorded in T4's report. Never assume them.

## Plan Rulings (spec gaps)

- **S1, the context line's count.** This counts the open curated programs that `openMoneyUsd` sums (same filter), so the money and the count always agree. The noun is singular at 1 ("1 program").
- **S2, "closes in N days".** `N = floor((ends_at - now) / 1 day)`. N = 1 reads "closes tomorrow". Under 24 hours never qualifies (`freshPick`).
- **S3, `Odds` gains `'unknown'`.** Every existing check is `=== 'good'` or `!== 'good'`, so `'unknown'` is never good. The "show more" cell for an unknown row reads `<repo>, users unknown` (never "low odds"). `qualifies`, `leadRow`, `repoCanWin` and alerts treat it as not good.
- **S4, when a repo is `unknown`.** Product tier fails only because of unchecked signals (`unchecked` includes `owned`, or includes `readme` and the score reaches 5 once they count), the live link passed, and the repo is active. Measured transactions of 0 on Base still give low "no users yet".
- **S5, the rank key.** Odds (good, unknown, low), then `hasRealUse(facts)` (measured or claimed), then traction, then row difficulty, prize and quickness, in `layout`, `bestFit`, the `match-projects.ts` fits sort and `matchRows`.
- **S6, the build path's state.** `installations.build jsonb` holds `{ program_id, starter_id, wallet?, name?, feature?, started_at }` for one build at a time. Shared clients never get the build path, since they can't build (`agent_can_build` false). A new `build.start` for another program replaces it.
- **S7, `prepare.build` shapes.** `{ start: true, program_id }`, `{ program_id, twist, name, description, feature, for_whom, wallet?, repo_url? }` and `{ program_id }` (marks the deploy-and-host call). Strict zod. Every unknown key is refused with an `agent_note`. (T8: `for_whom` is the agent's "for ..." phrase for `buildingLine`; `repo_url` gets the earnkit.txt proof line once the repo is chosen; the top-level `program_id` the MCP schema requires must equal `build.program_id`.)
- **S8, the proof line on a new repo.** The kit tells the agent to commit `earnkit.txt` with `tokenCode(installationId, repoUrl)` before calling `prepare` with `deploy`. `repoOwnershipPasses` already reads it from the default branch.
- **S9, the host gate without sign-in (decision 2).** Off a shared client, `issueUpload` accepts `repoOwnershipPasses` plus a public read of `GET /users/<owner>`. The read is cached 24 hours in `url_checks`, key `ghuser:<login>`, with `created_at` and `public_repos` in `note`. The site's slug login is the repo owner, with `login_basis` `proof_line`. On a shared client, today's sign-in stays.
- **S10, the GitHub Pages fallback.** When `host` is unavailable or refused on the build path, the reply's `agent_note` tells the agent to enable Pages on the public repo. Its next `prepare` sends `project.live_url`. A passing probe on a `*.github.io` URL whose owner equals the repo owner writes `hosted` with `detail.host = 'github_pages'`.
- **S11, `built`.** This is written on the first `prepare` with `build: { program_id }` whose repo passes the proof line. One per repo and program.
- **S12, a usage check's window.** It is due when `now - deployed.at >= 30 d` (or 90 d) and there is no `usage_check` with that window for that `deployed` event. Arc reads `eth_getLogs` in chunks of `ARC_LOG_CHUNK` blocks (from T4's fact, default 10,000), from `detail.block` to latest, at most 50 chunks a check. Anything more writes `detail.partial = true`.
