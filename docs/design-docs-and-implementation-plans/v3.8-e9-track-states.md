## Design

The ledger's stored `status` (started, applied, won, rejected, no_result, skipped; `held_at` for a hold) is left
alone, so every existing transition, count, reply and test keeps working. New columns beside it on `applications`:

| column | meaning |
| --- | --- |
| `stage` | found, registered, needs_build (on a held row); interview (on applied); delivered (on won) |
| `held_reason` | wallet, kyc, captcha, device_prompt, missing_demo, needs_yes |
| `proof` | `{ url?, confirmation? }`, required on applied |
| `round` | the program's round label |

`stateOf` reads a row as one of: found, started, registered, held, needs_build, applied, interview, won, rejected,
no_result, delivered, skipped, closed_past_deadline. A stage counts only while its row's status still matches, so a
send or result the ledger writes later supersedes it with no extra write. Closed past deadline is derived: an unsent
row whose program's deadline passed.

- Parked statuses (found, registered, needs_build) are written through the ledger's own hold path (so project,
  identity and repo-tie checks are the existing ones), then the stage is set on that row.
- interview / delivered need an applied / won row (by `application_id` when the program has several); one history
  line each.
- applied without `proof` is refused before anything is written (A9); held without `held_reason` likewise.
- `track action: list` (`limit` 1-200, default 50, keyset `cursor` on program and project): every application row of
  the owner with state, reason, proof, round, and the deadline as `{ at, zone, shown }`, where `shown` is in the
  builder's record `person.timezone` (IST for Asia/Kolkata), UTC with none. `total` is the DB count; following
  `next_cursor` reads exactly that many.
- `find` with `catalog { limit, cursor }`: every listed program (open and upcoming) by id, no fit read and no reply
  cap, `total` = the listed count.

## Dedup

The key stays program x canonical project: `applications_owner_program_identity` (identity is the canonical project)
plus one row per program and project, an earlier round's result moved into `earlier_win` by the ledger. `round` labels
the row. The build plan's extra unique index including `round` is not added: with the existing index still in place it
would enforce nothing new, and dropping the existing one is not additive. Separate rows per round would need that
index swap and every `ON CONFLICT` target changed together, in its own PR.

## Schema

Four `ADD COLUMN IF NOT EXISTS`, nullable, no backfill. On production: four empty columns.
