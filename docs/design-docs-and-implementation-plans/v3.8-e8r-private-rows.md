# v3.8 E8r: private program rows, program flags (restacked on main)

Plan: v3.8 item 5 (write path), cutover A3 (private rows) and A5 (program flags). Approval: earnkitai/earnkit#159.
Flag: `private_rows`. Supersedes #167, which was stacked on E7 (#165) and E6 (#164). This version branches from main
(E9 to E18 merged): it carries no E6 or E7 code (no official-page check, no organizer labels, no mail change). The
owner-digest masking is applied to main's `sendOwnerDigest`. Found-by fields and organizer status stay with E6r.

## Private rows

A program that cannot pass the public official-page check (apply by email, a thin client-rendered page, a form the
official page does not link) is saved by the builder's agent as a row only that owner sees.

- Storage: a new table `private_programs (owner, id, file jsonb, created_at, updated_at)`, PK `(owner, id)`. The build
  plan proposed `programs.private_owner`; a table of its own is safer: no public read of `programs` can list a private
  row through a forgotten filter, because none of them reads this table. `PRIVATE_PREFIX` (`private-`) starts every
  private id, and `ProgramFile` refuses a catalog id with it, so the two id spaces never meet.
- Write: `track` with `action: add_private` and `private { title, url (https), organizer?, reward?, ends_at?, tz?, note? }`.
  The same title (folded) updates the row; a new title gets `private-<slug>` (`-2`, `-3` on a slug clash). New rows
  count against `LIMITS.privateRows` (20 per owner per UTC day); an update is free.
- Track on a private row (by its id or title, own rows only): started, held, applied, won, rejected, no_result,
  skipped, unskip. `applied` needs `submitted_by: builder`: an agent's send is refused, so a private row is never
  submitted by an agent (and no auto-submit or standing approval reads this table). One application per private row
  (no project, no round, no gap steps). Another owner's private id reads as an unknown program.
- Account moves: `linkInstallation` moves the rows with the ledger (the builder's copy wins a clash); `deleteBuilder`
  deletes them.
- Operator reads: applications on private rows still count in totals. The owner digest and
  `GET /api/programs/applications` fold every private program into one `{ id: 'private', title: 'Private programs' }`
  entry, so the operator never reads another builder's private title. Public stats are counts only, unchanged.
- Flag off: `trackAdvertised()` is `TrackInput` itself and `trackDescription()` is `TRACK_DESCRIPTION`, so the tool
  list is byte-identical; `action` is an unknown key and refused as before.

## Hooks restored into the E9 to E11 code (all behind `private_rows`)

E9r, E10r and E11r were restacked on main without E8, so their private-row hooks were removed. They come back here,
each read only when the flag is on, so flag off runs exactly main's code path:

- `track` `action: add_private` (`addPrivate`), checked before the `track_v2` and `draft_check` handling. With the flag
  on, any other `action` value falls through to the existing handling unchanged.
- Track on a private row by id, then by title when no catalog program fits (`onPrivate`), wrapped in `withV2`, so a
  private row takes the v2 rules (proof on applied, held reason, stages).
- `afterSendAction` (interview, delivered): an own private id resolves to its row (id and title).
- `listTracked` (`track-states.ts`): a row with no catalog program reads its title and deadline from the owner's private
  row.
- Track import (`track-import.ts`): a grant with no catalog program but an https link becomes a private row
  (`private-<slug>`, `putPrivate`, no daily limit for the owner's own import); a grant with neither stays unresolved;
  `--map` may not name a `private-` id; the summary gains `private_rows`. Flag off: no `private` field on any line and
  no `private_rows` in the summary, as on main.
- `track check` (draft check) still refuses a private program, as it has no form; its text is unchanged from main.

## Program flags (A5)

Optional `ProgramFile` fields, each set only when the program's own text states it: `reward_kind` (cash, credits,
mixed), `application_kyc`, `payout_kyc`, `wallet_prompt`, `attestation`, `no_automation`. With the existing
`existing_work: new_work_only` (needs new work) and `sign_in` these are eight of the nine flags; `new_organizer`
(organizer status) comes with E6r. They are data only: they ride on find's `program` object (which already omits only `reviewers_contact`) and the
write API takes them; no behaviour reads them yet (the hold-not-auto-submit rule is item 20). Not flagged: an absent
field changes nothing.

## Schema

One new table, `CREATE TABLE IF NOT EXISTS`: additive and idempotent, no foreign keys and no ON DELETE actions (account
link and delete move or remove rows in code), so `schema-guard.ts` passes with no new allowlist entry. On production
it creates an empty table and changes nothing else.
